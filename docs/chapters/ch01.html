From Shannon to Serving

A history of language modelling, and how running a trained model—inference—became the hardest and most expensive engineering problem in AI.

Learning objectives

  1. State language modelling as conditional density estimation and relate cross-entropy, bits-per-token and perplexity.

1.1 Why a book on inference, and why now

For most of the history of machine learning, the interesting engineering happened during training. Inference—evaluating a trained function on a new input—was an afterthought: a ResNet-50 classifies an image in a few GFLOPs, one forward pass, done. Large language models broke this picture in three ways at once.

  1. Inference is iterative. An LLM produces its output one token at a time, each token requiring a full pass through billions of parameters. A 1,000-token answer is 1,000 sequential forward passes.
  2. Inference is stateful. Each pass must see everything that came before. The model carries a growing state—the key–value cache—that can be larger than the model weights themselves.
  3. Inference is where the money is. A frontier model is trained once, but served billions of times. Over a model's lifetime the compute spent answering requests routinely exceeds the compute spent training it (§1.9), and with reasoning models that think for thousands of tokens before answering (§1.11), the ratio keeps growing.

The result is a new discipline—LLM inference engineering—sitting at the intersection of numerical linear algebra, computer architecture, distributed systems and queueing theory. Companies hire specifically for it ("inference engineer", "ML systems engineer", "performance engineer, LLM serving"), and the interview loops probe a recognisable body of knowledge: KV caches, attention kernels, batching, quantisation, parallelism, speculative decoding, GPU architecture, and back-of-the-envelope cost estimation.

For the mathematician

You already own most of the tools. The roofline model is a minimum of two linear functions. A KV cache is memoisation of a function whose arguments only ever grow. Speculative decoding is rejection sampling. Continuous batching is a scheduling problem with a queueing-theoretic objective. Ring all-reduce is a bandwidth-optimal algorithm whose optimality is a three-line counting argument. What you may lack is the vocabulary of systems engineering and a mental model of the machine. This book supplies both, in "software-engineering bridge" boxes like this one.

1.2 Language modelling as probability

Fix a finite vocabulary \(V\) of tokens (words, sub-words or bytes; Chapter 2 explains how they are chosen). A language model is a probability distribution over finite sequences \(x_{1:T} = (x_1,\dots,x_T) \in V^*\). Every such distribution can be factorised by the chain rule of probability—no assumptions needed:

\[ p(x_{1:T}) \;=\; \prod_{t=1}^{T} p(x_t \mid x_{<t}), \qquad x_{<t} := (x_1,\dots,x_{t-1}). \]

An autoregressive language model parameterises the conditionals \(p_\theta(x_t \mid x_{<t})\) directly. Two consequences shape everything that follows:

  • Training is parallel. Given a whole document, all \(T\) conditionals can be evaluated simultaneously (if the architecture allows it—the Transformer does, the RNN does not).
  • Generation is sequential. To sample, we must draw \(x_1\), then \(x_2 \sim p_\theta(\cdot\mid x_1)\), and so on. There is no way around the dependency chain without changing the model or the sampler (Chapter 18 shows one way to cheat it exactly).

Cross-entropy, bits and perplexity

Let \(p^{*}\) be the (unknown) true distribution of text. We fit \(\theta\) by minimising the per-token cross-entropy

\[ H(p^{*}, p_\theta) \;=\; -\,\mathbb{E}_{x \sim p^{*}}\Big[\tfrac{1}{T}\textstyle\sum_{t} \log p_\theta(x_t\mid x_{<t})\Big], \]

estimated on held-out text. By Gibbs' inequality \(H(p^{*},p_\theta) = H(p^{*}) + D_{\mathrm{KL}}(p^{*}\,\|\,p_\theta) \ge H(p^{*})\): the loss is bounded below by the entropy rate of language, the irreducible term that reappears as the constant \(E\) in the Chinchilla scaling law (§1.8).

Definition — perplexity

With \(H\) measured in nats per token, the perplexity is \(\mathrm{PP} = e^{H}\) (equivalently \(2^{H}\) with \(H\) in bits). It is the size of a uniform distribution with the same cross-entropy: a perplexity of 8 means the model is, on average, as uncertain as a fair 8-sided die.

Perplexity is tokeniser-dependent: a model with a larger vocabulary predicts fewer, "bigger" tokens per document, so per-token perplexities are not comparable across tokenisers. Normalise to bits per byte (or per character) to compare models fairly—exactly the unit Claude Shannon used in 1951, when he had human subjects guess the next letter of English text and estimated the entropy of printed English at roughly 0.6–1.3 bits per character[2]. Shannon's earlier 1948 paper had already introduced \(n\)-gram approximations to English as an illustration of a Markov source[1]; seventy years of language modelling have been an effort to push the cross-entropy towards his bound.

Worked example — converting units

A model reports a validation loss of 1.95 nats/token on English web text, with a tokeniser averaging 4.2 bytes per token. Its perplexity is \(e^{1.95}\approx 7.0\). In bits per byte: \(1.95/\ln 2 = 2.81\) bits/token, divided by 4.2 bytes/token \(=0.67\) bits/byte—inside Shannon's human range.

1.3 The count-based era (1948–2003)

The first practical language models made a Markov assumption of order \(n-1\):

\[ p(x_t\mid x_{<t}) \approx p(x_t \mid x_{t-n+1:t-1}), \qquad \hat p_{\text{MLE}}(w\mid h) = \frac{c(h,w)}{c(h)}, \]

with \(c(\cdot)\) counts in a corpus. From the 1970s to the 2000s, \(n\)-gram models powered speech recognition and statistical machine translation, notably at IBM under Fred Jelinek—whose group is often credited with the quip that recognition accuracy improved every time a linguist left the team.

The fatal flaw is sparsity. A model of order \(n\) has \(|V|^{n}\) possible contexts-plus-continuations; with \(|V|=50{,}000\) a trigram table has \(1.25\times10^{14}\) cells, almost all of which are never observed. The MLE assigns probability zero to any unseen \(n\)-gram, giving infinite perplexity. Decades of work went into smoothing: additive (Laplace), Good–Turing, Katz back-off, interpolation, and finally Kneser–Ney smoothing[3], which backs off to a "continuation" distribution—how many distinct contexts a word appears in, not how often it appears. Chen and Goodman's empirical study[4] established modified Kneser–Ney as the strongest count-based method.

Why an inference engineer should care about n-grams

They have not disappeared. Prompt-lookup and n-gram speculative decoding (Chapter 18) use exactly this idea—match the last few tokens against earlier text and propose the continuation—as a free draft model. And an \(n\)-gram is the purest example of a model with bounded context: its "state" is the last \(n-1\) tokens, a theme we will revisit with sliding-window attention.

1.4 The neural turn (2003–2013)

Bengio, Ducharme, Vincent and Jauvin[5] attacked sparsity with distributed representations. Each word \(w\) is mapped to a learned vector \(C(w)\in\mathbb{R}^{m}\); the \(n-1\) context vectors are concatenated and passed through a hidden layer and a softmax over the vocabulary:

\[ p(x_t = w \mid x_{t-n+1:t-1}) = \operatorname{softmax}\!\big(b + U\tanh(d + H[C(x_{t-1});\dots;C(x_{t-n+1})])\big)_w . \]

Similar words get similar vectors, so evidence about "the cat sat" transfers to "the dog sat"—generalisation by smoothness in embedding space rather than by count heuristics. Two details foreshadow modern inference:

  • The softmax over \(|V|\) was the computational bottleneck. Bengio et al. had to parallelise it across machines. Today the output projection ("LM head") of a model with a 128k–256k vocabulary is still one of the largest single matrices (Chapter 2).
  • The embedding table is a lookup, not a matrix multiply: memory-bound, cheap in FLOPs.

Mikolov's recurrent neural LM (2010)[6] and especially word2vec (2013)[7] made embeddings ubiquitous; the latter's famous linear regularities (\(\vec{\text{king}}-\vec{\text{man}}+\vec{\text{woman}}\approx\vec{\text{queen}}\)) convinced the field that geometry in representation space carries meaning.

1.5 The recurrent era (2010–2017): constant-size state

A recurrent neural network drops the fixed window. It maintains a hidden state \(h_t\in\mathbb{R}^d\) updated by

\[ h_t = \phi(W h_{t-1} + U e_{x_t} + b), \qquad p(x_{t+1}\mid x_{\le t}) = \operatorname{softmax}(O h_t). \]

In principle \(h_t\) summarises the whole prefix. In practice, training by back-propagation through time multiplies Jacobians:

\[ \frac{\partial h_t}{\partial h_{s}} = \prod_{k=s+1}^{t} \operatorname{diag}\big(\phi'(a_k)\big)\, W, \qquad \Big\|\frac{\partial h_t}{\partial h_{s}}\Big\| \le \big(\gamma\,\|W\|\big)^{t-s}, \]

where \(\gamma\) bounds \(|\phi'|\). Unless \(\gamma\|W\|\approx 1\) the gradient vanishes or explodes exponentially in the distance \(t-s\) — the vanishing-gradient problem identified by Hochreiter (1991) and Bengio, Simard and Frasconi (1994)[8]. The LSTM[9] fixed this with an additively-updated cell state \(c_t = f_t\odot c_{t-1} + i_t\odot \tilde c_t\), whose Jacobian along the cell path is the diagonal gate \(f_t\), close to the identity when the forget gate is open.

In 2014 Sutskever, Vinyals and Le[10] showed that an LSTM encoder could compress a source sentence into a vector and an LSTM decoder could generate a translation from it (seq2seq). The bottleneck was obvious: a whole sentence squeezed into one fixed vector. Bahdanau, Cho and Bengio[11] introduced attention: at each decoder step \(i\), compute weights over all encoder states,

\[ \alpha_{ij} = \frac{\exp(\mathrm{score}(s_{i-1}, h_j))}{\sum_{k}\exp(\mathrm{score}(s_{i-1}, h_k))}, \qquad c_i = \sum_j \alpha_{ij}\,h_j, \]

so the decoder "looks back" at the source as needed. Remember the shape of this: to attend, you must keep all the \(h_j\).

Key property — inference cost of an RNN

Generating one token costs \(O(d^2)\) FLOPs (a few matrix–vector products) and needs \(O(d)\) memory of state per sequence, independent of how long the sequence already is. An RNN is the ideal inference machine. Its curse is training: step \(t\) cannot start before step \(t-1\) finishes, so a length-\(T\) sequence needs \(T\) sequential steps, which leaves GPUs idle.

1.6 The Transformer (2017): parallel training, growing state

"Attention Is All You Need"[12] removed recurrence entirely. Every position computes a query \(q_t\), key \(k_t\) and value \(v_t\) by linear maps, and attends to all permitted positions:

\[ \operatorname{Attn}(Q,K,V) = \operatorname{softmax}\!\Big(\frac{QK^\top}{\sqrt{d_k}} + M\Big)V , \]

with \(M\) a causal mask (\(-\infty\) above the diagonal) for language modelling. Because the whole \(T\times T\) score matrix is a single matrix product, training on a length-\(T\) document is one big parallel computation instead of \(T\) dependent steps—perfectly suited to GPUs. The original big model trained in 3.5 days on 8 NVIDIA P100 GPUs and set a new state of the art in English–German translation.

But look at what generation now requires. To produce token \(t+1\), the new query must be dotted with the keys of all \(t\) previous tokens, in every layer. Recomputing those keys and values every step would make generation quadratic. Instead, we cache them. This is the KV cache, the single most important data structure in this book.

1.7 Pre-training and scale (2018–2020)

The Transformer's parallelism made it practical to train on far more text. Three ideas compounded:

  • Generative pre-training. GPT-1 (OpenAI, 2018; 117M parameters)[13] pre-trained a decoder-only Transformer on books and fine-tuned it for downstream tasks. BERT (Google, 2018; up to 340M)[14] used a bidirectional encoder with masked-token prediction and dominated benchmarks—but an encoder cannot generate text autoregressively, so the decoder-only line is the one that leads to today's LLMs.
  • Zero-shot behaviour. GPT-2 (2019; 1.5B)[15] showed that a sufficiently large LM performs tasks it was never fine-tuned for, simply by being prompted.
  • In-context learning. GPT-3 (2020; 175B parameters, ~300B training tokens)[16] showed that few-shot examples in the prompt substitute for fine-tuning. Prompts got long; long prompts mean large prefill costs and large KV caches.

1.8 Scaling laws, and why inference changed them

Kaplan et al. (2020)[17] found that test loss falls as a power law in parameters \(N\), data \(D\) and compute \(C\), e.g. \(L(N)\approx (N_c/N)^{\alpha_N}\) with \(\alpha_N\approx0.076\), over many orders of magnitude. Their compute-optimal recipe favoured making models much bigger rather than training longer. Hoffmann et al. (2022, "Chinchilla")[18] revisited the question with better-tuned learning-rate schedules and fitted

\[ L(N,D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}}, \qquad E\approx1.69,\;A\approx406.4,\;B\approx410.7,\;\alpha\approx0.34,\;\beta\approx0.28 . \]

Minimising \(L\) subject to the training-compute constraint \(C\approx 6ND\) (we derive the 6 in Chapter 2) gives \(N_{\text{opt}}\propto C^{a}\), \(D_{\text{opt}}\propto C^{b}\) with \(a\approx b\approx 0.5\): scale parameters and tokens together, at roughly 20 tokens per parameter. Chinchilla (70B parameters, 1.4T tokens) beat the 4× larger Gopher (280B, 300B tokens) trained with the same compute.

Derivation sketch — the compute-optimal split

Substitute \(D = C/(6N)\): \(L(N) = E + A N^{-\alpha} + B (6N/C)^{\beta}\). Setting \(dL/dN=0\) gives \(\alpha A N^{-\alpha-1} = \beta B\,6^{\beta} N^{\beta-1} C^{-\beta}\), hence \[ N_{\text{opt}} = G\Big(\frac{C}{6}\Big)^{\frac{\beta}{\alpha+\beta}},\quad D_{\text{opt}} = G^{-1}\Big(\frac{C}{6}\Big)^{\frac{\alpha}{\alpha+\beta}},\quad G=\Big(\frac{\alpha A}{\beta B}\Big)^{\frac{1}{\alpha+\beta}} . \] With \(\alpha\approx\beta\) both exponents are \(\approx\tfrac12\).

Inference-aware scaling

Chinchilla optimises training compute only. But a model that will serve \(D_{\text{inf}}\) tokens over its life costs roughly

\[ C_{\text{lifetime}} \;\approx\; \underbrace{6\,N\,D_{\text{train}}}_{\text{training}} \;+\; \underbrace{2\,N\,D_{\text{inf}}}_{\text{inference}} \]

(forward pass ≈ \(2N\) FLOPs/token, forward+backward ≈ \(6N\); attention terms ignored—see Chapter 2).

If \(D_{\text{inf}}\) is large, it pays to shrink \(N\) and compensate with more training tokens: you reach the same loss with a smaller model that is cheaper on every future request. Sardana and Frankle (2023)[19] formalised this "beyond Chinchilla-optimal" regime. Practice had already moved: LLaMA-7B (2023) saw 1T tokens (~140 tokens/parameter); Llama 3 8B (2024) saw over 15T tokens[20]—nearly 1,900 tokens per parameter, ~90× past Chinchilla-optimal.

Drill 1.1 — When does serving cost more than training?

Llama 3 8B: \(N=8\times10^{9}\), \(D_{\text{train}}=15\times10^{12}\). Training compute \(\approx 6ND = 7.2\times10^{23}\) FLOPs. Inference compute equals training compute when \(2ND_{\text{inf}} = 6ND_{\text{train}}\), i.e. \(D_{\text{inf}} = 3D_{\text{train}} = 45\)T tokens. A popular open model served by many providers can plausibly process this many tokens within months. (In wall-clock and dollars the crossover comes even sooner, because inference—especially decode—runs at much lower hardware utilisation than training; Chapter 5.)

1.9 The ChatGPT moment and the economics of inference

InstructGPT (2022)[21] showed that supervised fine-tuning plus reinforcement learning from human feedback (RLHF) turns a pre-trained LM into an assistant that follows instructions. ChatGPT, released on 30 November 2022, packaged this as a chat product and reportedly reached 100 million users in about two months. Overnight, the bottleneck of the AI industry became serving: how many conversations per second can a GPU sustain, at what latency, at what cost?

Three economic facts define the field since then:

  1. Price per token falls fast. The price of a given capability level has fallen by roughly an order of magnitude per year (a16z's "LLMflation" analysis[22]). Much of that decline is inference engineering: better kernels, batching, quantisation, MoE, speculative decoding, newer hardware.
  2. Output tokens cost more than input tokens. API prices for output tokens are typically 3–5× input prices. You will be able to explain why after Chapter 2: input tokens are processed in a parallel, compute-efficient prefill; output tokens are produced one at a time in a memory-bandwidth-bound decode.
  3. Cached input is cheaper still. Providers discount repeated prompt prefixes ("prompt caching"), because the KV cache for a shared prefix can be stored and reused (Chapter 9).

1.11 The reasoning era (2024–)

Chain-of-thought prompting (Wei et al., 2022)[23] showed that letting a model "think out loud" improves multi-step reasoning. OpenAI's o1 (September 2024) and DeepSeek-R1 (January 2025)[24] trained models with reinforcement learning to produce long internal reasoning traces—often thousands to tens of thousands of tokens—before answering. Snell et al. (2024)[25] showed that, for some problems, spending more compute at test time can be more effective than scaling parameters.

For inference engineering this is a regime change:

  • Decode dominates. A chat turn with a 2,000-token prompt and a 300-token answer is prefill-heavy in tokens; a reasoning turn with a 20,000-token trace is overwhelmingly decode.
  • The KV cache explodes. Long outputs grow the cache throughout generation, limiting how many requests fit on a GPU. KV compression methods designed for long inputs often fail for long outputs.
  • Latency is product quality. A model that thinks 3× faster can think 3× longer under the same latency budget—so tokens/s translates directly into answer accuracy.
  • RL training is an inference workload. Generating rollouts dominates the cost of RL post-training, so training clusters now embed inference engines.

1.12 Hardware co-evolution and the memory wall

LLMs and GPUs co-evolved. NVIDIA added tensor cores—units that perform small dense matrix multiply-accumulates—in Volta (V100, 2017), BF16 and TF32 in Ampere (A100, 2020), FP8 and the Transformer Engine in Hopper (H100, 2022), and FP4 in Blackwell (B200, 2024–25). Google built TPUs around systolic arrays from 2015 onwards[26]. Each generation multiplied arithmetic throughput much faster than memory bandwidth.

1.13 The metrics vocabulary

Before we optimise anything we must define what "fast" and "cheap" mean. A request arrives with \(n_{\text{in}}\) prompt tokens and produces \(n_{\text{out}}\) output tokens, which are typically streamed to the user as they are generated.

Two structural facts recur throughout the book:

  1. Latency and throughput trade off. Batching more requests together raises throughput (better hardware utilisation) but raises each request's TPOT (each step does more work) and may raise TTFT (queueing). The art is choosing the operating point on this Pareto frontier that satisfies the SLO at minimum cost.
  2. Percentiles matter more than means. Users experience the tail. A system with mean TTFT 200 ms and P99 4 s feels broken. Interviewers will ask you which percentile an SLO refers to.
Software-engineering bridge — Little's law

For any stable queueing system in steady state, \(L=\lambda W\): mean number of requests in the system = arrival rate × mean time in system. If a deployment receives \(\lambda=20\) requests/s and each takes \(W=8\) s end to end, then on average \(L=160\) requests are in flight—so your engine must hold 160 concurrent KV caches. This one identity converts latency targets into memory requirements.

Drill 1.2 — Cost per million tokens

An 8×H100 node rents for $2.50 per GPU-hour and sustains 12,000 output tokens/s aggregated across all requests at your SLO. Cost per million output tokens \(= \frac{8\times 2.50}{12{,}000\times3600}\times10^{6} = \frac{20}{4.32\times10^{7}}\times10^{6}\approx \$0.46\). Doubling throughput by better batching halves this number—which is why throughput engineering is worth millions.

1.14 Your first back-of-the-envelope: the bandwidth bound

Consider generating with batch size 1 (a single user). Each decode step must apply every weight matrix to one new token vector. Matrix–vector products perform \(2\) FLOPs (one multiply, one add) for each weight, and each weight must be read from HBM once. So per step:

\[ \text{FLOPs} \approx 2N, \qquad \text{bytes read} \approx N\cdot b, \qquad \text{arithmetic intensity} \approx \frac{2N}{Nb} = \frac{2}{b}\ \text{FLOPs/byte}, \]

where \(b\) is bytes per parameter (2 for BF16). That is about 1 FLOP/byte—two orders of magnitude below any modern GPU's ridge point. The step time is therefore governed by memory, not arithmetic:

\[ t_{\text{step}} \;\gtrsim\; \frac{N\,b + \text{(KV-cache bytes)}}{\text{HBM bandwidth}}, \qquad \text{tokens/s per sequence} \;\lesssim\; \frac{\text{bandwidth}}{N b}. \]
Worked example — Llama-class 70B at batch 1

Weights in BF16: \(70\times10^9\times 2 = 140\) GB.

  • One H100 (80 GB, 3.35 TB/s): does not fit in BF16. In FP8 (70 GB) it barely fits with almost no room for KV cache: \(t \ge 70/3350\,\text{s}\approx 21\) ms → at most ≈ 48 tokens/s.
  • One H200 (141 GB, 4.8 TB/s): BF16 fits: \(t\ge 140/4800\approx 29\) ms → at most ≈ 34 tokens/s.
  • Two H100s with tensor parallelism: each GPU holds and reads half the weights, so aggregate bandwidth is 6.7 TB/s: \(t\gtrsim 21\) ms → ≈ 48 tokens/s, minus communication overhead (Chapter 16).
  • One B200 (8 TB/s): \(t\ge 140/8000\approx 17.5\) ms → at most ≈ 57 tokens/s in BF16; ≈ 114 tokens/s in FP8.

Real systems reach perhaps 60–85% of these bounds ("memory bandwidth utilisation", MBU). Meanwhile, compute utilisation is below 1%: an H100 could do \(989\times10^{12}\times 0.021\approx 2\times10^{13}\) FLOPs in those 21 ms but we used only \(1.4\times10^{11}\).

The obvious fix is to batch: if 64 users share each weight read, we do 64× more useful FLOPs per byte. Batching is free up to the point where the GPU becomes compute-bound—or runs out of memory for 64 KV caches. That tension, between amortising weight reads and holding per-request state, is the plot of Chapters 2, 5, 7, 9 and 10.

What interviewers listen for

When asked "how fast can model X run on GPU Y?", strong candidates (1) state the regime (memory-bound at small batch), (2) compute the weight bytes and divide by bandwidth, (3) add the KV-cache bytes for long contexts, (4) mention a realistic efficiency factor, and (5) say what changes at large batch (compute-bound) or with quantisation, tensor parallelism or speculative decoding. Weak candidates divide FLOPs by peak FLOP/s and get an answer 100× too optimistic.

1.15 A map of the book

Chapter summary

  • Language modelling is estimating \(p(x_t\mid x_{<t})\); loss is cross-entropy, bounded below by the entropy of language; perplexity \(=e^{H}\); compare across tokenisers in bits per byte.
  • Each era solved its predecessor's bottleneck: n-gram sparsity → embeddings; fixed windows → recurrence; vanishing gradients → LSTM; fixed-vector bottleneck → attention; sequential training → the Transformer.
  • The Transformer bought parallel training by keeping an explicit record of the past: the KV cache, which grows with context length. RNNs have constant-size state.
  • Chinchilla: ~20 tokens/parameter is compute-optimal for training. Counting lifetime inference (\(2ND_{\text{inf}}\)), smaller, over-trained models win; hence 1,000+ tokens/parameter today.
  • The cost centre moved to inference after ChatGPT (2022) and accelerated with reasoning models (2024–).
  • Hardware FLOP/s outgrew memory bandwidth (the memory wall); decode at batch 1 runs at ~1 FLOP/byte versus ridge points of ~150–300.
  • Metrics: TTFT, TPOT/ITL, E2E, throughput, goodput, cost/M tokens; tails matter; Little's law links load to concurrency.
  • Decode speed at small batch ≤ bandwidth / (weight bytes + KV bytes).

The chain-rule factorisation \(p(x_{1:T})=\prod_t p(x_t\mid x_{<t})\) used by autoregressive LMs is:

  1. An approximation that becomes exact only for Markov sources
  2. An identity that holds for any joint distribution over sequences
  3. Valid only if tokens are conditionally independent given the past
  4. Valid only for left-to-right languages
The chain rule of probability is an identity. The approximation in an n-gram model is truncating the conditioning set; in a neural model, it is the finite capacity of the parameterisation. The direction (left-to-right) is a modelling choice, not a validity condition.

  2. B is better because larger vocabularies are always better
  3. Nothing yet: per-token perplexities with different tokenisers are not comparable; convert to bits per byte

Why can a language model's cross-entropy on real text never go below the entropy rate of the text distribution?

  1. Because of the vanishing-gradient problem
  2. Because \(H(p^{*},p_\theta)=H(p^{*})+D_{\mathrm{KL}}(p^{*}\|p_\theta)\) and KL divergence is non-negative
  3. Because softmax outputs are bounded away from 1
  4. Because of finite vocabulary size
Gibbs' inequality. The irreducible term reappears as the constant \(E\) in the Chinchilla law \(L=E+A/N^\alpha+B/D^\beta\).

The main reason classical n-gram models could not simply increase \(n\) to capture long-range context was:

  1. Counting is computationally expensive
  2. The number of possible contexts grows as \(|V|^{n-1}\), so almost all are unseen in any corpus (data sparsity)
  3. Vanishing gradients
  4. They cannot be smoothed for \(n>3\)
Sparsity is exponential in \(n\). Smoothing (Kneser–Ney etc.) mitigates but cannot overcome it; neural embeddings attack it by sharing statistical strength between similar contexts.

Kneser–Ney smoothing's key idea for the lower-order (back-off) distribution is to use:

  1. Raw unigram frequency
  2. The number of distinct contexts a word follows ("continuation count")
  3. A uniform distribution over the vocabulary
  4. A learned neural embedding
"Francisco" is frequent but almost always follows "San"; its continuation count is low, so it gets little back-off mass in novel contexts.

In Bengio et al.'s 2003 neural probabilistic LM, which component was the dominant computational cost?

  1. The embedding lookup
  2. The tanh hidden layer
  3. The softmax over the full vocabulary
  4. Back-propagation through time
The output layer scales with \(|V|\times h\). Today's LM heads (e.g. \(128{,}256\times4096\) in Llama 3 8B, ~0.5B parameters) remain among the largest single matrices.

For a vanilla RNN \(h_t=\tanh(Wh_{t-1}+Ux_t)\), the gradient \(\partial h_t/\partial h_s\) is bounded in norm by \((\gamma\|W\|)^{t-s}\). This implies:

  1. Gradients always explode
  2. Gradients vanish exponentially in \(t-s\) whenever \(\gamma\|W\|<1\)
  3. Gradients are independent of sequence length
  4. The bound is only valid for linear activations
Product of Jacobians; with \(|\tanh'|\le1\), if \(\|W\|<1\) the bound decays geometrically. (Explosion is possible—not guaranteed—when the spectral radius exceeds 1.)

Why does the LSTM mitigate vanishing gradients?

  1. It uses ReLU activations
  2. Its cell state is updated additively, \(c_t=f_t\odot c_{t-1}+i_t\odot\tilde c_t\), so the Jacobian along the cell path is the diagonal forget gate, which can stay near 1
  3. It has fewer parameters
  4. It processes the sequence in parallel
The "constant error carousel": gradient flows through \(\prod f_t\) rather than through repeated multiplication by a full matrix and squashing derivative.

Per generated token at context length \(t\), which statement best compares the inference state of an RNN and a Transformer?

  1. Both need \(O(t)\) memory
  2. RNN: \(O(d)\) memory, constant in \(t\). Transformer: \(O(L\,d\,t)\) memory for the KV cache
  3. RNN: \(O(t^2)\). Transformer: \(O(d)\)
  4. Both are constant in \(t\)
This is the central trade-off of Figure 1.1, and it motivates MQA/GQA/MLA, sliding windows, PagedAttention, KV quantisation and the renewed interest in state-space models.

The decisive advantage of the Transformer over RNNs for training was:

  1. Fewer FLOPs per token
  2. All positions of a training sequence can be processed in parallel (no sequential dependency across time steps)
  3. Smaller memory footprint for long sequences
  4. No need for positional information
Causal masking lets all \(T\) next-token losses be computed in one pass. Attention is actually \(O(T^2)\) in sequence length and does need positional encodings.

Bahdanau-style attention (2014) was originally introduced to solve which problem?

  1. Slow training of language models
  2. The fixed-length vector bottleneck between encoder and decoder in seq2seq translation
  3. Out-of-vocabulary words
  4. GPU memory limits
Instead of compressing the whole source into one vector, the decoder computes a fresh weighted average of all encoder states at each step.

Why did the decoder-only (GPT) lineage, rather than encoder-only BERT, become the basis for chat LLMs?

  1. BERT was smaller
  2. A causal decoder defines a generative distribution that can be sampled token by token; a bidirectional masked-LM encoder does not directly generate text left to right
  3. BERT could not be fine-tuned
  4. Decoders do not need attention
Masked LMs see both sides of a blank; they are excellent encoders but do not define \(p(x_t\mid x_{<t})\).

Under the Chinchilla analysis, if you are given 4× more training compute, you should scale model size and data by roughly:

  1. 4× parameters, same data
  2. Same parameters, 4× data
  3. 2× parameters and 2× data
  4. 16× parameters, ¼ data
\(N_{\text{opt}}\propto C^{0.5}\), \(D_{\text{opt}}\propto C^{0.5}\), and \(C\approx6ND\): \(2\times2=4\).

Training compute for a dense Transformer is commonly approximated as \(C\approx 6ND\). The factor 6 comes from:

  1. Six layers in the original Transformer
  2. ≈2 FLOPs per parameter per token for the forward pass plus ≈4 for the backward pass
  3. Six bytes per parameter in mixed precision
  4. The Adam optimiser's six state tensors
Forward: one multiply-add per weight per token (2 FLOPs). Backward: gradients w.r.t. activations and w.r.t. weights, each about the same as the forward (4 FLOPs). Derived carefully in Chapter 2.

Llama 3 8B was trained on ~15T tokens, far beyond the Chinchilla-optimal ~160B. The best justification is:

  1. Chinchilla's law was proven wrong
  2. Lifetime cost includes inference \(\approx2ND_{\text{inf}}\); a smaller model trained longer reaches a target quality with lower per-request cost
  3. Larger datasets reduce the KV cache
  4. Over-training reduces training time
Chinchilla minimises training FLOPs only. When a model will be served heavily, extra training tokens are a one-off cost that buys a permanently cheaper model.

Why do LLM APIs usually charge more for output tokens than for input tokens?

  1. Output tokens are longer strings
  2. Input tokens are processed in one parallel, compute-efficient prefill pass; output tokens are generated one per step in a memory-bandwidth-bound decode, so each costs more GPU time
  3. Output tokens require a different model
  4. Input tokens are cached for free
Prefill amortises each weight read over thousands of tokens; decode amortises it only over the batch. Cached-prefix discounts are a separate, further reduction for repeated input.

Throughput can be inflated by batching that violates latency targets; goodput counts only requests that satisfy the SLOs.

The "memory wall" refers to:

  1. The maximum HBM capacity of a GPU
  2. Peak arithmetic throughput growing much faster than memory (and interconnect) bandwidth across hardware generations

Warm-up What is perplexity, and why is it a poor metric for comparing two LLMs with different tokenisers?

Perplexity is the exponentiated per-token cross-entropy on held-out data, \(\mathrm{PP}=\exp\big(-\tfrac1T\sum_t\log p(x_t\mid x_{<t})\big)\): the effective branching factor of the model's predictions. It depends on what a "token" is. A tokeniser with a larger vocabulary produces fewer, more informative tokens, so per-token loss rises even if the model assigns higher probability to the whole text. To compare, normalise the total negative log-likelihood by bytes or characters (bits per byte), or compare on downstream tasks. A strong answer also mentions that perplexity on a held-out corpus is only loosely related to usefulness after instruction tuning, and is sensitive to data contamination.

Warm-up Define TTFT, TPOT and throughput. Give one product where each is the primary concern.
  • TTFT — time from request arrival to the first output token (queueing + prefill). Primary for chat responsiveness and voice assistants, where silence is noticed after a few hundred milliseconds.
  • TPOT — mean time between subsequent output tokens. Primary for long streamed outputs, reasoning models, and agents whose total latency is dominated by generation.
  • Throughput — tokens (or requests) per second for the whole deployment. Primary for offline batch jobs (summarising a document corpus, synthetic data generation, evaluation, RL rollouts), where latency does not matter but cost does.

Mention the trade-off: larger batches raise throughput but hurt TPOT, and queueing hurts TTFT; real systems optimise goodput under P90/P99 SLOs.

Core Why is LLM decoding memory-bandwidth bound? Give the back-of-the-envelope argument.

Each decode step processes one new token per sequence. For every weight matrix \(W\in\mathbb{R}^{m\times n}\) we compute \(Wx\) for a batch of \(B\) vectors: \(2mnB\) FLOPs, but we must read all \(mn\) weights (\(2mn\) bytes in BF16). Arithmetic intensity ≈ \(B\) FLOPs/byte. An H100 delivers ~989 TFLOP/s against 3.35 TB/s, a ridge point of ~295 FLOPs/byte, so for \(B\ll 300\) the arithmetic units wait on memory. Step time ≈ (weight bytes + KV-cache bytes) / bandwidth. In addition, attention over the KV cache has intensity ~1 FLOP/byte per sequence regardless of batch (each sequence has its own cache)—so even large batches remain partially memory-bound in attention. Consequences: quantisation, larger batches, GQA/MLA, and speculative decoding all help; adding FLOPs does not.

Core Estimate the maximum single-stream tokens/s of a 70B dense model in BF16 on 2×H100 with tensor parallelism.

Weights: 140 GB, split across two GPUs (70 GB each). Each GPU reads its 70 GB per step at 3.35 TB/s → ≈ 21 ms per step if both work in parallel. Add KV-cache reads: Llama-2-70B with GQA stores \(2\times80\times8\times128\times2\) B = 320 KB per token, so a 4k-token context adds ≈ 1.3 GB (0.65 GB per GPU) — small. Add two all-reduces per layer (160 total) of a few KB each; with NVLink each costs ~10–20 µs of latency, ≈ 2–3 ms total. Estimate ≈ 23–25 ms per token → ~40–45 tokens/s upper bound; at realistic MBU (~70–80%) roughly 30–35 tokens/s. Then discuss: FP8 roughly doubles it, speculative decoding can give 2–3× more, larger batches raise throughput but not single-stream speed.

Core Contrast RNNs and Transformers from an inference-systems perspective.

RNN: constant-size state \(h_t\in\mathbb{R}^d\) per sequence, \(O(d^2)\) FLOPs per token, independent of history length; trivially batchable; memory per user is tiny. But training is sequential over time and long-range recall is lossy (everything must be compressed into \(h\)).

Transformer: parallel training across positions; exact access to any past token. At inference it must store keys and values for every past token in every layer: \(2\,L\,n_{kv}\,d_h\) values per token, growing linearly with context; attention FLOPs per token also grow linearly. This state limits concurrency (batch size), dominates memory at long context, and is the target of MQA/GQA/MLA, paging, prefix caching, quantisation, eviction and offloading. Modern hybrids (Mamba-style SSM layers interleaved with some attention layers) try to get the best of both.

Core Explain the Chinchilla scaling result and why most production models deliberately violate it.

Hoffmann et al. fitted \(L(N,D)=E+A N^{-\alpha}+B D^{-\beta}\) and minimised it under \(C=6ND\), finding \(N_{\text{opt}},D_{\text{opt}}\propto C^{\approx0.5}\), about 20 tokens per parameter; Chinchilla-70B trained on 1.4T tokens beat Gopher-280B at equal compute. But this minimises training FLOPs only. Total cost is \(6ND_{\text{train}}+2ND_{\text{inf}}\) (plus memory and latency costs that also scale with \(N\)). For heavily-served models, a smaller \(N\) trained on many more tokens achieves the same loss with much cheaper inference, lower latency, and the ability to run on fewer or smaller GPUs. Hence LLaMA-7B (1T tokens), Llama 3 8B (15T tokens, ~1,900 tokens/param), and the general "over-training" trend; Sardana & Frankle formalised the inference-aware optimum. Caveat: returns diminish, and data quality/availability becomes the constraint.

Core What is the difference between throughput and goodput, and why might optimising throughput hurt users?

Throughput counts all tokens or requests completed per second. Goodput counts only requests that meet the SLOs (e.g. P90 TTFT ≤ 1 s and P90 TPOT ≤ 50 ms). Maximising throughput pushes toward huge batches and long queues: GPU utilisation goes up, but each step slows (higher TPOT) and new requests wait for capacity (higher TTFT). Beyond some load, throughput still rises while goodput collapses because most requests miss their SLOs. Capacity planning should therefore pick the maximum load at which goodput is still near the arrival rate, and use scheduling (chunked prefill, priorities, disaggregation) to push that point up.

Core Why are output tokens typically priced 3–5× higher than input tokens, and why are cached input tokens cheaper still?

Input tokens are processed in prefill, a single forward pass over all prompt tokens. Each weight read is amortised across thousands of tokens, so prefill is compute-bound and runs near peak FLOP/s. Output tokens are produced one decode step at a time; each step re-reads all weights and the KV cache and is amortised only over the current batch, so GPU-seconds per token are much higher, and long outputs also occupy KV memory for longer, reducing concurrency. Cached input: if a prefix (system prompt, document, conversation history) was recently processed, its KV cache can be reused from GPU/CPU memory or storage, skipping its prefill compute entirely; the provider passes on part of the saving and encourages cache-friendly prompts.

Deep-dive Derive the compute-optimal \(N\) and \(D\) from the Chinchilla loss \(L=E+AN^{-\alpha}+BD^{-\beta}\) under \(C=6ND\).

Substitute \(D=C/(6N)\): \(f(N)=AN^{-\alpha}+B(6N/C)^{\beta}\). Then \(f'(N)=-\alpha AN^{-\alpha-1}+\beta B(6/C)^{\beta}N^{\beta-1}=0\), so \(N^{\alpha+\beta}=\frac{\alpha A}{\beta B}\left(\frac{C}{6}\right)^{\beta}\), giving \(N_{\text{opt}}=G\,(C/6)^{\beta/(\alpha+\beta)}\) with \(G=(\alpha A/\beta B)^{1/(\alpha+\beta)}\), and \(D_{\text{opt}}=C/(6N_{\text{opt}})=G^{-1}(C/6)^{\alpha/(\alpha+\beta)}\). Since \(f\) is a sum of a decreasing and an increasing power of \(N\), it is unimodal—so this is the minimum. With \(\alpha=0.34,\beta=0.28\), the exponents are 0.45 and 0.55; Hoffmann et al.'s other estimation approaches give ≈0.5 each. Extension for inference-awareness: add \(2ND_{\text{inf}}\) to the cost and minimise total cost subject to \(L(N,D)=L^{*}\); the optimum moves to smaller \(N\), larger \(D\).

Deep-dive Why do the ridge points of successive GPUs keep rising, and what does that imply for LLM inference algorithm design?

FLOP/s scale with transistor count and specialised units (tensor cores, lower precisions: FP16→FP8→FP4 roughly doubles throughput each time), while bandwidth is limited by the number of pins and stacks, signalling rates and packaging (HBM generations). So peak FLOP/s per byte of bandwidth trends upward (P100 ≈ 29, H100 ≈ 295 in BF16; much higher in FP8/FP4). Implications: (1) algorithms must raise arithmetic intensity—bigger batches, fusion, FlashAttention-style tiling, GQA/MLA (more queries per KV byte), speculative decoding (verify several tokens per weight read); (2) reduce bytes—quantisation of weights and KV; (3) exploit memory hierarchy (SRAM reuse); (4) accept that some phases (decode attention) will be bandwidth-bound and design hardware/scheduling around it, e.g. disaggregating prefill (compute-bound) and decode (bandwidth-bound) onto differently provisioned pools.

Deep-dive How did reasoning models change inference engineering priorities?

(1) Token mix flips from prefill-heavy to decode-heavy; decode is bandwidth-bound, so TPOT and decode throughput dominate cost. (2) KV cache grows during generation to tens of thousands of tokens per request, limiting batch size and making KV compression/offload important—but many eviction methods were designed for long inputs and degrade reasoning accuracy on long outputs. (3) Latency translates into capability: under a fixed time budget, faster decode allows longer thinking; providers expose "reasoning effort" knobs. (4) Speculative decoding becomes more valuable (long sequential generations). (5) Variance in output length grows, complicating scheduling (stragglers, preemption). (6) RL post-training uses massive rollout generation, so inference engines are embedded in training stacks, with weight-sync between trainer and inference engine as a new problem.

Deep-dive Little's law and capacity: you must serve 30 req/s with mean 1,500 input and 500 output tokens, at P50 TPOT ≈ 40 ms. Roughly how many concurrent sequences must the system hold, and what does that imply for KV memory for an 8B GQA model?

Time in system per request ≈ TTFT (say 0.5 s) + 500×0.04 s = 20.5 s. Little: \(L=\lambda W=30\times20.5\approx 615\) concurrent requests. KV cache per token for a Llama-3-8B-like model (32 layers, 8 KV heads, head dim 128, BF16) = \(2\times32\times8\times128\times2=131{,}072\) B = 128 KiB. Average live context ≈ 1,500 + 250 (half the output on average) = 1,750 tokens → ≈ 224 MiB per request → ≈ 134 GiB for 615 requests, plus 16 GB of weights. So you need at least two 80 GB GPUs worth of memory (more in practice for headroom and fragmentation), or FP8 KV cache, or more replicas. Then check compute: 30 req/s × 2,000 tokens × 2×8e9 FLOPs ≈ 1 PFLOP/s, so ~2–4 H100s at realistic utilisation. Conclusion: a handful of GPUs, likely 2–4 replicas; memory, not FLOPs, sets the replica count.

Core Name five inference optimisations from 2019–2025 and the specific bottleneck each attacks.
  • MQA/GQA (2019/2023) — KV cache size and bandwidth: share K/V across query heads.
  • FlashAttention (2022–26) — HBM traffic of materialising the \(T\times T\) score matrix: tile in SRAM with online softmax.
  • Continuous batching (Orca, 2022) — idle slots when batched requests finish at different times: schedule per iteration.
  • PagedAttention (vLLM, 2023) — KV memory fragmentation/over-reservation: fixed-size blocks with a block table.
  • Speculative decoding (2022–25) — sequential, low-intensity decode: draft many tokens cheaply and verify them in one pass, exactly preserving the distribution.
  • Quantisation (GPTQ/AWQ/FP8/FP4) — weight bytes and bandwidth (and compute for activation quantisation).
  • Chunked prefill / disaggregation (2024) — long prefills stalling decodes; prefill and decode needing different resources.
  • MoE (2017–25) — FLOPs per token: activate a small subset of parameters per token.
Design A product manager asks: "We want answers twice as fast. Should we buy GPUs with twice the TFLOPs?" How do you respond?

First clarify "fast": TTFT (responsiveness) or TPOT (streaming speed) or E2E? Get the current breakdown from traces. If generation (TPOT) dominates, as it usually does for long answers, the workload is memory-bandwidth bound at the batch sizes needed for latency; doubling TFLOPs with the same bandwidth would barely help. Options ranked by cost: (1) speculative decoding (EAGLE-style, 2–3× lower TPOT at small batch); (2) FP8/INT4 weight quantisation (fewer bytes per step; validate quality); (3) reduce batch size or use priority scheduling for latency-sensitive tiers; (4) more tensor parallelism (aggregate bandwidth, at some communication cost); (5) hardware with more HBM bandwidth (H200/B200-class). If TTFT dominates: prefix caching, chunked prefill, disaggregated prefill, more prefill capacity (here FLOPs do matter). Finish with a measurement plan and an estimate of cost per million tokens for each option.

Design Sketch, at a high level, what happens between a user pressing Enter in a chat app and seeing tokens stream back.
  1. Client sends HTTPS request (messages, parameters) to an API gateway: authentication, rate limiting, routing to a model deployment—ideally to a replica that already holds the conversation's KV cache (prefix-aware routing).
  2. Server applies the chat template and tokenises; checks the prefix cache for reusable KV blocks.
  3. Scheduler admits the request when KV memory is available; runs prefill for the uncached part of the prompt (possibly chunked and interleaved with others' decode steps, or on a separate prefill pool with KV transferred to a decode pool).
  4. The first token is sampled from the logits (temperature/top-p, possibly grammar-constrained); TTFT is measured here.
  5. The request joins the continuous decode batch; each iteration runs one forward pass for all running sequences, appends K/V to paged cache blocks, samples next tokens.
  6. Tokens are incrementally detokenised and streamed (server-sent events); stop conditions (EOS, stop strings, max tokens) end the request; KV blocks are freed or retained in the prefix cache.
  7. Metrics/traces recorded; billing counts input, cached-input and output tokens.

Each step maps to later chapters: routing (22), prefix caching (9), scheduling (10), disaggregation (12), sampling (3), kernels (6, 8).

Warm-up What is the KV cache and why does it exist?

During autoregressive generation, each new token's query must attend to the keys and values of every previous token in every layer. Those keys and values depend only on earlier tokens (causal masking), so they never change once computed. The KV cache stores them so each decode step computes K and V only for the new token and reads the rest from memory—turning per-step cost from re-processing the whole prefix into a single-token forward pass plus attention over cached vectors. Its size is \(2\cdot L\cdot n_{kv}\cdot d_h\cdot\text{bytes}\) per token per sequence (Chapter 2), which can exceed the model weights at long contexts or high concurrency, making it the central resource that serving systems manage.
