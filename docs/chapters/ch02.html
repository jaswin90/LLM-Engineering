2.2 Tokenisation

A model consumes integers. The tokeniser maps text to a sequence of ids in \(\{0,\dots,|V|-1\}\) and back. Three families dominate:

  • Byte-Pair Encoding (BPE)[3]. Start from characters (or bytes). Repeatedly find the most frequent adjacent pair in the training corpus and merge it into a new symbol, until the vocabulary reaches the target size. Encoding applies the learned merges greedily in order. GPT-2 introduced byte-level BPE: the base alphabet is the 256 byte values, so any string—any language, emoji, binary junk—is encodable with no "unknown" token.
  • Unigram LM[4]. Start with a large candidate vocabulary and prune it, keeping the subset that maximises corpus likelihood under a unigram model; encoding finds the most probable segmentation by Viterbi.
  • SentencePiece[5] is a library implementing both, treating whitespace as a normal symbol (▁), used by Llama 1/2, Gemma and T5. Llama 3 switched to a tiktoken-style byte-level BPE with 128k tokens.

The vocabulary trade-off, seen by an inference engineer

  • Bigger vocabulary → fewer tokens per text. Llama 3's tokeniser encodes English with roughly 15% fewer tokens than Llama 2's. Fewer tokens means fewer decode steps, a smaller KV cache and less attention compute—for the same text.
  • Bigger vocabulary → bigger embedding and LM head. The LM head costs \(2d|V|\) FLOPs per token: for Llama 3 8B that is \(2\times4096\times128{,}256\approx1.05\) GFLOPs, about 6.5% of the whole forward pass. In Llama 3.2 1B (\(d=2048\)) the embedding is ~20% of all parameters.
  • Bigger vocabulary → bigger softmax and sampling cost. Top-\(k\)/top-\(p\) sampling over 150k–260k logits per sequence per step is non-trivial on GPU (Chapter 3).
  • Prefill needs logits only at the last position. A naive implementation computes \((T\times d)\cdot(d\times|V|)\) during prefill; a good engine slices to the last token first, saving \(2d|V|(T-1)\) FLOPs and a \(T\times|V|\) activation.
Production gotcha — incremental detokenisation

With byte-level BPE a single token may contain an incomplete UTF-8 sequence (a Chinese character or an emoji split across two tokens), and SentencePiece tokens carry leading-space markers whose rendering depends on the previous token. Streaming servers therefore decode a sliding window of recent tokens and emit only the newly stable suffix of text. Tokenisation and detokenisation run on the CPU and, at high request rates, can become a real bottleneck—one reason vLLM V1 moved them into separate processes (Chapter 11).

2.3 Embeddings and the LM head

The embedding matrix \(E\in\mathbb{R}^{|V|\times d}\) maps token id \(i\) to row \(E_i\). This is a gather, not a matrix product: zero FLOPs, \(T\cdot d\cdot b\) bytes read. At the top, the unembedding or LM head \(W_U\in\mathbb{R}^{d\times|V|}\) maps the final hidden state to logits \(z = h W_U\). Press and Wolf (2016)[6] showed that tying \(W_U = E^\top\) works well and saves \(|V|d\) parameters; GPT-2, Gemma and small Llama 3.2 models tie, Llama 3 8B/70B do not.

2.4 Scaled dot-product attention

Let \(X\in\mathbb{R}^{T\times d}\) be the (normalised) inputs of one sequence. For a single head with projections \(W_Q, W_K, W_V\in\mathbb{R}^{d\times d_h}\):

\[ Q = XW_Q,\quad K = XW_K,\quad V = XW_V \;\in\mathbb{R}^{T\times d_h},\qquad S = \frac{QK^\top}{\sqrt{d_h}} + M \in\mathbb{R}^{T\times T}, \] \[ P = \operatorname{softmax}_{\text{row}}(S), \qquad O = PV\in\mathbb{R}^{T\times d_h}, \qquad M_{ij} = \begin{cases}0 & j\le i\\ -\infty & j>i\end{cases}. \]

Row \(i\) of \(O\) is a convex combination of value vectors of positions \(j\le i\), with weights determined by the similarity \(q_i\cdot k_j\). The causal mask \(M\) is what makes the model autoregressive: position \(i\) cannot see the future.

Why divide by \(\sqrt{d_h}\)?

Suppose the coordinates of \(q\) and \(k\) are independent with mean 0 and variance 1 (roughly true at initialisation with a normalised input). Then \[ \mathbb{E}[q\cdot k] = 0,\qquad \operatorname{Var}(q\cdot k) = \sum_{c=1}^{d_h}\operatorname{Var}(q_c k_c) = \sum_c \mathbb{E}[q_c^2]\,\mathbb{E}[k_c^2] = d_h . \] Unscaled logits therefore have standard deviation \(\sqrt{d_h}\) (≈11 for \(d_h=128\)). Softmax of logits that differ by tens is essentially one-hot: the Jacobian \(\operatorname{diag}(p)-pp^\top\) is nearly zero, so gradients vanish and training stalls. Dividing by \(\sqrt{d_h}\) restores unit variance. (Some recent models add QK-norm—RMSNorm on \(q\) and \(k\)—to control logit growth during training.)

Multi-head attention

With \(n_h\) heads, each head \(i\) has its own \(W_Q^{(i)},W_K^{(i)},W_V^{(i)}\in\mathbb{R}^{d\times d_h}\) with \(d_h = d/n_h\), producing \(O^{(i)}\in\mathbb{R}^{T\times d_h}\). The outputs are concatenated and mixed:

\[ \operatorname{MHA}(X) = [O^{(1)};\dots;O^{(n_h)}]\,W_O,\qquad W_O\in\mathbb{R}^{d\times d}. \]

In implementation, the \(n_h\) query projections are one \(d\times d\) matrix whose output is reshaped to \((T, n_h, d_h)\) and transposed to \((n_h, T, d_h)\): heads are a batch dimension. Each head can specialise (previous-token heads, induction heads, positional heads[7]).

From MHA to MQA and GQA: the first KV-cache optimisation

During decoding, every step must read the cached \(K\) and \(V\) of every head for every past token. Shazeer (2019)[8] observed that this memory traffic, not FLOPs, limits decoding speed, and proposed multi-query attention (MQA): all query heads share a single key head and a single value head (\(n_{kv}=1\)). The KV cache shrinks by \(n_h\times\). Quality degraded slightly and training was sometimes unstable, so Ainslie et al. (2023)[9] proposed the interpolation grouped-query attention (GQA): \(n_{kv}\) groups, each shared by \(g=n_h/n_{kv}\) query heads. Llama 2 70B uses \(n_h=64, n_{kv}=8\); Llama 3 uses GQA at every size. Multi-head latent attention (MLA, DeepSeek-V2, 2024)[10] goes further, caching a low-rank latent instead of per-head keys and values; Chapter 7 derives it.

2.5 Positional information

Proposition — attention without positions is permutation-equivariant

Let \(\Pi\) be a permutation matrix and drop the causal mask. Then \((\Pi X)W_Q (\Pi X W_K)^\top = \Pi\,QK^\top\Pi^\top\); row-softmax commutes with simultaneous row/column permutation, so \(P' = \Pi P\Pi^\top\) and \(O' = \Pi P \Pi^\top \Pi V = \Pi O\). Permuting the inputs merely permutes the outputs: the model cannot tell "dog bites man" from "man bites dog". (The causal mask breaks the symmetry somewhat, which is why decoder-only models without explicit positions—"NoPE"—can still learn some positional information, but explicit encodings work better.)

The field tried several fixes, roughly in this order:

  • Sinusoidal absolute encodings (2017): add \(\mathrm{PE}_{(m,2i)} = \sin(m/10000^{2i/d})\), \(\mathrm{PE}_{(m,2i+1)}=\cos(m/10000^{2i/d})\) to the input embedding.
  • Learned absolute embeddings (GPT-2/3, BERT): a trainable \(T_{\max}\times d\) table. Cannot extrapolate beyond \(T_{\max}\).
  • ALiBi[11] (2021): no embeddings; add a head-specific linear penalty \(-\lambda_h\,(i-j)\) to attention logits. Extrapolates somewhat to longer sequences; used by BLOOM and MPT.
  • Rotary position embedding, RoPE[12] (2021): rotate queries and keys by a position-dependent angle. The de facto standard since LLaMA (2023).

RoPE, properly

Split \(q\in\mathbb{R}^{d_h}\) into \(d_h/2\) pairs \((q_{2i},q_{2i+1})\) and view each pair as a complex number \(\tilde q_i = q_{2i} + \mathrm{i}\,q_{2i+1}\). Choose frequencies \(\theta_i = \beta^{-2i/d_h}\) for \(i = 0,\dots,d_h/2-1\) (base \(\beta=10^4\) in LLaMA, \(5\times10^5\) in Llama 3). At position \(m\), RoPE multiplies each pair by a unit complex number:

\[ \operatorname{RoPE}(q, m)_i = \tilde q_i\, e^{\mathrm{i} m\theta_i} \quad\Longleftrightarrow\quad \begin{pmatrix} q'_{2i}\\ q'_{2i+1}\end{pmatrix} = \begin{pmatrix}\cos m\theta_i & -\sin m\theta_i\\ \sin m\theta_i & \cos m\theta_i\end{pmatrix}\begin{pmatrix} q_{2i}\\ q_{2i+1}\end{pmatrix}. \]
Theorem — RoPE logits depend only on relative position

For a query at position \(m\) and a key at position \(n\), \[ \big\langle \operatorname{RoPE}(q,m), \operatorname{RoPE}(k,n)\big\rangle = \operatorname{Re}\sum_i \tilde q_i e^{\mathrm{i}m\theta_i}\,\overline{\tilde k_i e^{\mathrm{i}n\theta_i}} = \operatorname{Re}\sum_i \tilde q_i\,\overline{\tilde k_i}\,e^{\mathrm{i}(m-n)\theta_i}. \] Equivalently, with \(R_m\) the block-diagonal rotation, \(R_m^\top R_n = R_{n-m}\) because rotations in each plane form a group. The score is a function of \(q\), \(k\) and \(m-n\) only.

Low-index pairs rotate fast (high frequency, sensitive to nearby positions); high-index pairs rotate slowly and carry long-range information. Context-extension methods (position interpolation, NTK-aware scaling, YaRN; Chapter 19) work by rescaling these frequencies.

Inference consequence — the cache stores rotated keys

Engines apply RoPE to \(k\) before writing it to the KV cache, so a cached key is bound to its absolute position. Prefix caching therefore reuses KV only for prefixes at the same positions, and techniques that drop or move tokens (StreamingLLM, some KV-eviction schemes, "context shifting" in llama.cpp) must either re-rotate cached keys or accept position gaps. MLA (DeepSeek) keeps a small separate RoPE key precisely because rotation does not commute with its low-rank compression (Chapter 7).

2.6 Normalisation: LayerNorm → RMSNorm, Post-LN → Pre-LN

LayerNorm[13] normalises each token vector: \(\operatorname{LN}(x) = \gamma\odot\frac{x-\mu}{\sqrt{\sigma^2+\epsilon}}+\beta\), with \(\mu,\sigma^2\) the mean and variance over the \(d\) coordinates. RMSNorm[14] drops the centring and the bias:

\[ \operatorname{RMSNorm}(x) = \gamma\odot \frac{x}{\sqrt{\tfrac{1}{d}\sum_c x_c^2+\epsilon}} . \]

It is slightly cheaper (one reduction instead of two) and empirically as good, so Llama-family models use it. Both are tiny in FLOPs but are memory-bound reductions: on a GPU their cost is the time to read and write the \(T\times d\) activation, which is why engines fuse "residual add + RMSNorm" into one kernel (Chapter 6).

Where the normalisation sits matters more. The original Transformer used Post-LN: \(x\leftarrow\operatorname{LN}(x+\operatorname{Sublayer}(x))\). Xiong et al. (2020)[15] showed that with Post-LN the gradients near the output layer are large at initialisation, requiring careful learning-rate warm-up; Pre-LN, \(x\leftarrow x + \operatorname{Sublayer}(\operatorname{LN}(x))\), keeps an identity path from input to output (the residual stream) and trains stably without warm-up. GPT-2 onward use Pre-LN; some 2024–25 models (Gemma 2/3, OLMo 2) add extra norms after sub-layers too ("sandwich" norm).

2.7 Feed-forward networks: ReLU → GELU → SwiGLU

The original FFN is a two-layer MLP applied to each position independently, \(\operatorname{FFN}(x) = \max(0, xW_1)W_2\) with \(W_1\in\mathbb{R}^{d\times 4d}\). GPT-2 and BERT replaced ReLU by GELU[16]. Shazeer (2020)[17] showed that gated linear units train better:

\[ \operatorname{SwiGLU}(x) = \big(\operatorname{SiLU}(xW_1)\odot xW_3\big)W_2,\qquad \operatorname{SiLU}(z)=z\,\sigma(z),\quad W_1,W_3\in\mathbb{R}^{d\times d_{ff}},\ W_2\in\mathbb{R}^{d_{ff}\times d}. \]

SwiGLU has three matrices instead of two. To keep the parameter count equal to a \(4d\) ReLU FFN (\(2\cdot 4d^2 = 8d^2\)), set \(3dd_{ff}=8d^2\), i.e. \(d_{ff} = \tfrac{8}{3}d\). LLaMA-7B uses \(d_{ff}=11008\approx 2.69d\) (\(\tfrac83 d\) rounded up to a multiple of 256); Llama 3 8B widened it to \(14336=3.5d\).

The FFN holds about two-thirds of a dense model's non-embedding parameters, so it dominates weight bytes—and it is the part replaced by a Mixture of Experts in MoE models (Chapter 17).

2.8 Counting parameters

With \(d_{kv} := n_{kv}d_h\), one block contains

\[ \underbrace{d\cdot d}_{W_Q} + \underbrace{2\cdot d\cdot d_{kv}}_{W_K,W_V} + \underbrace{d\cdot d}_{W_O} + \underbrace{3\cdot d\cdot d_{ff}}_{W_1,W_2,W_3} + \underbrace{2d}_{\text{norms}} \]

parameters, and the whole model has

\[ N = L\big(2d^2 + 2dd_{kv} + 3dd_{ff} + 2d\big) + |V|d\,(1 + [\text{untied}]) + d . \]

Rule of thumb for MHA with a 4d ReLU/GELU FFN: \(N\approx 12Ld^2\) (4d² attention + 8d² FFN per layer).

Worked example — Llama 2 7B (MHA, \(n_{kv}=n_h=32\))

Attention: \(4d^2 = 4\times4096^2 = 67.11\)M. FFN: \(3\times4096\times11008 = 135.27\)M. Norms: 8,192. Per layer: 202.38M; ×32 layers = 6.476B. Embedding + untied head: \(2\times32000\times4096 = 262.1\)M. Total ≈ 6.738B—matching the published "6.74B".

Worked example — Llama 3 8B (GQA, \(n_{kv}=8\))

\(d_{kv} = 8\times128 = 1024\). Attention: \(2\times4096^2 + 2\times4096\times1024 = 33.55\text{M}+8.39\text{M} = 41.94\)M. FFN: \(3\times4096\times14336=176.16\)M. Per layer ≈ 218.11M; ×32 = 6.980B. Embedding + untied head: \(2\times128256\times4096 = 1.051\)B. Total ≈ 8.03B. Note that GQA cut attention parameters by 37% versus MHA, and that the big vocabulary makes embeddings 13% of the model.

Worked example — Llama 2 70B

\(d=8192, L=80, n_{kv}=8, d_h=128, d_{ff}=28672\). Attention: \(2\times8192^2+2\times8192\times1024 = 134.2\text{M}+16.8\text{M}=151.0\)M. FFN: \(3\times8192\times28672=704.6\)M. Per layer ≈ 855.6M; ×80 = 68.45B. Embedding + head: 0.52B. Total ≈ 68.98B.

2.9 Counting FLOPs

The fundamental rule

Multiplying \(A\in\mathbb{R}^{m\times k}\) by \(B\in\mathbb{R}^{k\times n}\) takes \(mn\) dot products of length \(k\): \(mnk\) multiplies and \(mn(k-1)\approx mnk\) adds. We count \(2mnk\) FLOPs. (Hardware vendors count a fused multiply-add as 2 FLOPs as well.)

Apply it to a linear layer with weight \(W\in\mathbb{R}^{k\times n}\) processing \(M\) tokens: \(2Mkn\) FLOPs, i.e. 2 FLOPs per parameter per token. Summing over all weight matrices:

\[ C_{\text{forward}} \approx 2N_{\text{matmul}} + \underbrace{4\,L\,n_h d_h\,t}_{\text{attention scores and }PV}\quad\text{FLOPs per token at context length }t, \]

where \(N_{\text{matmul}}\) excludes the embedding table (a lookup) but includes the LM head. Kaplan et al. write the same as \(2N + 2n_{\text{layer}}n_{\text{ctx}}d_{\text{attn}}\), averaging over a causal window.

Where the attention term comes from. For one new query at position \(t\), each head computes \(t\) dot products of length \(d_h\) for \(q\cdot k_j\) (\(2td_h\) FLOPs) and a weighted sum of \(t\) value vectors (\(2td_h\)). Times \(n_h\) heads and \(L\) layers: \(4Ln_hd_ht = 4Ldt\) when \(n_hd_h=d\). Note that GQA does not reduce attention FLOPs—every query head still attends—only the bytes read.

When does attention compute matter?

For an MHA model with \(N\approx12Ld^2\), the ratio of attention FLOPs to weight FLOPs per token is \[ \frac{4Ldt}{2\cdot12Ld^2} = \frac{t}{6d}. \] For \(d=4096\) attention compute equals weight compute at \(t\approx 24{,}600\) tokens. Below a few thousand tokens, "\(2N\) FLOPs per token" is accurate to a few percent; at 128k context, attention dominates compute. (Its memory traffic matters much earlier during decode—§2.11.)

Why training costs \(6N\)

For \(Y = XW\) with \(X\in\mathbb{R}^{M\times k}\): the forward pass costs \(2Mkn\). Back-propagation needs \(\partial\mathcal{L}/\partial X = (\partial\mathcal{L}/\partial Y)\,W^\top\) (another \(2Mkn\)) and \(\partial\mathcal{L}/\partial W = X^\top(\partial\mathcal{L}/\partial Y)\) (another \(2Mkn\)). Total \(6Mkn\): \(2\) forward \(+\,4\) backward FLOPs per parameter per token, so \(C_{\text{train}}\approx 6ND\). With activation recomputation (gradient checkpointing) it becomes \(\approx8ND\).

2.10 Autoregressive generation: prefill, decode and the KV cache

Generation has two phases with completely different performance characteristics.

  • Prefill (a.k.a. prompt processing, context encoding). Run the model on all \(n_{\text{in}}\) prompt tokens at once, like a training forward pass with no backward. This computes and stores \(K\) and \(V\) for every prompt token in every layer, and the logits of the last position, from which the first output token is sampled. It is a sequence of large matrix–matrix products: compute-bound.
  • Decode (a.k.a. generation, incremental decoding). Each step feeds only the newest token, computes its \(q,k,v\), appends \(k,v\) to the cache, attends over the cache, and produces the next logits. It is a sequence of matrix–vector (or skinny matrix) products plus cache reads: memory-bound.

Why caching is exact

Proposition — KV caching changes nothing

Let \(h^{(\ell)}_j\) be the hidden state of position \(j\) after layer \(\ell\). Claim: \(h^{(\ell)}_j\) depends only on tokens \(x_{1:j}\). Proof by induction on \(\ell\). For \(\ell=0\), \(h^{(0)}_j = E_{x_j}\). Suppose true for \(\ell-1\). In layer \(\ell\), the norm and FFN act position-wise; attention at position \(j\) combines \(q_j\) with \(k_i, v_i\) for \(i\le j\) only (causal mask), each of which is a function of \(h^{(\ell-1)}_i\), hence of \(x_{1:i}\subseteq x_{1:j}\). ∎

Consequently the keys and values of positions \(1..t\) are the same whether we compute them in one pass over \(x_{1:t}\) or incrementally; appending new tokens never changes them. Storing them is pure memoisation. (Numerically, results can differ in the last bits because floating-point reductions are performed in different orders—relevant to reproducibility, Chapter 3.)

Without a cache, step \(t\) would recompute the whole prefix: \(\sum_{t=1}^{T}2Nt\approx NT^2\) FLOPs for \(T\) tokens instead of \(2NT\)—a factor of \(T/2\) waste.

2.11 Arithmetic intensity and the first roofline

Definition — arithmetic intensity and the roofline

The arithmetic intensity of a kernel is \(I = \text{FLOPs} / \text{bytes}\), counting bytes moved to and from main memory. On a machine with peak compute \(P\) (FLOP/s) and bandwidth \(\beta\) (bytes/s), the attainable throughput is bounded by the roofline[18] \[ \text{attainable FLOP/s} = \min(P,\ I\cdot\beta), \] and the ridge point \(I^{*} = P/\beta\) separates memory-bound kernels (\(I<I^{*}\)) from compute-bound ones (\(I>I^{*}\)). For an H100 SXM in dense BF16: \(I^{*}\approx 989\times10^{12}/3.35\times10^{12}\approx 295\) FLOPs/byte.

Linear layers

A weight \(W\in\mathbb{R}^{k\times n}\) applied to \(M\) token vectors (\(M=B\) during decode, \(M=B\cdot n_{\text{in}}\) during prefill) performs \(2Mkn\) FLOPs and moves \(b(kn + Mk + Mn)\) bytes (weights, inputs, outputs). Hence

\[ I_{\text{linear}} = \frac{2Mkn}{b(kn+Mk+Mn)} \;\xrightarrow{\;M\ll k,n\;}\; \frac{2M}{b}\quad(=M\text{ FLOPs/byte in BF16}). \]

So in BF16 each token that shares a weight read contributes about one FLOP per byte. Decode at batch 1: \(I\approx1\). Decode at batch 64: \(I\approx64\), still memory-bound on H100. Prefill of a 2,000-token prompt: \(I\) in the thousands (capped by the \(Mk+Mn\) activation terms), comfortably compute-bound. The crossover batch for weight-dominated decode is roughly the ridge point: \(B^{*}\approx I^{*} b/2\approx 295\) in BF16 on H100 (≈150 on A100), which is why decode engines want hundreds of concurrent sequences.

Decode attention: a batch-independent intensity

For one sequence at context \(t\), one layer of decode attention reads the cache—\(2\,t\,n_{kv}d_h\,b\) bytes—and performs \(4\,t\,n_hd_h\) FLOPs. Thus

\[ I_{\text{attn-decode}} = \frac{4tn_hd_h}{2tn_{kv}d_hb} = \frac{2}{b}\cdot\frac{n_h}{n_{kv}} = \frac{2g}{b}. \]

In BF16, MHA gives 1 FLOP/byte, GQA with \(g=8\) gives 8. Crucially, this does not improve with batch size: each sequence has its own cache, so there is nothing to share. Batching amortises weights but not KV. At long contexts the KV read dominates the step—which is the quantitative reason for GQA, MLA, KV quantisation and sparse attention.

2.12 A latency model for decode

Putting it together, a decode step for a batch of \(B\) sequences with average context \(\bar t\) takes roughly

\[ t_{\text{step}}(B) \approx \max\Bigg(\underbrace{\frac{N b + B\,\bar t\, s_{\text{kv}}}{\beta}}_{\text{memory time}},\ \underbrace{\frac{2N_{\text{matmul}}B + 4Ld\bar tB}{P}}_{\text{compute time}}\Bigg) + t_{\text{overhead}}, \]

throughput \(=B/t_{\text{step}}\) tokens/s; per-user speed \(=1/t_{\text{step}}\). \(t_{\text{overhead}}\) covers kernel launches, sampling and scheduling (reduced by CUDA graphs and overlapped scheduling, Chapters 6 and 11).

2.13 From logits to tokens (preview)

The last hidden state \(h_T\) yields logits \(z = \operatorname{RMSNorm}(h_T)W_U\in\mathbb{R}^{|V|}\). The next token is drawn from

\[ p_\tau(i) = \frac{\exp(z_i/\tau)}{\sum_j\exp(z_j/\tau)}, \]

where the temperature \(\tau\) interpolates between greedy decoding (\(\tau\to0\), argmax) and the model's raw distribution (\(\tau=1\)); a Gibbs distribution at inverse temperature \(1/\tau\). Truncation (top-\(k\), top-\(p\), min-\(p\)), penalties, and grammar-constrained decoding are the subject of Chapter 3. Computationally, softmax is a memory-bound reduction over \(|V|\) per sequence; numerically it is computed as \(\exp(z_i-\max_j z_j)\) to avoid overflow—an idea that becomes the "online softmax" at the heart of FlashAttention.

The following is a complete, runnable Llama-style model with RMSNorm, RoPE, grouped-query attention, SwiGLU and a pre-allocated KV cache—stripped of everything except the inference path. It uses random weights; load real ones by mapping parameter names from a checkpoint. Read it with Figure 2.1 open.

import torch, torch.nn as nn, torch.nn.functional as F

class Cfg:                                   # tiny Llama-style hyper-parameters
    d, L, n_h, n_kv, d_ff, V, max_T, rope_base = 512, 8, 8, 2, 1408, 32000, 2048, 10000.0

def rope_tables(c, device):
    d_h = c.d // c.n_h
    inv = c.rope_base ** (-torch.arange(0, d_h, 2, device=device) / d_h)   # θ_i, shape (d_h/2,)
    ang = torch.outer(torch.arange(c.max_T, device=device), inv)           # m·θ_i, shape (max_T, d_h/2)
    return ang.cos(), ang.sin()

def apply_rope(x, cos, sin):                  # x: (B, heads, T, d_h); cos/sin: (T, d_h/2)
    x1, x2 = x[..., 0::2], x[..., 1::2]          # coordinate pairs (2i, 2i+1)
    rot = torch.stack((x1 * cos - x2 * sin, x1 * sin + x2 * cos), dim=-1)
    return rot.flatten(-2)                      # re-interleave → (B, heads, T, d_h)

class RMSNorm(nn.Module):
    def __init__(self, d, eps=1e-6):
        super().__init__(); self.w = nn.Parameter(torch.ones(d)); self.eps = eps
    def forward(self, x):
        return self.w * x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)

class Block(nn.Module):
    def __init__(self, c):
        super().__init__(); self.c = c; d_h = c.d // c.n_h
        self.wq = nn.Linear(c.d, c.n_h * d_h, bias=False)
        self.wk = nn.Linear(c.d, c.n_kv * d_h, bias=False)
        self.wv = nn.Linear(c.d, c.n_kv * d_h, bias=False)
        self.wo = nn.Linear(c.n_h * d_h, c.d, bias=False)
        self.w1 = nn.Linear(c.d, c.d_ff, bias=False)    # gate
        self.w3 = nn.Linear(c.d, c.d_ff, bias=False)    # up
        self.w2 = nn.Linear(c.d_ff, c.d, bias=False)    # down
        self.n1, self.n2 = RMSNorm(c.d), RMSNorm(c.d)

    def forward(self, x, cache, pos, cos, sin):    # x: (B, T, d); new tokens occupy positions pos..pos+T-1
        B, T, _ = x.shape; c = self.c; d_h = c.d // c.n_h
        h = self.n1(x)
        q = self.wq(h).view(B, T, c.n_h,  d_h).transpose(1, 2)    # (B, n_h,  T, d_h)
        k = self.wk(h).view(B, T, c.n_kv, d_h).transpose(1, 2)    # (B, n_kv, T, d_h)
        v = self.wv(h).view(B, T, c.n_kv, d_h).transpose(1, 2)
        cs, sn = cos[pos:pos + T], sin[pos:pos + T]
        q, k = apply_rope(q, cs, sn), apply_rope(k, cs, sn)        # cache stores ROTATED keys
        K, Vc = cache                                              # pre-allocated (B, n_kv, max_T, d_h)
        K[:, :, pos:pos + T] = k                                   # append: the only write to the cache
        Vc[:, :, pos:pos + T] = v
        g = c.n_h // c.n_kv                                        # GQA group size
        k_all = K[:, :, :pos + T].repeat_interleave(g, dim=1)      # (B, n_h, pos+T, d_h) — real kernels avoid this copy
        v_all = Vc[:, :, :pos + T].repeat_interleave(g, dim=1)
        # query i (absolute position pos+i) may see keys j ≤ pos+i
        mask = torch.ones(T, pos + T, dtype=torch.bool, device=x.device).tril(diagonal=pos)
        o = F.scaled_dot_product_attention(q, k_all, v_all, attn_mask=mask)   # (B, n_h, T, d_h)
        x = x + self.wo(o.transpose(1, 2).reshape(B, T, c.n_h * d_h))
        h = self.n2(x)
        return x + self.w2(F.silu(self.w1(h)) * self.w3(h))     # SwiGLU FFN

class TinyLlama(nn.Module):
    def __init__(self, c):
        super().__init__(); self.c = c
        self.emb = nn.Embedding(c.V, c.d)
        self.blocks = nn.ModuleList(Block(c) for _ in range(c.L))
        self.norm = RMSNorm(c.d)
        self.head = nn.Linear(c.d, c.V, bias=False)

    def new_cache(self, B, device, dtype):
        shape = (B, self.c.n_kv, self.c.max_T, self.c.d // self.c.n_h)
        return [(torch.zeros(shape, device=device, dtype=dtype),
                 torch.zeros(shape, device=device, dtype=dtype)) for _ in range(self.c.L)]

    def forward(self, ids, cache, pos, cos, sin):
        x = self.emb(ids)                                          # gather, not a matmul
        for blk, layer_cache in zip(self.blocks, cache):
            x = blk(x, layer_cache, pos, cos, sin)
        return self.head(self.norm(x[:, -1:]))                    # logits for the LAST position only

@torch.no_grad()
def generate(model, prompt_ids, n_new, temperature=0.8):
    B, T0 = prompt_ids.shape; dev = prompt_ids.device
    cos, sin = rope_tables(model.c, dev)
    cache = model.new_cache(B, dev, next(model.parameters()).dtype)
    logits = model(prompt_ids, cache, 0, cos, sin)                 # PREFILL: all T0 tokens in one pass
    out, pos = [], T0
    for _ in range(n_new):                                        # DECODE: one token per step
        probs = torch.softmax(logits[:, -1] / temperature, dim=-1)
        nxt = torch.multinomial(probs, 1)                          # (B, 1)
        out.append(nxt)
        logits = model(nxt, cache, pos, cos, sin); pos += 1
    return torch.cat(out, dim=1)

model = TinyLlama(Cfg()).eval()
print(generate(model, torch.randint(0, Cfg.V, (2, 16)), n_new=8))   # two sequences, 16-token prompts
What a production engine does differently
  • No contiguous per-sequence buffers. The cache is a pool of fixed-size blocks with a per-sequence block table (PagedAttention, Chapter 9), so sequences of different lengths share memory without waste.
  • No repeat_interleave. GQA kernels read each KV head once and apply it to its \(g\) query heads in on-chip memory—that is where the \(g\times\) intensity gain comes from.
  • Ragged batches. Prefill tokens of new requests and decode tokens of running requests are packed into one flat token batch each step (continuous batching with chunked prefill, Chapter 10), with attention kernels such as FlashAttention/FlashInfer handling variable lengths (Chapter 8).
  • Fused kernels and CUDA graphs to remove launch overhead at small batch (Chapter 6); tensor parallelism to split each matrix across GPUs (Chapter 16).
  • Note: this code pairs coordinates as \((2i,2i+1)\); Hugging Face's Llama pairs \((i, i+d_h/2)\) ("rotate-half"). Both are valid RoPE variants, but weights trained with one are not interchangeable with the other without permuting \(W_Q,W_K\) columns.

Chapter summary

  • A Llama-style block: \(x\leftarrow x+\mathrm{Attn}(\mathrm{RMSNorm}(x))\), \(x\leftarrow x+\mathrm{SwiGLU}(\mathrm{RMSNorm}(x))\); RoPE on \(q,k\); GQA.
  • \(\sqrt{d_h}\) keeps logit variance \(O(1)\); RoPE makes logits depend on \(m-n\) via \(R_m^\top R_n=R_{n-m}\).
  • \(N = L(2d^2+2dd_{kv}+3dd_{ff}+2d)+|V|d(1+[\text{untied}])\); Llama 3 8B ≈ 8.03B.
  • Inference ≈ \(2N\) FLOPs/token \(+\,4Ldt\) for attention; training ≈ \(6N\). Attention compute rivals weights at \(t\approx6d\).
  • Prefill is compute-bound (sets TTFT); decode is memory-bound (sets TPOT).
  • KV per token \(=2Ln_{kv}d_hb\): 512 KiB (Llama 2 7B), 128 KiB (Llama 3 8B), ≈69 KiB (DeepSeek-V3 MLA).
  • Linear-layer intensity ≈ tokens sharing the weight read (BF16); decode attention intensity \(=2g/b\), independent of batch.
  • Decode step ≈ (weights + batch KV)/bandwidth; batch is limited by KV memory long before compute.

Warm-up Why do we divide attention scores by \(\sqrt{d_k}\)?

If query/key coordinates are roughly independent with unit variance, \(q\cdot k\) has variance \(d_k\). For \(d_k=128\), logits have std ≈ 11, and softmax becomes nearly one-hot; its Jacobian \(\operatorname{diag}(p)-pp^\top\) is then close to zero, so gradients vanish and training is slow or unstable. Scaling by \(1/\sqrt{d_k}\) keeps logits at unit variance, so attention starts out diffuse and learnable. Follow-ups: it is a temperature; QK-norm is a stronger fix used in some newer models; MLA and other variants adjust the scale for their effective head dimension.

Core Derive the KV-cache size and compute it for Llama 2 70B at 8 concurrent 16k-token requests.

Each layer caches a key and a value vector for each KV head: \(2\times n_{kv}\times d_h\) elements per token per layer. Over \(L\) layers at \(b\) bytes: \(s_{kv}=2Ln_{kv}d_hb\). Llama 2 70B: \(2\times80\times8\times128\times2=327{,}680\) B = 320 KiB/token. For 8 × 16,384 tokens: \(131{,}072\times320\) KiB = 40 GiB. Weights are ~138 GB in BF16, so with 2×H100 (160 GB) there is only ~20 GB left—insufficient; you'd need 4×H100 with TP=4, FP8 weights, or FP8 KV (20 GiB). Point out that without GQA (MHA, 64 KV heads) it would be 8× more: 320 GiB.

Core Why is decode memory-bound but prefill compute-bound? Use arithmetic intensity.

A linear layer with weights \(k\times n\) applied to \(M\) tokens does \(2Mkn\) FLOPs and reads \(\approx bkn\) weight bytes; intensity ≈ \(2M/b\) (= \(M\) in BF16). Prefill has \(M=B\cdot n_{\text{in}}\) (thousands) → intensity far above the ridge (≈295 on H100) → compute-bound. Decode has \(M=B\) (1 to a few hundred) → below the ridge → bandwidth-bound. Decode attention is worse: intensity \(2g/b\) (1 for MHA, 8 for GQA-8) regardless of batch, because each sequence's KV cache is private. Hence prefill time ∝ FLOPs/peak and decode time ∝ bytes/bandwidth.

Core What does GQA buy you, and what does it cost?

Buys: KV cache and its bandwidth shrink by \(g=n_h/n_{kv}\) (4× for Llama 3 8B, 8× for 70B); decode attention intensity rises from 1 to \(g\) FLOPs/byte; more concurrent sequences fit; K/V projection parameters shrink; with tensor parallelism, KV heads are naturally partitioned across GPUs (as long as TP ≤ \(n_{kv}\); beyond that KV heads must be replicated). Costs: a small quality loss versus MHA at equal size (mostly recovered by training; Ainslie et al. also showed MHA checkpoints can be "uptrained" into GQA with ~5% of pre-training compute); attention FLOPs are unchanged. MQA (\(n_{kv}=1\)) is the extreme with larger quality risk and the TP replication problem; MLA trades extra compute (up/down projections, absorbed into weights at inference) for even smaller caches.

Core Explain RoPE and prove its relative-position property.

RoPE groups coordinates into \(d_h/2\) pairs, treats each as a complex number, and multiplies pair \(i\) of the query (or key) at position \(m\) by \(e^{\mathrm{i}m\theta_i}\), with \(\theta_i=\beta^{-2i/d_h}\). Then \(\langle\mathrm{RoPE}(q,m),\mathrm{RoPE}(k,n)\rangle=\operatorname{Re}\sum_i\tilde q_i\overline{\tilde k_i}e^{\mathrm{i}(m-n)\theta_i}\), which depends only on \(m-n\). In matrix form, \(R_m\) is block-diagonal of 2×2 rotations and \(R_m^\top R_n=R_{n-m}\). Advantages: no learned parameters, relative-position behaviour inside attention, works with any length (though quality beyond training length requires frequency rescaling such as PI/NTK/YaRN). Inference notes: applied to q and k only (not v); applied before caching; fused into the QKV projection or attention kernel.

Core Estimate the decode throughput of Llama 3 8B on one H100 at batch 64 with 2k-token contexts.

Bytes per step: weights 16.06 GB + KV \(64\times2048\times128\text{ KiB}=17.2\) GB ≈ 33.3 GB → at 3.35 TB/s ≈ 9.9 ms. Compute: \(2\times7.5\times10^9\times64\approx9.6\times10^{11}\) + attention \(\approx 7\times10^{10}\) FLOPs → ~1.0 ms at peak. Memory-bound: step ≈ 10 ms ideal, say 12–14 ms at 70–80% MBU. Throughput ≈ 64/0.013 ≈ 4,500–5,000 tokens/s; per-user ≈ 75–80 tokens/s. To improve: FP8 KV (~7 ms ideal), FP8 weights, larger batch until memory is full, prefix sharing.

Core Why does the LM head deserve special attention in inference engines?

(1) Size: \(d\times|V|\) is the largest single matrix in many modern models (Llama 3 8B: 525M parameters, 1.05 GB in BF16), and it is read every decode step. (2) Compute: \(2d|V|\) FLOPs/token (~6.5% of Llama 3 8B). (3) Prefill waste: compute logits only for the last position (or positions where log-probs are requested), saving a \(T\times|V|\) activation that could be gigabytes. (4) Sampling: softmax and top-k/top-p over 128k–256k logits per sequence need efficient GPU kernels. (5) Parallelism: with tensor parallelism the head is split along the vocabulary dimension, requiring a gather or a distributed argmax/sampling. (6) Speculative decoding and MTP heads often share it.

Deep-dive Show that attention FLOPs equal weight FLOPs at \(t\approx6d\). What changes for GQA and for long-context serving?

Per token at context \(t\): attention scores + weighted sum = \(4Ln_hd_ht=4Ldt\) FLOPs. Weight FLOPs = \(2N\approx24Ld^2\) for an MHA model with a 4d FFN. Equal when \(t=6d\). For GQA, weight FLOPs fall a bit (smaller \(W_K,W_V\)) but attention FLOPs are unchanged, so the crossover moves slightly earlier (for Llama 3 8B's actual parameter count, \(2\times7.5\text{B}/(4\times32\times4096)\approx 28.6\)k tokens because of its wide FFN). For long-context prefill, total attention FLOPs grow as \(\approx2Ldt^2\) and dominate at 128k (hence FlashAttention, context parallelism, sparse attention). For decode, attention's bytes matter far earlier than its FLOPs: KV bytes per step equal weight bytes when \(t\cdot s_{kv}=Nb\), e.g. Llama 3 8B: \(16\text{ GB}/128\text{ KiB}\approx122\)k tokens for one sequence—but with batch 64 the crossover is at under 2k tokens each.

Deep-dive Prove that KV caching is exact. Where can numerical results nevertheless differ?

Induction on layers: hidden state \(h^{(\ell)}_j\) depends only on \(x_{1:j}\). Base: embedding of \(x_j\). Step: position-wise operations preserve the property; causal attention at \(j\) uses \(k_i,v_i\) for \(i\le j\), functions of \(h^{(\ell-1)}_i\), which by hypothesis depend only on \(x_{1:i}\). So appending tokens never changes earlier K/V; caching is memoisation. Numerical differences: floating-point addition is not associative, and the kernels used for prefill (big GEMMs, tiled attention over many queries) and for decode (GEMV, split-K attention) reduce in different orders and tile sizes; batch composition can change kernel choice. Results agree to within rounding but not bit-for-bit, which matters for "temperature 0" reproducibility and for comparing speculative-decoding outputs. Truly batch-invariant kernels fix this at some speed cost (Chapter 3).

Deep-dive Derive the decode-attention arithmetic intensity, and explain why batching does not help it but GQA and MLA do.

One sequence, one layer, context \(t\): read \(K,V\): \(2tn_{kv}d_hb\) bytes. FLOPs: for each of \(n_h\) query heads, \(2td_h\) (scores) + \(2td_h\) (weighted sum) → \(4tn_hd_h\). Intensity \(=2n_h/(n_{kv}b)=2g/b\). A batch of \(B\) sequences reads \(B\) separate caches and does \(B\) times the FLOPs: the ratio is unchanged, unlike weights, which are shared. GQA raises it to \(g\) (BF16) by reusing each loaded KV head for \(g\) query heads in on-chip memory. MLA (with weight absorption) makes all \(n_h=128\) heads attend over the same 576-dim latent, so per byte of cache read it performs \(\sim 2n_h\cdot\frac{(512+64)+512}{576\cdot b}\) FLOPs—hundreds of FLOPs/byte, close to compute-bound on H100, which is why DeepSeek wrote dedicated kernels (FlashMLA). Prefix sharing (many sequences attending to the same cached prefix, e.g. a shared system prompt or parallel sampling) also raises it, enabling "cascade"/shared-prefix attention kernels.

Core Why must engines compute only last-position logits in prefill, and how does that interact with returning prompt log-probs?

Logits are \(T\times|V|\): for a 32k-token prompt and 128k vocabulary that is 4.2B elements (8.4 GB in BF16) and \(2d|V|T\) FLOPs (~34 TFLOPs for Llama 3 8B)—wasted unless needed. Engines gather the hidden state of each sequence's last token before the LM head. If the API requests prompt log-probs (common in evaluation), the engine must compute logits for all prompt positions, usually in chunks to bound memory, and may bypass optimisations such as prefix caching (vLLM documents that requests with prompt logprobs recompute the full prefill).

Core Implement single-step decode attention for one head, given cached K and V. What is its complexity? 
def decode_attn(q, K, V):            # q: (d_h,), K, V: (t, d_h)
    s = K @ q / math.sqrt(q.shape[0]) # (t,)  scores; no mask needed: all t are in the past
    s = s - s.max()                   # numerical stability
    p = torch.exp(s); p = p / p.sum() # softmax
    return p @ V                      # (d_h,)

Time \(O(td_h)\) FLOPs (\(4td_h\)), memory traffic \(O(td_h)\) bytes; it is bandwidth-bound. Follow-ups: batch over heads/sequences; GQA (one K/V for \(g\) queries); for long \(t\), split the sequence into chunks processed by different thread blocks and combine partial softmaxes with the log-sum-exp trick (FlashDecoding, Chapter 8); paged K/V via a block table (Chapter 9).

Deep-dive Why did the field move from ReLU FFNs to SwiGLU, and what are the inference implications?

Shazeer (2020) found gated variants (GEGLU, SwiGLU) give lower perplexity at equal parameters and compute; LLaMA/PaLM adopted SwiGLU. A gate multiplies two linear projections, providing multiplicative interactions and smoother activations. Inference: (1) three matrices instead of two—\(W_1\) and \(W_3\) are typically fused into one \(d\times2d_{ff}\) GEMM, followed by a fused SiLU-and-multiply kernel; (2) with \(d_{ff}=\tfrac83 d\) parameter count matches the old FFN so FLOPs/token are unchanged; (3) activation sparsity is lower than with ReLU, weakening "sparse activation" speed-ups (Deja Vu, PowerInfer) unless models are "ReLU-fied"; (4) the FFN dominates weight bytes, so it is where weight quantisation and MoE give the largest gains.

Design You must serve a 7B-class model with 32k contexts to as many concurrent users as possible on one 80 GB GPU. Which architectural and serving choices matter most?

Start from memory: weights ~14–16 GB (BF16). KV per user at 32k: MHA 7B = 16 GiB (only ~4 users!), GQA-8 (Llama 3 8B-like) = 4 GiB (~15 users). Levers, in order: (1) choose a model with GQA/MLA or sliding-window layers (e.g. interleaved local/global attention cuts most layers' cache to the window); (2) FP8 KV cache (2×) or INT4 KV with careful calibration; (3) FP8/INT4 weights to free ~8–12 GB; (4) PagedAttention to avoid reserving 32k per user when most use far less (Little's law on actual lengths); (5) prefix caching if users share system prompts/documents; (6) KV offload to CPU memory for idle conversations; (7) admission control/preemption policy. Then check bandwidth: at 32k, KV reads per step dominate; expect TPOT to grow with total live tokens, so set an SLO-aware cap on concurrent live tokens rather than users.

Warm-up What is the difference between the residual stream and the hidden size, and why does it matter for tensor parallelism?

The residual stream is the \(d\)-dimensional vector per token that flows through all blocks and accumulates sub-layer outputs (\(x\leftarrow x+f(\mathrm{Norm}(x))\)); "hidden size" is its width \(d\). Sub-layers temporarily expand into other spaces (\(n_hd_h\) for attention, \(d_{ff}\) for the FFN) and project back to \(d\). Tensor parallelism (Megatron) splits those expanded spaces across GPUs—column-parallel first matrix, row-parallel second—so each GPU holds a slice of heads or FFN columns, and an all-reduce over the \(d\)-dimensional output re-forms the residual stream after each sub-layer: two all-reduces of \(B\times T\times d\) per block (Chapter 16).

Design An interviewer gives you a new model config and an accelerator spec sheet. Outline, step by step, how you'd predict TTFT and TPOT.
  1. From the config: compute \(N\) (and active \(N\) for MoE), weight bytes at the serving precision, KV bytes per token \(2Ln_{kv}d_hb\) (or the MLA/sliding-window variant).
  2. From the spec sheet: dense peak FLOP/s at the precision used (not the sparse number), HBM bandwidth, capacity; interconnect if multi-GPU. Ridge point \(P/\beta\).
  3. Fit: weights + KV(batch × context) + workspace ≤ capacity → decide TP degree / max batch.
  4. TTFT ≈ queueing + prefill FLOPs \((2N_{\text{mm}}n_{\text{in}}+2Ldn_{\text{in}}^2)\) / (P × MFU≈0.4–0.6) (+ TP communication).
  5. TPOT ≈ max((weight bytes/TP + per-GPU KV bytes)/(β × MBU≈0.7–0.85), compute time) + per-step overhead (~0.5–2 ms without CUDA graphs) + TP all-reduce latency × 2L.
  6. Sanity-check against known benchmarks; state assumptions; discuss which lever (quantisation, speculative decoding, batching, disaggregation) moves which term.
