Volume II · Part V · Beyond Chat — Chapter 19

Batch, Offline and Rollout Inference

A large and growing share of tokens is generated with nobody waiting for them: evaluation suites, synthetic training data, document-processing pipelines, embedding backfills and the reinforcement-learning rollouts that train reasoning models. Freed from latency targets, such work is judged on cost per token and on meeting a deadline hours away. It can run at batch sizes no interactive service would tolerate, in the troughs that online traffic leaves, and on capacity that may be taken back at any moment. This chapter develops the engineering of inference without an audience.

Why this chapter

Every chapter so far has assumed a user, or an agent, waiting for each answer. That assumption shaped everything: capacity had to cover the peak (Chapter 9), batch sizes were limited by latency targets (Vol. I Chapter 11), and utilisation of 50–60% counted as good (Chapter 10). But consider a company that wants to classify two hundred million support tickets, a lab that must score a new checkpoint on forty benchmarks before tomorrow's meeting, or a training run that needs thirty million generated tokens for each gradient step. None of them cares whether an individual response takes two seconds or two minutes. They care that the whole job finishes by a deadline and what it costs.

Removing the latency constraint changes the optimisation problem, and with it the infrastructure. It is also a favourite interview topic, because it tests whether a candidate understands which constraints produce which designs: "why is the batch API half price?", "how would you run a 200-million-document job by tomorrow, and what would it cost?", "how do you run batch jobs on the same GPUs as production without hurting production?", "why is batch inference a good fit for spot instances when training is a harder one?", "in RL for reasoning models, where does the time go?".

We classify work by how long it can wait (§19.1), derive the throughput-optimal operating point (§19.2) and explain batch pricing through the diurnal trough (§19.3). We then schedule batch work beside online traffic (§19.4), run it on preemptible capacity (§19.5), build the pipelines around the model (§19.6), and examine rollout fleets for reinforcement learning (§19.7), ending with the operational habits of offline work (§19.8).

Learning objectives
  1. Classify inference workloads by deadline and explain how the objective changes from latency to cost per token.
  2. Derive decode throughput as a function of batch size and context length, and find the throughput-optimal operating point.
  3. Explain batch-API pricing from utilisation and trough filling, and compute how much batch work a fleet can absorb for free.
  4. Design priority, preemption and deadline-aware admission for batch work on a shared fleet.
  5. Run batch inference on spot capacity with row-level checkpoints and idempotent outputs, and estimate the waste.
  6. Size an offline pipeline end to end, and describe the infrastructure of RL rollout generation.

Uses: the bandwidth model of decode (Vol. I Chapter 6), prefix caching (Vol. I Chapter 10), cluster sharing (§7.7), spot capacity (§9.5), cold starts (Chapter 5), token economics (Chapter 10), RL rollouts (Vol. I §25.7 and §26.7), sandboxes (§17.3).

19.1 Work that nobody waits for

It is useful to place workloads on a single axis: how long the requester will wait. Figure 19.1 shows four classes. Interactive work—chat, completion, voice—has deadlines of milliseconds to seconds and has occupied this book so far. Asynchronous work—a research agent, a long report, a code review—returns in minutes, and the user does something else meanwhile. Batch work—evaluations, document processing, synthetic data—has a deadline of hours, classically 24. And best-effort work—backfills, speculative precomputation, low-priority experiments—has no deadline at all and runs whenever capacity would otherwise idle.

Figure 19.1 is a statement about flexibility. A workload that can wait gives the operator a degree of freedom: when to run it, on which hardware, and in what company. Every technique in this chapter spends that freedom—on larger batches, on off-peak hours, on cheaper preemptible machines. The classes also differ in what failure means. An interactive request that fails must be retried within the user's patience; a batch row that fails is simply run again later, so batch systems can tolerate far higher transient error rates per attempt, provided they track which rows are done. The first question is how much cheaper a token becomes when latency no longer matters.

19.2 The throughput-optimal operating point

Vol. I Chapter 6 showed that a decode step is limited by memory bandwidth: the step must read the weights once and every active sequence's KV cache once. With \(B\) sequences of mean context \(n_{\text{ctx}}\) tokens, weights of \(W_{\text{bytes}}\) bytes, \(s_{kv}\) bytes of cache per token and effective bandwidth \(\beta_{\text{eff}}\), the step time and the throughput are

\[ t_{\text{step}}(B)=\frac{W_{\text{bytes}}+B\,n_{\text{ctx}}\,s_{kv}}{\beta_{\text{eff}}},\qquad \text{throughput}(B)=\frac{B}{t_{\text{step}}(B)}=\frac{B\,\beta_{\text{eff}}}{W_{\text{bytes}}+B\,n_{\text{ctx}}\,s_{kv}}. \]

Throughput rises with \(B\) because the fixed cost of reading the weights is shared among more sequences, and it saturates at \(\beta_{\text{eff}}/(n_{\text{ctx}}s_{kv})\) when cache reads dominate. Two limits stop the rise earlier: the KV caches must fit in memory, and at very large batches the GPU's arithmetic rate \(\pi\) becomes the limit instead. Figure 19.2 plots the formula for Llama 3 8B on an H100.

Figure 19.2 shows why batch work is cheap, and what limits it. An interactive service rarely runs this model above \(B\approx64\): arrivals are bursty, headroom must be kept for the peak, and each additional sequence lengthens every user's step. A batch job has a queue of millions of rows, so every slot is refilled the instant a sequence finishes, and it runs at the right-hand end of the curve. For short contexts that is 32,000 tokens per second against about 8,500 at \(B=64\), nearly four times the throughput from the same GPU. The figure also shows that context length, not batch size, is the real constraint: at 2,000 tokens of context the memory fills at \(B=236\) and throughput is a quarter of the short-context value. Batch jobs with short rows are therefore far cheaper per token than jobs with long documents, and anything that shortens the context each row carries—sharing a common instruction prefix, trimming retrieved passages—pays twice, in prefill and in decode.

Three further optimisations become available when nobody is watching. Prefix sharing: a batch job typically applies one instruction to millions of rows, so the instruction's KV is computed once and shared by every row (Vol. I Chapter 10), and row order can even be arranged so that rows with a common prefix are adjacent. No streaming: results are written when complete, so the gateway machinery of Chapter 11 is unnecessary and tokens need not be detokenised one at a time. Quantisation and model choice: with time to validate quality offline, a job can use a smaller or more aggressively quantised model for easy rows and escalate hard ones, the cascade of §18.6 applied to cost. What it cannot do is exceed the memory, which makes the context-length distribution of a job the first thing to measure.

Worked example — two hundred million documents by tomorrow

Job. Classify 200 million support tickets with Llama 3 8B. Each row has a 300-token instruction, a 500-token ticket and a 50-token structured answer: 160 billion input tokens and 10 billion output tokens.

Rates. Prefill is compute-bound: \(2N=16\) GFLOP per token at an effective 500 TFLOP/s gives about 31,000 tokens per second per H100. Decode at \(B=512\) with about 850 tokens of context reads \(16+57=73\) GB per step, 27 ms, so about 18,800 tokens per second.

GPU time, naive. Prefill: \(1.6\times10^{11}/31{,}000\approx5.2\times10^6\) s. Decode: \(10^{10}/18{,}800\approx0.53\times10^6\) s. Total about 1,580 GPU-hours.

With the instruction cached. Only the 500-token ticket is prefilled per row: \(10^{11}/31{,}000\approx3.2\times10^6\) s, for a total of about 1,040 GPU-hours, a third less.

Deadline and cost. To finish in 24 hours needs \(1{,}040/24\approx44\) H100s, say 50 with margin. At $2.50 per committed GPU-hour the job costs about $2,600; on spot capacity at $1.00, about $1,050 plus a few percent of waste (§19.5)—roughly five dollars per million documents.

Lesson. The job is dominated by prefill, so the levers are the cached prefix and input length, not decode batching; and its total need, about a thousand GPU-hours, is small beside the idle capacity of a large online fleet, as the next section shows.

19.3 Why the batch API is half price: filling the trough

In April 2024 OpenAI introduced a Batch API that accepted a file of requests, promised results within 24 hours and charged half the interactive price; Anthropic, Google and others followed with similar offerings within the year, at similar discounts. The 50% figure is not arbitrary generosity. It follows from the shape of online demand and the cost structure of Chapter 10.

An online fleet is sized for its peak plus headroom, but demand follows the sun (§12.3), so for much of the day a large fraction of the fleet idles. Those idle GPU-hours are already paid for—by commitments, by depreciation, by the power contract—so their marginal cost is little more than the extra electricity of running rather than idling. Any revenue from them is nearly pure margin. Figure 19.3 shows a stylised day in one region.

Figure 19.3's arithmetic is the business case for batch pricing. If online load averages 55% of capacity and batch work fills the fleet to 90%, the spare capacity averages 35% of the fleet: the fleet can generate \(0.35/0.55\approx64\%\) more token-capacity without one additional GPU. For Atlas's 4,000 H100s that is about 33,600 GPU-hours every day—thirty times the two-hundred-million-document job of §19.2. Selling this capacity at half price is profitable because its marginal cost is near zero, and attractive to customers because half price moves work that would otherwise not be done at all. The 24-hour window is what makes the promise safe: whatever the hour of submission, the window contains a full trough.

The discount also reflects the higher efficiency of batch execution—larger batches, shared prefixes, no streaming—described in §19.2, and it serves the provider in a third way: flexible demand is a shock absorber. When a region loses capacity, or online demand spikes, batch work can be paused within seconds, releasing GPUs to interactive traffic; the batch tier is thus the first rung of the load-shedding ladder of §9.7, and a cheap substitute for idle reserve. The limit of the argument is equally clear. Once batch demand exceeds the trough, further batch work needs GPUs bought for it, and its cost returns to the full cost of a GPU-hour at high utilisation, which is roughly where a 50% discount on a 55%-utilised online price lands.

Drill 19.1 — How much batch can the fleet absorb?

A region has 1,000 GPUs. Online load is 70% of capacity for 8 hours, 50% for 8 hours and 25% for 8 hours. Batch may fill the fleet to 90%. How many GPU-hours per day are available to batch work? A customer submits a job needing 9,000 GPU-hours with a 24-hour deadline at the start of the 70% period; can it be accepted?

Solution. Spare capacity: \((0.90-0.70)\times8+(0.90-0.50)\times8+(0.90-0.25)\times8=1.6+3.2+5.2=10\) fleet-hours, that is 10,000 GPU-hours per day. The job needs 9,000, and its 24-hour window covers all three periods, so it fits—with only 1,000 GPU-hours of slack, and only if no other batch work is queued. An admission controller would accept it at a lower priority than work already promised, or quote a later completion time, because an online surge of a few percent would consume the slack.

19.4 Scheduling batch beside online traffic

Using the trough requires running batch and online work on the same GPUs without the first harming the second. Two designs exist. The coarse one switches whole replicas: an autoscaler (§9.6) watches online load, and replicas not needed online are handed to a batch pool, then reclaimed as load rises. It is simple, but a replica takes minutes to change hands (the cold starts of Chapter 5 if the model differs), so it follows only the slow diurnal swing and wastes the minute-to-minute slack.

The fine-grained design mixes both classes inside one engine. Online and batch requests for the same model share a replica; the engine's scheduler gives online sequences strict priority and fills whatever batch slots and KV memory remain with batch sequences. When online load rises, batch sequences are preempted at a token boundary: their KV is evicted (or offloaded), and they are requeued to resume later—by recomputation, or from a saved prefix—exactly the preemption mechanism of Vol. I §11.7. Systems such as ConServe (2024) showed that this kind of harvesting can raise GPU utilisation substantially while keeping online tail latency close to that of a dedicated fleet[1]. Figure 19.4 illustrates the mechanism.

Figure 19.4 hides three details that decide whether harvesting is safe. First, interference: even a preemptible batch sequence lengthens the decode step while it runs (the \(B\,n_{\text{ctx}}s_{kv}\) term of §19.2), so online TPOT rises with the batch load; the engine must cap batch occupancy at the level where online TPOT still meets its target, and long prefill chunks of batch rows must be bounded (Vol. I §11.5) so that they do not stall decode steps. Second, memory headroom: a new online request needs KV space immediately, so some memory is kept free, or batch KV is evictable without waiting. Third, fairness among batch jobs: with many customers' jobs sharing the trough, a job with a near deadline should run before one submitted earlier with a distant deadline.

That last point is classical real-time scheduling. Each job \(j\) has remaining work \(w_j\) (in GPU-hours) and a deadline; the earliest-deadline-first rule runs the job whose deadline is nearest, and it is optimal in the sense that if any schedule meets all deadlines on the available capacity, EDF does. The admission test is correspondingly simple: order jobs by deadline and check, for each deadline in turn, that the cumulative work due by then does not exceed the spare capacity forecast up to then. Because spare capacity is a forecast—tomorrow's online demand is uncertain—prudent systems admit against a conservative quantile of the forecast (§9.4) and keep purchased capacity or the next region's trough (§12.3) as a fallback for the promises that the forecast fails to cover.

19.5 Spot capacity and row-level checkpoints

Spot instances (§9.5) sell a cloud's own idle capacity at discounts of 60–90%, with the condition that the provider may take the machine back at short notice. Chapter 7 showed what this costs a training job: its state is a single large object, so it must write checkpoints at an interval chosen by the Young–Daly formula, and every preemption loses the work since the last one. Batch inference is in a much better position, for a structural reason: its work is a set of independent rows, and a row's result, once written, never needs recomputing. The checkpoint is simply the set of completed row identifiers, and a preemption loses only the rows in flight—seconds of work—plus the time to restart.

The waste can be estimated in one line. If preemptions arrive at a mean interval \(\text{MTBF}\) and each costs a restart time \(t_{\text{restart}}\) (acquiring a new instance, loading weights, re-warming caches) plus the in-flight work, the fraction of paid time that produces no output is about \(t_{\text{restart}}/(\text{MTBF}+t_{\text{restart}})\). With a preemption every two hours and four minutes to restart, that is about 3%. A spot price of 40% of the committed price then yields an effective cost of \(0.40/0.97\approx41\%\)—a saving that few other optimisations in this book can match. The saving is real only if the pipeline is engineered for it, and three properties matter.

Idempotent, keyed output. Every row has a stable identifier, and results are written keyed by it, so that a row processed twice—because a worker was preempted after generating but before acknowledging—overwrites the same record rather than appending a duplicate. This is the idempotency of §11.7, applied to storage. Small commit units. Results are flushed in chunks of seconds to minutes of work, not at the end of a file of a million rows. Fast restart. Because restart time is the whole waste, the cold-start techniques of Chapter 5—weights cached on local disk or in a nearby object store, streamed loading, pre-pulled images—determine the economics; a 20-minute cold start with hourly preemptions would waste a quarter of the spend. Preemption notices (two minutes on AWS, thirty seconds on some other clouds) are used to stop admitting rows and flush what is finished. SpotServe (2024) and similar systems extended these ideas even to latency-sensitive serving, migrating state between instances within the notice period[2]; for batch work the simpler row-level scheme suffices.

For the mathematician — why inference checkpoints are free and training's are not

A training run is a long chain: step \(k+1\) depends on the parameters after step \(k\), so the computation's dependency graph is a path, and losing the state at any point loses everything since the last saved vertex. Batch inference has a dependency graph with no edges between rows: it is an embarrassingly parallel map over a set. Its state is therefore a subset of a set—the completed rows—which grows monotonically and can be recorded incrementally at negligible cost. The Young–Daly trade-off between checkpoint cost and lost work (§7.5) disappears because the checkpoint cost per unit of work is essentially zero and the unit of loss is one row. RL rollouts sit in between: rows within a step are independent, but steps form a chain.

Drill 19.2 — Is spot worth it with a slow cold start?

A batch job runs on spot H100s at $1.00 per GPU-hour; committed capacity costs $2.50. Preemptions arrive on average every 90 minutes. Compare the effective cost per productive GPU-hour when a restart takes (a) 3 minutes and (b) 25 minutes. At what restart time does spot stop being cheaper?

Solution. Productive fraction \(=\text{MTBF}/(\text{MTBF}+t_{\text{restart}})\). (a) \(90/93=0.968\): $1.03 per productive hour. (b) \(90/115=0.783\): $1.28. Both beat $2.50. Spot stops paying when \(1.00\times(90+t_{\text{restart}})/90=2.50\), that is \(t_{\text{restart}}=135\) minutes—far beyond any reasonable cold start. The practical risks are different: spot capacity may be unavailable when the deadline nears, so deadline-bound jobs keep a committed or on-demand fallback and switch to it when the remaining work no longer fits in the remaining time at the observed spot rate.

19.6 The pipeline around the model

An offline job is more than a model call: rows are read from storage, parsed, perhaps rendered or cropped, tokenised, run through the model, parsed again, validated and written. Figure 19.5 shows the stages. The system's throughput is the minimum of the stages' throughputs, and in practice the GPU is often not the bottleneck: a pipeline that renders PDF pages or decodes images on a few CPU cores can leave expensive accelerators starved.

Figure 19.5 embodies four design rules. Scale stages independently. CPU preprocessing and GPU inference have different unit costs and different bottlenecks, so they run in separate worker pools whose sizes are chosen to match rates; data-processing frameworks built for this heterogeneous, streaming style of batch execution—Ray Data is the best-known open example[3]—replaced the older pattern of one process per GPU doing everything. Bound the queues. An unbounded queue between a fast reader and a slower model fills memory until the job crashes; a bounded queue makes the producer wait, which is backpressure, the same principle as the admission control of Chapter 11. Order by length. Grouping rows of similar length keeps the KV memory of §19.2 well packed and prefill padding low; with a deep queue and continuous batching, a finished sequence's slot is refilled at once, so the straggler problem that plagues step-synchronous work (§19.7) does not arise. Validate and retry rows, not jobs. A row whose output fails to parse, or trips a guard (Chapter 18), is retried a bounded number of times and then written to a dead-letter set for inspection; one bad row in two hundred million must never fail the job.

The sizing exercise is a chain of rate calculations. In the ticket job of §19.2, 50 GPUs prefill about 1.5 million tokens per second, some 6 MB of text: storage and tokenisation are trivial. Replace tickets with scanned pages that take 100 ms of CPU each to render and yield 1,000 tokens, and each GPU consumes 31 pages per second, needing about three cores of rendering per GPU, 150 cores for the fleet—still cheap, but only if someone provisions them. The habit of computing every stage's rate, and monitoring GPU utilisation as the signal that an upstream stage has fallen behind, is what separates a job that costs $1,000 from one that costs $5,000.

19.7 Rollout fleets: inference that feeds a trainer

The largest single class of offline inference is the generation of rollouts for reinforcement learning. Vol. I §25.7 and §26.7 analysed one step in detail: for an 8B policy on 64 H100s, 512 prompts with \(n_s=16\) samples each and a mean of 4,000 generated tokens come to \(3.3\times10^7\) tokens per step; generation takes about 200 seconds and training about 105, so two thirds of the step is inference, and more than half of the generation time is spent waiting for the longest rollouts. A training run of ten thousand such steps generates \(3.3\times10^{11}\) tokens—more than many products serve in a month. Here we take the infrastructure view: what kind of fleet produces those tokens? Figure 19.6 shows its parts.

Figure 19.6 distinguishes three fleets with different needs. The rollout engines are an inference fleet like any other and should be production engines (Vol. I §26.7), run at the throughput-optimal point of §19.2; with \(n_s\) samples per prompt, the shared prompt's KV is computed once. They are the elastic part: generation is row-parallel within a step, so rollout replicas can be added from spare or spot capacity and removed without harm, and a preempted replica loses only its in-flight rollouts. The trainer is the opposite: a tightly coupled job whose loss stalls the whole run, so it stays on committed capacity with checkpoints (§7.5). The environments are the part newcomers forget. For agentic tasks each rollout drives a sandbox (§17.3)—a code interpreter, a browser, a set of unit tests—so eight thousand concurrent rollouts need eight thousand sandboxes, whose start time and execution time enter the step directly; a verifier that takes thirty seconds per rollout on too few cores turns a GPU bottleneck into a CPU one.

Worked example — the environment fleet for a coding-agent RL step

Setting. The step of Vol. I §25.7—8,192 concurrent rollouts on 64 H100s, about 200 s of generation—now trains a coding agent. Each rollout makes 10 tool calls (running tests, executing snippets), each using 5 s of one CPU core, in a sandbox holding 0.5 GiB of memory.

CPU work. \(8{,}192\times10\times5\approx4.1\times10^5\) core-seconds per step. For the tools not to lengthen the 200-second generation phase, they must be spread over at least \(4.1\times10^5/200\approx2{,}050\) cores: about eleven 192-core servers, with \(8{,}192\times0.5\approx4\) TiB of sandbox memory among them.

If under-provisioned. With 256 cores the tool work alone takes \(4.1\times10^5/256\approx1{,}600\) s. The step grows from 300 s to nearly half an hour, and 64 H100s costing $160 per hour wait on $10 per hour of CPUs—with their KV caches held or reloaded throughout (§17.4).

Weight synchronisation. The updated 8B policy is 16 GB; relayed between nodes at 50 GB/s (a 400 Gb/s link), each hop takes about 0.3 s, and a tree reaches 64 engines in six hops, about 2 s—under 1% of the step. Reloading each engine from object storage at 2 GB/s would take 8 s for this model and over a minute for a 141 GB 70B policy, every step.

Lesson. In agentic RL the cheap fleet can stall the expensive one. Environment capacity is sized from tool seconds per rollout, exactly as the GPU fleet is sized from tokens.

Two couplings between the fleets create the distinctive problems. The first is weight synchronisation. After each update the engines must load the new policy—16 GB for the 8B model, hundreds of gigabytes for a large one. Reloading from object storage every few minutes would dominate the step, so weights move directly from trainer to engines over the cluster network, by the tree or chain broadcast of §5.5, or are updated in place when trainer and engine share GPUs; and every prefix cache in every engine is invalidated at each update, because KV computed by old weights is wrong for new ones. The second is staleness. A step-synchronous loop wastes most of its generation capacity on stragglers; an asynchronous loop—engines generating continuously, the trainer consuming from the trajectory store, as in the actor–learner architectures of earlier deep RL[4]—keeps every GPU busy, at the price that trajectories were generated by a policy \(n_{\text{stale}}\) updates old and must be corrected by importance ratios or discarded beyond a staleness limit (Vol. I §25.7). The trajectory store therefore records the policy version and the sampling log-probabilities with every rollout: without them the data cannot be used correctly.

The capacity-planning consequence closes the loop with §19.3. A lab's rollout demand is flexible in exactly the way batch demand is: it can be throttled, paused and resumed within minutes. Labs that both serve products and train models therefore treat rollout generation as the largest tenant of the trough—running it on the serving fleet at night, yielding to interactive traffic by day—so that a single pool of GPUs earns revenue at its peak and produces training data in its valley.

19.8 Operating offline work: evaluations, synthetic data and reproducibility

Offline jobs lack the alarms of online service—no user complains when an evaluation is quietly wrong—so their operational discipline must be designed in. Reproducibility comes first. An evaluation score or a synthetic dataset is only meaningful if it can be regenerated, so each job records the model's weight hash, the engine and its version, quantisation, sampling parameters and seeds, the prompt template and the dataset version. Even then, bit-identical outputs are not guaranteed across batch sizes, hardware and engine versions, because floating-point reductions are reordered (Vol. I §23.8); evaluations therefore report variation across seeds, and comparisons between checkpoints are made under identical configurations on the same fleet.

Result caching exploits the same determinism where it holds: keyed by the hash of model, prompt and parameters, a cache lets a re-run of an evaluation suite, or a pipeline restarted after a bug in a later stage, skip rows already computed. At temperature zero the saving is often large, because evaluation suites change slowly while checkpoints change daily—though each new checkpoint necessarily recomputes everything. Cost attribution matters because offline work is invisible: a tag on every job for team, project and purpose, and a weekly report of GPU-hours by tag, is the only way to learn that a forgotten nightly job consumes a tenth of the trough. Quality gates replace user feedback: sampled outputs are checked by validators, by a stronger judge model or by people before a synthetic dataset is used for training, because errors in generated data are amplified, not averaged out, by the model trained on them.

Finally, offline work has its own safety and governance. Batch APIs receive the same abuse attempts as interactive ones, with the difference that guards (Chapter 18) can run asynchronously over a whole file before any output is released, at batch prices. Data residency (§12.6) applies to batch files and their outputs, which constrains which regions' troughs a job may use. And evaluation sets must be protected from leaking into training data—a governance problem that no amount of infrastructure solves, but that good lineage records, the offline analogue of audit logs, make detectable.

Looking ahead

We now have every component of cloud AI infrastructure: buildings and power, accelerators and networks, storage, orchestration and scheduling, serving platforms, capacity and economics, the front door, regions, reliability and security, and the workloads beyond chat—multimodal, retrieval, agents, guardrails and batch. An interview does not ask for the components one at a time. It asks for a system: "design a global LLM API", "design a serverless GPU platform", "design the scheduler for a ten-thousand-GPU cluster". The skill it tests is assembling what you know, under time pressure, with numbers, and defending the trade-offs. Chapter 20 turns the book into that skill: an estimation toolkit, a method for the design interview, and worked case studies with the rubrics by which they are judged.

Chapter summary

  • Inference divides by deadline into interactive, asynchronous, batch and best-effort work; flexibility in time is a resource spent on larger batches, off-peak hours and cheaper machines.
  • Decode throughput is \(B\beta_{\text{eff}}/(W_{\text{bytes}}+B\,n_{\text{ctx}}s_{kv})\), rising until KV memory fills: Llama 3 8B on an H100 reaches ≈ 32k tokens/s at 500-token contexts (B ≈ 945) but ≈ 8k at 2,000 tokens. Context length, shared prefixes and prefill dominate batch cost.
  • 200 million 800-token classifications cost ≈ 1,040 GPU-hours with a cached instruction: ≈ 44 H100s for a day, ≈ $2,600 committed or ≈ $1,050 on spot.
  • Batch APIs (2024) charge about half because troughs are paid-for capacity: with online load averaging 55% and filling to 90%, a fleet absorbs 64% more work for free; batch is also the first load to shed.
  • Share GPUs by replica switching (slow) or in-engine harvesting (strict online priority, token-boundary preemption, capped batch occupancy and KV headroom); schedule batch jobs earliest-deadline-first and admit against conservative forecasts of spare capacity.
  • Batch inference suits spot capacity because rows are independent: checkpoints are completed-row sets, waste ≈ \(t_{\text{restart}}/(\text{MTBF}+t_{\text{restart}})\) (≈ 3%), given idempotent keyed outputs, small commits and fast cold starts.
  • Pipelines are limited by their slowest stage: scale CPU and GPU pools independently, bound queues for backpressure, order by length, and retry rows rather than jobs.
  • RL rollout fleets combine elastic inference engines, bursty CPU environments and a fixed trainer; weight broadcast, cache invalidation, stragglers and staleness are the system problems; rollouts are the natural largest tenant of the trough.
  • Offline operations need recorded configurations and seeds, result caches, cost attribution, quality gates, asynchronous guards and data lineage.

Warm-up Why is the batch API half price?

Online fleets are sized for the peak and average ~50–60% utilisation; trough GPU-hours are already paid for, so batch work there has near-zero marginal cost. Batch also runs more efficiently: maximum batch sizes, shared prefixes, no streaming, ~90% utilisation. The 24-hour window guarantees a full trough. Batch is also interruptible, acting as a reserve the provider can reclaim in seconds. Once batch demand exceeds the trough it needs its own GPUs, and the full cost at high utilisation is about half the interactive price.

Warm-up How does the optimisation objective change for offline inference?

From meeting TTFT/TPOT percentiles at minimum cost to minimising cost per token subject to a deadline. Consequences: run at the largest batch memory allows; choose when and where to run (troughs, cheap regions, spot); drop streaming; reorder rows for prefix sharing and length packing; tolerate and retry failures per row; trade model size and quantisation against validated quality.

Core Derive decode throughput versus batch size and say what limits it.

Step time = (W_bytes + B·n_ctx·s_kv)/β_eff: weights read once, every sequence's KV once. Throughput = B·β_eff/(W_bytes + B·n_ctx·s_kv); rises with B, saturating at β_eff/(n_ctx·s_kv). Limits: KV memory (B·n_ctx·s_kv ≤ HBM − weights), then compute π at very large B. Llama 3 8B/H100: 500-token contexts → B ≈ 945, ~32k tok/s; 2,000 tokens → B ≈ 236, ~8k tok/s. Context length is the lever.

Core Estimate the cost of classifying 200 million documents with an 8B model by tomorrow.

Per row 800 input (300 shared instruction + 500 doc), 50 output. Prefill ~31k tok/s per H100 (2N FLOPs/token at ~500 TFLOP/s); decode ~19k tok/s at B = 512. Naive: 160B/31k + 10B/19k ≈ 5.7M GPU-s ≈ 1,580 GPU-h. With instruction cached: 100B/31k + … ≈ 1,040 GPU-h. 24 h → ~44 GPUs (+margin). Cost ≈ $2,600 committed at $2.50/h, ≈ $1,050 spot. Check CPU stages, storage and validation are not bottlenecks.

Core How do you run batch jobs on production GPUs without hurting production?

Share engines with strict priority for online sequences; batch fills leftover slots and KV; preempt batch at token boundaries on online arrival (evict or offload KV, requeue with progress). Cap batch occupancy so online TPOT stays within target; bound batch prefill chunks; keep KV headroom so new online requests never wait. At fleet level, autoscaler shifts replicas between pools for the diurnal swing. Monitor online tail latency with and without batch; kill switch to pause batch. ConServe-style harvesting.

Core Why is batch inference a good fit for spot instances?

Work is independent rows; the checkpoint is the set of completed row IDs, nearly free to maintain. A preemption loses only in-flight rows plus restart time: waste ≈ t_restart/(MTBF + t_restart), e.g. 4 min / 124 min ≈ 3%, against 60%+ discounts. Requirements: idempotent outputs keyed by row ID, small commit units, fast cold starts (cached weights/images), use of preemption notices, and a committed fallback for deadlines. Training by contrast is a chain needing Young–Daly checkpoints.

Deep-dive Design admission control for a batch API with a 24-hour SLA.

Estimate each job's work (tokens → GPU-hours by model, using measured rates). Forecast spare capacity per hour per region (capacity × ceiling − online forecast) with uncertainty; use a conservative quantile. Order admitted jobs by deadline (EDF); a new job is feasible if for every deadline the cumulative work due does not exceed cumulative spare capacity. If not, quote a later completion, route to another region's trough (residency permitting), or reserve paid capacity. Per-customer quotas to prevent one job taking the trough; continuous re-planning as actual online load deviates; alarms when projected completion approaches the SLA.

Deep-dive In RL for reasoning models, where does the time go and how do systems fix it?

Generation dominates (about two thirds in the 8B example), and over half of generation is waiting for long-tail rollouts while GPUs decode at small batch. Fixes: asynchronous actor–learner with a trajectory store (bounded staleness, importance correction), over-sampling with early termination, partial rollouts, length curricula, production engines at maximum batch with shared-prompt KV for n_s samples; fast weight sync by broadcast or in-place update; enough CPU for environments/verifiers. Then training speed-ups matter.

Deep-dive What are the infrastructure parts of a rollout fleet and how does each scale?

Rollout engines: elastic GPU inference, row-parallel, spot-friendly, policy-version tagged. Environments: CPU sandboxes/tools/tests, one per concurrent rollout, bursty, need fast start (snapshots) and isolation. Trajectory store: tokens, log-probs, rewards, versions; decouples generation from training. Trainer: fixed, committed GPUs with checkpoints. Weight distribution: tree/chain broadcast each update; cache invalidation. Control: curriculum/task queue, staleness limits. Capacity: rollouts as the largest flexible tenant, run in the serving trough.

Design Design an offline pipeline to OCR and summarise one billion scanned pages.

Stages: list/read from object storage → CPU render/deskew → vision-language model for OCR (image tokens, Chapter 15) → summariser (smaller text model) → validation → keyed write. Compute each stage's rate; separate autoscaled pools; bounded queues. Model stage: maximum batch, shared instruction prefix, length bucketing, spot GPUs with row checkpoints and fast restart, committed fallback. Cascade: cheap OCR model first, escalate low-confidence pages. Idempotent outputs keyed by page ID, small commits, dead-letter set. Quality sampling by a judge model and humans. Cost tags; residency of data; throughput and GPU-utilisation dashboards; estimate total GPU-hours and deadline before starting.

Design Design an evaluation service that scores every new checkpoint on forty benchmarks.

Job spec pins weight hash, engine/version, quantisation, sampling params, seeds, templates, dataset versions. Scheduler runs benchmarks as batch jobs with priorities (release-blocking first), on trough or spot capacity with deadlines. Core Your batch job's GPUs show 40% utilisation. What do you check?

Upstream starvation: CPU preprocessing, tokenisation, storage reads, network—look at queue depth before the model stage. Batch size below memory limit (engine config, too few concurrent requests from the client). Long-context rows crowding KV. Output/validation stage backpressure. Row ordering causing padding. Stragglers if the job is step-synchronous. Small files and per-request overheads (HTTP per row instead of in-process batching). Fix the slowest stage; scale CPU pools; raise client concurrency.

Core How much batch work can a fleet absorb for free?

Integrate (ceiling − online load) over the day. With online peak at 80% and mean 55% of capacity and a 90% ceiling: spare averages 35% of the fleet → 0.35/0.55 = 64% more work. For 4,000 GPUs ≈ 33,600 GPU-h/day. Subtract headroom for forecast error and interference caps; account for model mix (spare GPUs must host the batch job's model, or pay switching time).

Warm-up What makes batch output writes safe under retries and preemption?

Stable row IDs; outputs keyed by ID so reprocessing overwrites; small atomic commits (write temp object then rename, or transactional append with offsets); a manifest of completed chunks as the checkpoint; bounded retries with dead-letter storage; deterministic chunking so workers do not overlap. Exactly-once effect from at-least-once processing plus idempotent writes.

Deep-dive Why are outputs not bit-reproducible across batch runs, and how do you handle it?

Floating-point addition is not associative; batch size, kernel choice, hardware, parallelism (TP degree) and engine version change reduction order, and tiny logit differences flip near-ties and then diverge. Sampling adds seeds and RNG streams tied to batch position. Handle by pinning configuration, using per-row seeds independent of batch composition, reporting variance across seeds, comparing checkpoints under identical setups, caching results by full configuration hash, and treating small score differences as noise unless significant.

Design A lab serves a product and trains with RL on the same 10,000 GPUs. How do you share them?

Three classes: online serving (priority, sized for peak with headroom), trainer (fixed committed slice), rollouts and batch (flexible). Rollout engines harvest serving capacity: in-engine if the policy and served model match, otherwise replica switching with fast weight load from local cache. Scheduler with quotas and preemption (§7.7); rollouts throttle by day and expand at night; the trainer consumes asynchronously from a trajectory store so varying rollout rates only change staleness, bounded by policy. Environment sandboxes on a CPU fleet. Weight broadcast per update. Kill switch returns everything to serving in an incident. Track GPU-hours by class to judge the split.
