Volume II · Part I · The Physical Cloud — Chapter 5

Storage, Weights and Cold Starts

Before a new replica can produce its first token it must obtain a machine, a container image of several gigabytes, and tens to hundreds of gigabytes of weights, and then initialise an engine that compiles kernels and captures graphs. Done naively this takes ten minutes or more, which makes autoscaling slow, failures expensive and scale-to-zero impossible. This chapter takes the cold start apart, derives how fast each piece can be made, and shows how storage tiers, file formats, streaming loaders, peer-to-peer distribution and snapshots bring it down to seconds.

Why this chapter

Volume I treated cold-start time as a parameter of autoscaling: in Vol. I §27.3 we argued that because a large replica took minutes to start, the autoscaler had to keep headroom for the demand growth that could occur during one cold start. We did not ask why it took minutes, or how much shorter it could be. The question matters more than it appears. Cold-start time determines how much idle capacity a fleet must hold (Chapter 9), how long a fleet runs degraded after a failure (Chapter 13), whether a platform can scale a rarely used model to zero and back (Chapter 8), and how quickly a new model version can be rolled out. A fleet whose replicas start in thirty seconds instead of ten minutes can run with far less headroom, and headroom is GPUs.

The cold start is also a good example of a systems problem with a quantitative core. Each of its steps moves bytes from one tier of a storage hierarchy to another, and each tier has a bandwidth, a capacity and a cost. The design question is which bytes should be where, and the answer follows from the same kind of reasoning as Volume I's analysis of HBM and caches—only the tiers are now object storage, network file systems, local disks, host memory, and the HBM of other GPUs.

We begin by timing each step of a naive cold start (§5.1). We then survey where weights can live and how fast each tier delivers them (§5.2), the file formats in which they are stored and why the format matters for both speed and security (§5.3), and how to stream bytes from storage into GPU memory at the hardware's limit (§5.4). We analyse the distribution of weights to many new replicas at once, including peer-to-peer and chain broadcast (§5.5), the container image (§5.6), and engine initialisation and snapshotting (§5.7). We end with complete cold-start budgets for the three running models (§5.8).

Learning objectives
  1. List the steps of a replica's cold start and estimate the time of each from sizes and bandwidths.
  2. Describe the storage tiers for model weights (object storage, shared file systems, local NVMe, host DRAM, peer HBM) and model their throughput.
  3. Explain the differences between pickle checkpoints, safetensors, GGUF and compiled engine files, including the security risk of pickle.
  4. Design a loader that streams weights into GPU memory at the bandwidth of the slowest link, and say where GPUDirect Storage helps.
  5. Derive the time to distribute weights to many replicas by a central store, peer-to-peer swarming and pipelined chain broadcast, including the optimal chunk size.
  6. Explain lazy image pulling, compilation caches, sleep modes and process snapshots, and build a cold-start budget for a given model.

Uses: weight and KV sizes (Vol. I §2.10, §3.4), autoscaling (Vol. I §27.3), engine internals (Vol. I Chapter 12), the α–β model (Vol. I §17.2) and Chapters 3–4 of this volume.

5.1 Anatomy of a cold start

Suppose Atlas's autoscaler decides at 08:00 that the Llama 3 70B tier needs another replica. What must happen before that replica serves its first request? Figure 5.1 lays out the steps of a straightforward implementation on a cloud Kubernetes cluster, with typical durations, and the same steps after the optimisations of this chapter.

Read Figure 5.1 from left to right. First, the cluster may have no idle GPU node, so the cluster autoscaler must ask the cloud for one: the cloud finds capacity, boots a VM or bare-metal server, starts its operating system, installs or verifies the GPU driver, and joins it to the cluster—three to five minutes is typical, longer for bare metal, and it may fail outright if the region has no capacity (Chapter 9). Second, the cluster scheduler places the replica's pod on the node (Chapter 6), which takes seconds. Third, the node pulls the container image: CUDA libraries, PyTorch, the inference engine and its dependencies, often 10–20 GB compressed, from a registry, at a few hundred megabytes per second, so one to three minutes. Fourth, the engine loads the weights—about 70 GB for Llama 3 70B in FP8—from wherever they are stored. Fifth, the engine initialises: it creates NCCL communicators among its eight GPUs, allocates the KV-cache pool, compiles or loads kernels, runs torch.compile, captures CUDA graphs for many batch sizes (Vol. I §7.7), and profiles memory. Sixth, it warms up with a few requests and passes health checks, after which the router starts sending it traffic.

The total, which we can write as

\[ t_{\text{cold}}=t_{\text{node}}+t_{\text{sched}}+t_{\text{image}}+t_{\text{weights}}+t_{\text{init}}+t_{\text{warm}}, \]

is ten to fifteen minutes in the naive case. Two features of the sum guide everything that follows. Its largest terms are obtaining capacity and moving bytes, not computation. And its terms are not inherently sequential: an image can be pulled while weights are fetched, weights can be loaded while kernels compile, and the node can exist before it is needed. The rest of this chapter takes the byte-moving terms one at a time; Chapter 9 deals with \(t_{\text{node}}\) through warm pools and capacity planning.

5.2 Where weights live: the storage hierarchy

A model's weights have a canonical home and several caches. The canonical home is almost always object storage: Amazon S3, Google Cloud Storage, Azure Blob Storage or an S3-compatible service. Object storage keeps immutable objects (files) addressed by a bucket and a key, replicated across devices and often across zones, with effectively unlimited capacity at a few cents per gigabyte-month. It is accessed over HTTP from the front-end network. Its performance model is unusual and worth understanding: a single request (a GET of an object or of a byte range of one) is served at perhaps 50–100 MB/s, but the service handles enormous numbers of requests in parallel, so the throughput a client sees is roughly

\[ \beta_{\text{obj}}\approx\min\bigl(n_{\text{conn}}\,\beta_{\text{conn}},\ \beta_{\text{NIC}},\ \beta_{\text{svc}}\bigr), \]

where \(n_{\text{conn}}\) is the number of concurrent range requests, \(\beta_{\text{conn}}\) the throughput of each, \(\beta_{\text{NIC}}\) the client's network bandwidth, and \(\beta_{\text{svc}}\) whatever limit the service imposes for that bucket or key prefix (S3, for example, documents per-prefix request-rate limits of several thousand GETs per second). A loader that reads a 70 GB checkpoint with one sequential stream gets 100 MB/s and takes twelve minutes; the same loader with 64 parallel range requests gets about 5 GB/s and takes fourteen seconds. Parallelism is the first and largest optimisation.

Between object storage and the GPU sit faster tiers, shown in Figure 5.2. A shared file system—a parallel file system such as Lustre (offered as Amazon FSx for Lustre), or a high-performance NAS such as WEKA, VAST or Google's Filestore and Managed Lustre—presents a POSIX file interface backed by many storage servers, delivering tens of gigabytes per second to a cluster, at a much higher price per gigabyte than object storage. Local NVMe drives in each GPU server deliver 7–14 GB/s each, so a server with eight drives in a RAID-0 stripe can read at 25–50 GB/s; capacity is tens of terabytes per server, enough to cache many models. Host DRAM, 1–2 TB per server, can hold one or two large models in the operating system's page cache or in a pinned buffer, and transfers to the GPUs over PCIe Gen5 at roughly 50 GB/s per GPU, several hundred GB/s per server. And the HBM of other GPUs—replicas that already have the weights loaded—can supply them over NVLink or the back-end RDMA network at 50–900 GB/s per GPU.

The tiers also differ in cost, though less than one might expect from their speeds. Object storage costs roughly two cents per gigabyte-month, so keeping a terabyte of model versions costs about $20 a month. Local NVMe and host DRAM are already paid for as part of the GPU server, so using them as caches is essentially free. High-performance shared file systems cost perhaps ten times more per gigabyte than object storage and are the only tier whose cost needs justifying. Next to a GPU fleet that costs millions of dollars a month, every caching tier is cheap; the real constraint is capacity on the faster tiers and the engineering needed to keep them consistent.

Figure 5.2 is the familiar shape of a memory hierarchy, and the same reasoning applies. If a fraction \(p_i\) of cold starts find the weights first in tier \(i\), whose effective bandwidth is \(\beta_i\), the expected weight-loading time for a model of \(W_{\text{bytes}}=Nb_w\) bytes is \(\mathbb E[t_{\text{weights}}]=\sum_ip_iW_{\text{bytes}}/\beta_i\). Because the bandwidths span three orders of magnitude, the expectation is dominated by the rare loads from the slowest tier unless its hit probability is driven very low. A fleet that caches its top models on every node's NVMe, and falls back to object storage only for rarely used ones, gets the NVMe time for almost every cold start. Figure 5.3 shows load time against model size for each tier.

Figure 5.3 makes the economics of caching concrete. For an 8B model, even object storage delivers the weights in a few seconds, and caching hardly matters. For a 70B model, the difference between object storage and local NVMe is the difference between a quarter-minute and three seconds. For DeepSeek-V3 in FP8, object storage takes over two minutes per server even with good parallelism—and a DeepSeek-V3 replica spans many servers, all loading at once—while peers can supply it in a few seconds. The faster tiers cost money (NVMe and DRAM are already in the servers; a shared file system is expensive), so the design question is which models to cache where. Before we answer it, we should look at what is actually stored, because the file format determines how efficiently the bytes can be read.

5.3 File formats: pickle, safetensors, GGUF and engines

For years the default way to save a PyTorch model was torch.save, which serialises the model's state dictionary with Python's pickle format into a .bin or .pt file. Pickle is a general object-serialisation format: a pickle file is a small program for a stack-based virtual machine that reconstructs Python objects, and that program may call arbitrary Python functions while it runs. Loading an untrusted pickle file can therefore execute arbitrary code on the loading machine. This is not a hypothetical concern: researchers and security firms have repeatedly found malicious pickle files uploaded to public model hubs. For an inference platform that loads models from customers or the internet, pickle is a remote-code-execution vulnerability by design (Chapter 14 returns to the model supply chain).

Pickle is also slow to load: its tensors are reconstructed by the Python interpreter, often with extra copies, and a file must generally be read in full and in order. In 2022 Hugging Face introduced safetensors, a deliberately simple format that fixes both problems[1]. Figure 5.4 shows its layout: an 8-byte integer giving the length of a header; a JSON header listing, for each tensor, its name, data type, shape and byte offsets; and then the raw tensor data, contiguous and aligned. There is no code to execute—parsing the header is parsing JSON—and because each tensor's location is known from the header, a loader can memory-map the file and read any tensor, or any slice of one, without touching the rest. An independent security audit of the format was published in 2023, and safetensors has since become the standard distribution format for open-weight models.

Figure 5.4's design has a consequence for distributed serving that is easy to miss. A replica with tensor parallelism of degree \(n_{\text{TP}}\) gives each GPU a slice of each weight matrix—a block of rows or columns (Vol. I §18.2). With a pickle file, each rank must deserialise the whole checkpoint and discard \((n_{\text{TP}}-1)/n_{\text{TP}}\) of it, so the eight ranks of a TP8 replica together read eight times the model's size. With safetensors and row-sharded tensors, each rank can read exactly the byte ranges of its slice; column slices are strided but can still be read selectively, or the checkpoint can be pre-sharded—re-saved once in the serving layout, one file per rank—so that each rank reads one contiguous file of \(W_{\text{bytes}}/n_{\text{TP}}\) bytes. Pre-sharding a 140 GB BF16 checkpoint for TP8 cuts the bytes each rank reads from 140 GB to 17.5 GB.

Two other formats are common. GGUF, the format of llama.cpp (Vol. I Chapter 29), packs a model's architecture metadata, tokenizer and quantised tensors (in its many block-quantisation formats) into a single memory-mappable file, designed for local and edge inference. Compiled engine files, such as TensorRT-LLM engines, store not only weights but kernels and execution plans specialised to one GPU type, parallel layout and set of maximum shapes; they skip compilation at start-up but must be rebuilt for each hardware and configuration change. The general lesson is that the serving format should be chosen for loading, not for training: what was convenient to save is rarely what is fastest to load.

5.4 Reading fast: streaming weights into GPU memory

Once the weights are in a loadable format on some tier, they must travel to HBM. The path, for a load from object storage or NVMe, is storage → network or NVMe controller → host DRAM → PCIe → GPU HBM. A naive loader runs these hops sequentially: download the files to local disk, then read each tensor into host memory, then copy it to the GPU, waiting for each stage to finish before starting the next. The time is the sum of the stages. A streaming loader pipelines them, so that while one chunk is crossing PCIe, the next is being read from storage; its time approaches the maximum of the stages, that is, the size divided by the slowest link's bandwidth.

For the mathematician — pipelining turns a sum into a maximum

Let a transfer of \(W_{\text{bytes}}\) bytes pass through \(n_s\) stages with bandwidths \(\beta_1,\dots,\beta_{n_s}\). Done stage by stage, the time is \(\sum_jW_{\text{bytes}}/\beta_j\). Split the data into chunks of \(c\) bytes and let each stage work on chunk \(i+1\) while the next stage works on chunk \(i\). Chunk \(i\) leaves the last stage at time \(\sum_jc/\beta_j+(i-1)\max_jc/\beta_j\), so all \(W_{\text{bytes}}/c\) chunks are done at \(\sum_jc/\beta_j+(W_{\text{bytes}}/c-1)\max_jc/\beta_j\approx W_{\text{bytes}}/\min_j\beta_j\) when \(c\ll W_{\text{bytes}}\). The pipeline's throughput is the bottleneck stage's bandwidth, and the other stages cost only a fill-and-drain latency proportional to \(c\). This is the same algebra as the pipeline-parallel bubble of Vol. I §18.4, and it reappears in the chain broadcast of §5.5.

Several open-source loaders implement streaming for LLM weights. The Run:ai Model Streamer reads safetensors files from object storage or file systems with many concurrent range requests and copies tensors into GPU memory as they arrive, without first writing them to disk; vLLM integrates it as a load format. CoreWeave's Tensorizer serialises models into a format designed for streaming over HTTP or from S3. Other loaders read safetensors directly from NVMe into GPU memory with parallel I/O. All exploit the same two ideas: many concurrent reads to saturate the source, and overlap of reading and copying so that the slowest link sets the pace.

Which link is the slowest? PCIe rarely is: each GPU has its own PCIe Gen5 x16 link of about 64 GB/s per direction, roughly 50 GB/s achievable with pinned (page-locked) host buffers, so eight GPUs can absorb several hundred GB/s in aggregate if the host's memory and PCIe topology allow it. The front-end NIC, at 100–400 Gb/s (12.5–50 GB/s), often is, as is the storage service's per-object or per-prefix throughput. Local NVMe at 25–50 GB/s per server is often the binding link for cached loads. GPUDirect Storage (GDS) removes a hop for NVMe and some network file systems: the storage device writes directly into GPU memory by DMA, bypassing the host DRAM bounce buffer, which saves CPU and memory bandwidth and helps most when the host's memory system, not the drive, is the limit.

Worked example — loading Llama 3 70B onto eight GPUs

Setup. Llama 3 70B in FP8 (70.6 GB), TP8, on an H100 instance with a 200 Gb/s front-end NIC (25 GB/s), eight local NVMe drives (about 25 GB/s together after RAID overhead) and PCIe Gen5 to each GPU (about 50 GB/s each with pinned buffers).

Naive. One stream downloads the whole checkpoint (not pre-sharded) from object storage at 100 MB/s to local disk: about 12 minutes. Then each of eight ranks reads the full 70.6 GB from disk and keeps an eighth: 565 GB of disk reads at 25 GB/s, about 23 s. Copy to GPUs: under 1 s. Total about 12.5 minutes.

Parallel streaming from object storage. A streaming loader with 64 concurrent range requests at about 80 MB/s each reaches about 5 GB/s, and with a pre-sharded checkpoint each rank streams only its 8.8 GB slice. Aggregate 70.6 GB at 5 GB/s: about 14 s. If the bucket and NIC allow more concurrency, the 25 GB/s NIC becomes the limit: about 3 s.

From the local NVMe cache. 70.6 GB at 25 GB/s: about 2.8 s, pipelined to the GPUs.

From host DRAM (e.g. after a process restart, with weights still in the page cache): eight parallel PCIe streams of 8.8 GB at about 50 GB/s each: about 0.2 s, in practice perhaps a second with allocation overheads.

Lesson. Format and parallelism take the load from twelve minutes to fifteen seconds; caching takes it to three; keeping the weights in host memory takes it to one. The remaining cold-start time is elsewhere.

5.5 Caching tiers and peer-to-peer distribution

Loading one replica quickly is a matter of bandwidth. Loading many replicas at once is a matter of contention, and it is the case that matters for autoscaling and recovery. When Atlas's morning ramp requires 170 new 70B replicas within half an hour, or when a rollout restarts every replica of a model with new weights, or when a zone fails and its replicas must be recreated elsewhere, hundreds of servers ask for the same tens of gigabytes at the same moment. A central store that delivers 5 GB/s to one client may deliver only its aggregate limit—perhaps 50–100 GB/s for one bucket and prefix—to all of them together, and that limit is shared. Two hundred servers each needing 70 GB from a store limited to 50 GB/s in aggregate wait \(200\times70/50=280\) seconds, however fast each server's NIC is.

The remedy is to stop treating the central store as the only source. Once one server has the weights, it can serve them to others, and those to more. There are three standard patterns, sketched in Figure 5.5. In a star, every server fetches from the central store; time grows linearly with the number of servers once the store's aggregate limit binds. In a swarm, as in BitTorrent or container-distribution systems such as Uber's Kraken and the CNCF project Dragonfly, the weights are split into chunks and servers exchange chunks with each other, so that every server's upload bandwidth contributes; time grows only logarithmically. In a chain or tree broadcast over the back-end RDMA network, servers are arranged in a pipeline (or a tree of pipelines) and each forwards chunks to the next as soon as it receives them; with pipelining, the time is almost independent of the number of servers.

Proposition 5.1 — Pipelined chain broadcast

A source holds \(W_{\text{bytes}}\) bytes and \(n\) receivers are arranged in a chain, each link having bandwidth \(\beta\) and per-chunk latency \(\alpha\). If the data are sent in chunks of \(c\) bytes and each receiver forwards a chunk as soon as it has received it, the last receiver finishes at

\[ t_{\text{chain}}(c)=\Bigl(\frac{W}{c}+n-1\Bigr)\Bigl(\alpha+\frac{c}{\beta}\Bigr), \]

which is minimised at \(c^*=\sqrt{W\alpha\beta/(n-1)}\), giving \(t^*_{\text{chain}}=\bigl(\sqrt{W/\beta}+\sqrt{(n-1)\alpha}\bigr)^2\).

Proof. Each chunk takes \(\alpha+c/\beta\) per hop. The last chunk leaves the source after \(W_{\text{bytes}}/c\) chunk times and needs \(n-1\) further hops to reach the last receiver, giving the product. Writing \(f(c)=(W_{\text{bytes}}/c+n-1)(\alpha+c/\beta)\), \(f'(c)=-W_{\text{bytes}}\alpha/c^2+(n-1)/\beta\), which vanishes at \(c^*\). Substituting, \(f(c^*)=W_{\text{bytes}}/\beta+(n-1)\alpha+2\sqrt{W\alpha(n-1)/\beta}=(\sqrt{W/\beta}+\sqrt{(n-1)\alpha})^2\). \(\square\)

Proposition 5.1 is the same trade-off as Vol. I's α–β analysis of collectives: small chunks fill the pipeline quickly but pay the per-chunk latency many times; large chunks pay it rarely but leave the pipeline empty for longer. For realistic numbers the second term is tiny. With \(W_{\text{bytes}}=70\) GB, \(\beta=300\) GB/s per server over eight RDMA NICs, \(\alpha=50\) µs and \(n=255\) receivers, \(c^*\approx\sqrt{70\times10^9\times5\times10^{-5}\times3\times10^{11}/254}\approx64\) MB and \(t^*\approx(0.483+0.113)^2\approx0.36\) s. Every one of 255 servers receives the full 70 GB in about a third of a second—the time to deliver it to one server, plus a few milliseconds. Figure 5.6 compares the three patterns as the number of new replicas grows.

Figure 5.6 explains why large serving platforms distribute weights peer to peer. With a central store, scaling from 16 to 256 new replicas makes each wait sixteen times longer; with peers, it makes almost no difference. The chain over the back-end is fastest but needs the source and the receivers on the same RDMA fabric and a coordinator to build the chain; the swarm works over the ordinary front-end network and tolerates churn. Research systems have pushed the idea further. ServerlessLLM (2024) loads checkpoints through a multi-tier cache (GPU, DRAM, SSD) with a loading-optimised format and chooses servers by where weights are already cached, reporting large reductions in start-up latency[2]; later systems multicast parameters over the RDMA network and even let a new replica begin serving before it has all of its layers, by executing early layers locally and late layers on a peer until the copy completes.

Caching policy decides which models are present on which tier. A sensible default for a fleet like Atlas is: every model in active service has its weights on the NVMe of every node in its pool, written by a background agent when the model is registered; host DRAM keeps the weights of the models currently loaded on the node, so that a crashed engine can restart from memory; the central object store is used only for new models and cache misses, and then seeds a swarm. Because NVMe capacity per node is tens of terabytes, even a large catalogue of models fits, and the cost of caching is small next to the GPU time it saves. Weights, however, are only one of the two big downloads of a cold start.

Drill 5.1 — Atlas's morning ramp

Between 07:30 and 09:00 UTC, Atlas's 70B tier grows from about 140 to 311 replicas (eight GPUs each). If weights come from object storage with a 50 GB/s aggregate limit, how long does the weight loading of the 171 new replicas take in total, and how does that compare with the swarm and with chain broadcast from existing replicas? What does this imply for autoscaling headroom?

Solution. 171 replicas × 70.6 GB ≈ 12.1 TB. Star: if the replicas start at once, \(12{,}100/50\approx242\) s for the last one; spread over 90 minutes at about two replicas per minute, the store is not saturated and each takes about 14 s. Swarm: about 3 s each regardless of concurrency. Chain from running replicas: under a second. The difference matters most for bursts and recoveries: if a zone with 60 replicas fails, re-creating them from object storage takes \(60\times70.6/50\approx85\) s of weight loading alone, versus seconds with peers. Faster recovery means less spare capacity must be held to meet the SLO during it (Chapter 13), and faster scale-up lets the autoscaler hold less headroom for the ramp (Vol. I §27.3).

5.6 Container images: the other big download

An inference replica runs inside a container (Chapter 6 explains what that is): a process with its own view of the file system, populated from an image. An image is a stack of read-only layers, each a compressed archive of files, identified by a cryptographic hash of its contents and stored in a registry. Starting a container conventionally requires downloading and decompressing every layer not already on the node. LLM serving images are large: a CUDA runtime and its math libraries, cuDNN, NCCL, PyTorch, the inference engine, Triton and FlashInfer kernels, and Python dependencies easily total 10–20 GB uncompressed, several gigabytes compressed. Pulled at a few hundred megabytes per second and decompressed on a few CPU cores, that is one to three minutes.

Most of those bytes are never read. Harter and colleagues measured container start-up in 2016 and found that pulling images accounted for 76% of container start time, while only 6.4% of the pulled data was actually read during start-up[3]. The observation led to lazy pulling: start the container as soon as its file-system metadata is available, and fetch file contents on demand when the process first reads them. Formats and snapshotters that support this include eStargz (seekable compressed layers), Nydus, AWS's SOCI (seekable OCI indexes that work with unmodified images), and the image-streaming features of managed Kubernetes services. With lazy pulling the image term of the cold start shrinks to seconds, though first accesses to large libraries then pay a small latency during initialisation.

Three simpler techniques also help, and are often combined with lazy pulling. Pre-pulling the serving image onto every node of a GPU pool, by a background process or by baking it into the node's machine image, removes the pull entirely for the common case. Layer discipline—putting the large, rarely changing CUDA and framework layers at the bottom of the image and the frequently changing engine code at the top—means that a new engine version changes only a small top layer, so only that layer must be pulled. And keeping weights out of the image lets images and models change independently and lets weights use the specialised tiers of §5.5; baking weights into images makes every model update a multi-gigabyte image push and pull.

The idea that makes container layers cacheable—naming each artefact by a cryptographic hash of its contents—applies equally to model weights, and mature platforms adopt it. A model registry records, for each model version, the content hashes of its shard files, its serving configuration (precision, parallel layout, tokenizer, chat template, maximum context) and its provenance (training run, evaluation results, approvals). Deployments refer to a model by its immutable version or digest rather than by a mutable name such as "latest", so that every replica of a deployment is guaranteed to load the same bytes, caches can be keyed by digest and shared safely across tenants who use the same base model, and a rollback is simply a reference to an older digest whose files are probably still cached. Loaders verify each shard's hash after download, which catches corrupted transfers and tampering at the same time.

Content addressing also simplifies the cache invalidation problem that plagues every caching system. A cache keyed by digest never needs invalidation: a new model version has a new digest and therefore new cache entries, and old entries are evicted by ordinary LRU when space runs low. The only mutable state is the mapping from deployment to digest, which lives in the control plane (Chapter 8) and changes only through a rollout. This is the same separation of mutable references from immutable content that version-control systems such as Git use, and for the same reasons.

Drill 5.2 — Pulling an image onto 500 nodes

A serving image is 18 GB uncompressed and 7 GB compressed. A node pulls from the registry at 500 MB/s and decompresses at about 600 MB/s of output using a few cores. (a) How long does a full pull take on one node? (b) With lazy pulling, start-up reads 6.4% of the image; how long is the image step? (c) A new image version must reach 500 nodes; the registry serves 20 GB/s in aggregate. How long does a simultaneous full pull take, and what would you do instead?

Solution. (a) Download 7 GB at 0.5 GB/s is 14 s; decompressing 18 GB at 0.6 GB/s is 30 s; if pipelined, the pull takes about 30 s, sequentially about 44 s—and real pulls often take longer because layers are fetched and unpacked one at a time. (b) About 1.2 GB of uncompressed data, fetched on demand: a few seconds, plus latency on first access to each file. (c) 500 × 7 GB = 3.5 TB at 20 GB/s is 175 s for the last node, during which every node competes. Instead: pre-pull in the background before the rollout, use a regional pull-through mirror or a peer-to-peer distribution layer (the swarm of §5.5 works for image layers too), and structure layers so that only a small top layer changes between versions.

5.7 Initialisation, compilation caches and snapshots

With the image and weights in place, the engine still has to initialise, and modern engines do a lot at start-up because it makes them faster later. Creating NCCL communicators for tensor parallelism takes seconds within a server and longer across servers. Allocating and initialising the KV-cache pool is fast, but profiling memory to decide its size runs a dummy forward pass at the largest batch. JIT-compiled kernels—Triton kernels, FlashInfer's attention variants, torch.compile's generated code—may be compiled on first use, and autotuning tries several configurations of each kernel to find the fastest. CUDA graph capture (Vol. I §7.7) records the decode step for each of dozens of batch sizes. Together, these can take from tens of seconds to several minutes, especially for large models with many layer types.

The cure is to do the work once and reuse it. Compilation and autotuning results are deterministic functions of the model, engine version, GPU type and configuration, so they can be cached—written to a persistent directory or a shared store keyed by those inputs—and loaded on subsequent starts; vLLM, SGLang and PyTorch all support caches for compiled artefacts. CUDA graph capture can be limited to the batch sizes that matter, or deferred until traffic needs them. Within a running process, the cheapest cold start is the one that never happens: an engine can release its GPU memory while keeping its weights in host memory and its compiled state alive, and resume in seconds. vLLM calls this sleep mode; it is useful when GPUs are time-shared between models (several models on one pool, only some active) and between inference and training (reinforcement-learning systems that alternate rollouts and updates, Chapter 19).

The most complete form of reuse is a process snapshot: freeze a fully initialised engine—host memory, GPU memory, open files—to storage, and restore it on a new machine, skipping every step after the image pull. CPU process checkpointing has existed for years (CRIU on Linux); NVIDIA released a cuda-checkpoint utility in 2024 that makes a CUDA process's GPU state checkpointable, and some serverless GPU platforms restore snapshots of initialised engines to start replicas in seconds. Snapshots have caveats—they are tied to GPU type and driver version, they contain the weights (so they are large, and must be secured like the weights), and restoring multi-GPU communicators is delicate—but they turn \(t_{\text{init}}\) into a load of bytes, which the techniques of §5.4–5.5 make fast.

What a faster cold start buys can be quantified with the headroom model of Vol. I §27.3. If demand can grow at a rate \(\dot\lambda\) during a ramp, an autoscaler that reacts after a cold start of duration \(t_{\text{cold}}\) must hold enough spare capacity to absorb \(\dot\lambda\,t_{\text{cold}}\) of growth. Cutting \(t_{\text{cold}}\) from fifteen minutes to thirty-five seconds cuts that headroom by a factor of about 25. For a recovery from the loss of a zone, the period of degraded service shrinks in the same ratio, and with it the spare capacity needed to meet the availability target. In both cases the saving is measured in GPUs, which is why the unglamorous engineering of this chapter pays for itself many times over.

Worked example — headroom saved by a faster cold start

Setup. Atlas's 70B tier ramps from 140 to 311 replicas over 90 minutes each morning, roughly linearly: about 1.9 replicas' worth of demand per minute. The autoscaler adds replicas when utilisation exceeds its target, and a new replica serves traffic only after \(t_{\text{cold}}\).

Naive, \(t_{\text{cold}}=15\) min. During one cold start demand grows by about \(1.9\times15\approx29\) replicas' worth, so the autoscaler must hold about 29 replicas (232 GPUs) of headroom throughout the ramp to avoid breaching the SLO.

Optimised, \(t_{\text{cold}}\approx35\) s. Growth during one cold start is about 1.1 replicas' worth: headroom of one or two replicas (8–16 GPUs).

Value. About 220 GPUs fewer held idle during the ramp. If headroom is held only during the ramp (90 minutes a day) the saving is modest; but fleets that cannot scale quickly usually keep the headroom all day, and then 220 H100s at $2.50 per GPU-hour are worth about $4.8 million a year—for a single tier.

Part I has built the physical cloud from the bottom up: power and cooling (Chapter 2), accelerators as products (Chapter 3), the networks that join them (Chapter 4), and the storage from which weights and images reach them (this chapter). Throughout we have spoken of "starting a replica" on "a node" as if something decided where each replica should go and kept it running. That something is the orchestration layer: containers that package an engine and its dependencies, and a cluster manager—usually Kubernetes—that places them on machines, gives them GPUs, restarts them when they fail and scales them as demand changes. Chapter summary

  • A cold start is \(t_{\text{node}}+t_{\text{sched}}+t_{\text{image}}+t_{\text{weights}}+t_{\text{init}}+t_{\text{warm}}\); naively 10–15 minutes for a 70B replica, dominated by obtaining capacity and moving bytes.
  • Weights live canonically in object storage, whose throughput is \(\min(n_{\text{conn}}\beta_{\text{conn}},\beta_{\text{NIC}},\beta_{\text{svc}})\): parallel range reads are essential. Faster tiers: shared file systems, local NVMe (25–50 GB/s per server), host DRAM, and peer HBM over RDMA.
  • Pickle checkpoints can execute arbitrary code on load; safetensors (JSON header plus raw aligned bytes) is safe, memory-mappable and supports selective reads. Pre-sharding for the serving layout cuts per-rank I/O by \(n_{\text{TP}}\).
  • Streaming loaders pipeline storage, network, PCIe and HBM so time approaches size divided by the slowest link; PCIe (≈ 50 GB/s per GPU) rarely binds; GPUDirect Storage removes the host bounce buffer.
  • Many simultaneous loads contend for a central store; swarms add every server's upload; pipelined chain broadcast takes \((W_{\text{bytes}}/c+n-1)(\alpha+c/\beta)\), optimal \(c^*=\sqrt{W\alpha\beta/(n-1)}\), nearly independent of \(n\).
  • Container images are 10–20 GB but only a few percent is read at start-up: lazy pulling, pre-pulling and layer discipline remove most of \(t_{\text{image}}\); keep weights out of images.
  • Engine initialisation (communicators, compilation, autotuning, CUDA graphs) is cut by persistent compilation caches, limited graph capture, sleep modes and process snapshots.
  • Optimised cold starts are about 20 s (8B), 35 s (70B) and 75 s (DeepSeek-V3) on warm nodes; faster cold starts reduce autoscaling headroom and recovery capacity in proportion.

Warm-up Walk through what happens when a new LLM replica starts, with rough times.

Warm-up Why did the ecosystem move from pickle checkpoints to safetensors?

Security: unpickling executes a program that can call arbitrary Python callables, so loading an untrusted checkpoint can run attacker code; malicious pickles were found on model hubs. Performance: pickle reconstructs tensors through the interpreter, often with copies, and generally needs reading the whole file. Safetensors is an 8-byte header length, a JSON table of tensor names, dtypes, shapes and offsets, and raw aligned bytes—no code, memory-mappable, zero-copy, supporting selective reads of tensors or row ranges, which enables parallel and sharded loading. It was audited in 2023 and is now the default distribution format.

Warm-up What is lazy image pulling and why does it work?

Container images are stacks of compressed layers; conventionally all must be downloaded and unpacked before start. Measurements show that pulling dominates start time while only a few percent of the data is read during start-up (6.4% in Harter et al. 2016). Lazy pulling starts the container once file-system metadata is available and fetches file contents on demand (seekable formats like eStargz, Nydus, SOCI indexes, cloud image streaming). The image step drops from minutes to seconds; the cost is some latency on first access to files, which pre-fetching of known-hot files mitigates.

Core How fast can you load Llama 3 70B onto an 8-GPU node, and what limits it?

70.6 GB in FP8. Path: source → NIC or NVMe → host DRAM → PCIe → HBM. PCIe gives about 50 GB/s per GPU (8 × 50 = 400 GB/s), so it is rarely the limit. From object storage, one stream at 100 MB/s takes 12 min; 64 parallel range reads at about 80 MB/s each give 5 GB/s, about 14 s; higher concurrency is capped by the front-end NIC (200 Gb/s = 25 GB/s, about 3 s) or by the bucket's throughput. From local NVMe RAID-0 (about 25 GB/s): about 3 s. From host DRAM (process restart): under a second. From peers over RDMA (8 × 50 GB/s): about 0.25 s. Use a pre-sharded safetensors checkpoint so each TP rank reads only its 8.8 GB, and a streaming loader that overlaps reads and copies.

Core 200 replicas must start at once after a zone failure. How do you get them weights quickly?

A central store limited to, say, 50 GB/s aggregate would take \(200\times70/50=280\) s for a 70B model, regardless of NIC speed. Options: (1) node-local NVMe caches pre-populated for all active models (each replica loads at 25 GB/s locally, no contention); (2) peer-to-peer swarm (chunks exchanged among servers; total supply grows with servers; time ≈ W/β + O(log n) chunks); (3) pipelined chain or tree broadcast over the back-end RDMA from running replicas in other zones/pools (time ≈ (W + (n−1)c)/β, under a second for 70 GB at 300 GB/s per server). Combine with pre-pulled images and cached compilation. Also rate-limit and prioritise the most critical models, and make sure caches and sources are not in the failed zone.

Core Derive the completion time of a pipelined chain broadcast and its optimal chunk size.

\(n\) receivers in a chain, per-hop chunk time \(\alpha+c/\beta\). The last of \(W_{\text{bytes}}/c\) chunks leaves the source after \(W_{\text{bytes}}/c\) chunk times and needs \(n-1\) more hops: \(T(c)=(W_{\text{bytes}}/c+n-1)(\alpha+c/\beta)\). Setting \(dT/dc=-W_{\text{bytes}}\alpha/c^2+(n-1)/\beta=0\) gives \(c^*=\sqrt{W\alpha\beta/(n-1)}\) and \(T^*=(\sqrt{W/\beta}+\sqrt{(n-1)\alpha})^2\). For \(W_{\text{bytes}}=70\) GB, \(\beta=300\) GB/s, \(\alpha=50\) µs, \(n=255\): \(c^*\approx64\) MB, \(T^*\approx0.36\) s—close to the one-receiver time \(W_{\text{bytes}}/\beta=0.23\) s. Same structure as α–β collectives and pipeline bubbles: small chunks fill fast but pay α often.

Core Why does a faster cold start save GPUs? Quantify it.

An autoscaler must hold headroom to absorb demand growth during one cold start: if demand grows at \(\dot\lambda\) replicas' worth per minute, headroom ≈ \(\dot\lambda t_{\text{cold}}\). With Atlas's ramp of about 1.9 replicas/min, 15 minutes needs about 29 replicas (232 GPUs) of headroom; 35 seconds needs one or two. During failures, degraded time ∝ \(t_{\text{cold}}\), so spare capacity to meet availability shrinks too. Core Explain how you would cache models across a GPU fleet.

Tiers: object storage (canonical, durable), optional shared file system, node-local NVMe, host DRAM, peer HBM. Policy: when a model is registered for serving, a background agent writes its pre-sharded safetensors to the NVMe of every node in its pool (capacity is tens of TB per node, so catalogues fit); host DRAM keeps weights of models currently loaded on the node so a crashed engine restarts in seconds; cache misses (new or rare models) stream from object storage with high parallelism and seed a swarm. Eviction by LRU with pinning of production models; integrity verified by content hashes; access controlled per tenant. Deep-dive What takes time in engine initialisation, and how do you shorten it?

NCCL communicator creation (seconds intra-node, longer multi-node); memory profiling via a dummy forward at max batch to size the KV pool; JIT compilation of Triton/FlashInfer/torch.compile kernels; autotuning; CUDA graph capture for many batch sizes; loading tokenizers and LoRA adapters; warm-up. Deep-dive Compare star, swarm and chain distribution for model weights. When would you use each?

Star: every node fetches from the central store; simple, robust; time ≈ max(W/β_client, nW/β_svc), linear in n once the store's aggregate limit binds—fine for few nodes or small models. Swarm (BitTorrent-like, Kraken, Dragonfly): chunks exchanged among nodes over the front-end; every node's upload adds supply; time ≈ W_bytes/β + O(log n) chunks; tolerates churn and heterogeneous networks; needs a tracker or coordinator. Chain/tree broadcast over back-end RDMA from running replicas: time ≈ (W + (n−1)c)/β with β of hundreds of GB/s; fastest, but requires shared fabric, a coordinator to build chains, and a live source; fragile if a node in the chain fails (use trees or re-routing). Use star for small scale, swarm as the general mechanism, chain for large models and bursty scale-ups within a fabric.

Deep-dive Your platform must support scale-to-zero for thousands of fine-tuned 8B models. What does the cold-start path look like?

Requirement: a request for an idle model should get its first token within a few seconds. Approach: keep a warm pool of GPUs running the base engine (image pulled, compiled, graphs captured); store fine-tunes as LoRA adapters where possible (tens to hundreds of MB, loadable in milliseconds into a running multi-LoRA engine—no cold start at all). For full fine-tunes, cache popular ones on NVMe, keep recently used ones in host DRAM, and swap weights into a sleeping engine (load 16 GB from DRAM over PCIe in well under a second; from NVMe in about a second; from object storage with parallel streams in about 3 s). Route by cache locality: send the request to a node that already has the weights in DRAM or NVMe. Queue the request during load and stream once ready; set SLOs that distinguish warm and cold paths; evict by LRU with per-tenant quotas.

Design Design the weight-distribution system for a fleet serving DeepSeek-V3 in three regions.

Canonical copy: pre-sharded safetensors (FP8, about 700 GB, laid out per EP/TP rank) in object storage in each region, replicated cross-region on publish with integrity hashes and signatures. Regional: a cache agent on every node of the DeepSeek pools pre-populates NVMe with the current and next versions. Scale-up and recovery: new nodes fetch from peers over back-end RDMA via chain or tree broadcast coordinated by a distribution service; fall back to swarm over front-end and then to object storage. Rollouts: pre-stage new weights on NVMe before switching, so cutover is a fast local load; keep the old version cached for rollback. Design A new engine version must be rolled out to 2,000 replicas without affecting availability. How do image and weight handling affect the plan?

Keep weights out of the image so only the engine image changes; structure image layers so the new version changes only a small top layer; pre-pull the new image onto all nodes in the background before the rollout (or use lazy pulling with pre-fetch of hot files). Pre-warm compilation caches for the new version on a canary node per GPU type and publish them. Roll out progressively by failure domain (Chapter 13): drain a replica, restart with the new image (weights from local DRAM or NVMe: seconds), run warm-up and health checks, compare metrics with old replicas, continue. Keep the old image cached for fast rollback. With these, each replica's restart takes tens of seconds instead of many minutes, so capacity loss during the rollout is small.

Core Why does pre-sharding a checkpoint for tensor parallelism matter?

Each TP rank holds a slice of each weight matrix. If the checkpoint stores full tensors and the loader cannot read slices selectively (pickle), every rank reads the entire checkpoint and discards most of it: a TP8 replica reads 8× the model size, competing for storage and NIC bandwidth. Safetensors allows reading byte ranges of row-sharded tensors, but column shards are strided. Pre-sharding re-saves the model once in the serving layout, one contiguous file per rank, so each rank reads exactly its \(1/n_{\text{TP}}\) share sequentially—e.g. 17.5 GB instead of 140 GB per rank for a BF16 70B model at TP8—and loads become embarrassingly parallel.

Deep-dive When is GPUDirect Storage worth it, and when not?

GDS lets NVMe (and some network file systems) DMA directly into GPU memory, avoiding the host bounce buffer and CPU copies. It helps when the host's memory bandwidth or CPU is the bottleneck—many GPUs loading simultaneously from fast local NVMe or a parallel file system, or when host memory is busy with other work—and reduces CPU usage and latency. It matters less when the bottleneck is upstream (object storage throughput, front-end NIC), when loads are rare and small, when the storage stack does not support it, or when weights are already in host DRAM (then a pinned-memory copy is equally fast). It also requires driver and file-system support and alignment constraints. Measure the slowest link first.

Design How would you cut the cold start of an 8B model to under five seconds on a node that has never served it?

Remove node provisioning with a warm pool; pre-pull the base engine image on all pool nodes; keep a sleeping or idle base engine with compiled kernels and captured graphs for the 8B architecture; distribute the weights in pre-sharded FP8 safetensors (about 8 GB) to node NVMe when registered, or stream from peers over RDMA (well under a second) or from object storage with high parallelism (about 2–3 s at 5 GB/s); load into the waiting engine's memory without re-initialising; run a minimal warm-up. Alternatively restore a snapshot of an initialised engine for that model. If the model is a LoRA fine-tune of an already-running base, load the adapter into the running engine (milliseconds).
