Volume II · Part IV · The Global Request Path — Chapter 11

The Front Door: Gateways, Streaming and Rate Limits

Before a prompt reaches an engine it crosses the internet, a TLS handshake, several load balancers and an API gateway that decides who the caller is, whether they may make this request now, and where it should go. Then the response flows back as a stream of tokens over a connection that may stay open for minutes. This chapter follows that path: its latency budget, the protocols that carry token streams, the problems of long-lived connections, how rate limits are defined and enforced across many gateway instances, and how a service protects itself under overload without collapsing.

Why this chapter

Parts I–III built and paid for a fleet. Part IV follows requests to it, from users anywhere in the world, and asks how the service stays fast, available and safe on the way. The first stop is the front door, and for LLM services it differs from the front door of a web application in three ways. Responses are long-lived streams: a chat response streams for ten seconds, a reasoning response for minutes, so the gateway holds hundreds of thousands of open connections. Requests are wildly unequal in cost: one may need 100 tokens of computation and the next 100,000, so limits on requests per minute are nearly meaningless and limits must be stated in tokens—including output tokens that are unknown when the request is admitted. And overload is expensive and contagious: a GPU fleet cannot be scaled in seconds (Chapters 5 and 9), so the gateway is the last line of defence when demand exceeds capacity, and a gateway that responds badly—queueing everything, or letting clients retry aggressively—turns a capacity shortfall into an outage.

Volume I touched on parts of this: server-sent events in Vol. I §12.6 and token-bucket rate limits in Vol. I §27.5. This chapter treats the front door as a system. Interviewers ask about it in design questions ("design the API layer for an LLM service with 100,000 concurrent streams") and in debugging questions ("our reasoning model's long responses get cut off at exactly 60 seconds"; "a 5% error spike turned into a 40% load spike").

We trace a request's path and its latency budget (§11.1), compare streaming protocols (§11.2), and examine long-lived connections (§11.3). We then define rate limits for LLMs and the algorithms that enforce them (§11.4), extend them to many gateway instances (§11.5), and treat admission control, load shedding and retries (§11.6). We end with the design of the API itself (§11.7).

Learning objectives
  1. Trace a request from DNS resolution to the engine, and build a latency budget for time to first token.
  2. Compare SSE, chunked HTTP/1.1, HTTP/2, HTTP/3, WebSockets and gRPC for streaming tokens, and compute their overheads.
  3. Size the connection-handling layer with Little's law and avoid idle-timeout and draining failures for long streams.
  4. Define request, token and concurrency limits, and implement them with token buckets, sliding windows and GCRA, including the reservation of unknown output tokens.
  5. Design distributed rate limiting across gateway instances and bound its error.
  6. Explain goodput collapse under overload, design admission control and load shedding, and quantify retry amplification.

Uses: Vol. I §12.6 (SSE), §27.5 (token buckets), §11.8 (queueing); Chapters 1, 6 and 8 of this volume.

11.1 A request's journey

Figure 11.1 traces one chat request from a user's laptop to an Atlas engine and back. Each hop adds latency and is a place where things can fail, and it is worth knowing what each does and roughly what it costs.

Walk through Figure 11.1. The client first resolves the API's host name through DNS, which, for a global service, returns an address chosen for the client's location (Chapter 12); results are cached, so this costs nothing on most requests. It then opens a TCP connection and negotiates TLS (encryption and server authentication); with TLS 1.3 this takes one round trip after TCP's own handshake, and connections are kept alive and reused, so a busy client pays it once. The connection usually terminates at an edge location close to the user—a point of presence of the provider's or a content-delivery network—that forwards the request over the provider's backbone to a region, where a regional load balancer spreads connections over many gateway instances. The API gateway authenticates the caller (an API key or token), validates the request (model name, parameters, size limits), checks rate limits and quotas, records usage, applies policies such as data-residency routing and guardrails (Chapter 18), and hands the request to the router of Chapter 8, which picks a replica. The engine queues the request, prefills it and starts streaming tokens back through the same chain.

The budget at the bottom of Figure 11.1 makes the relative sizes plain. On a warm connection to an idle replica, time to first token is about 100 ms, of which the engine's prefill and first decode step are a third and the network round trip a fifth; everything the front door adds—edge, load balancer, gateway, router—is about 10 ms. On a new connection to a busy replica, connection setup adds tens of milliseconds and the engine's queue can add hundreds. The lesson is that the front door should be cheap and must never be the bottleneck, but that it controls the factors that dominate tail latency: whether connections are reused, which replica is chosen, and whether the request is admitted to a queue it cannot clear in time.

For the mathematician — latency budgets compose by addition, tails do not

The mean latency of a request through stages in sequence is the sum of the stages' means. Percentiles do not add: the 99th percentile of a sum is generally less than the sum of the 99th percentiles, because the stages rarely hit their tails together, and more than the largest single 99th percentile. When a request fans out—a gateway that calls an authentication service, a quota store and a guardrail classifier in parallel and waits for all—the latency is the maximum of the calls, and if each has a probability \(\epsilon\) of a slow response, the fan-out of \(k\) calls is slow with probability \(1-(1-\epsilon)^k\approx k\epsilon\). Dean and Barroso's "tail at scale" argument (2013) is this observation applied to large services: every dependency on the request path multiplies the chance of a slow request, so front-door dependencies must be few, fast, and protected with timeouts and fallbacks.

11.2 Protocols for streaming tokens

An LLM response is a sequence of small messages—a few characters each—produced over seconds to minutes, and the client wants each as soon as it exists. HTTP was designed for request–response exchanges, and several mechanisms extend it to streams. Table 11.1 compares them.

Public LLM APIs converged on server-sent events over HTTPS, for pragmatic reasons: SSE is plain HTTP, so it passes through corporate proxies, CDNs and load balancers that understand HTTP; it is trivially consumed in browsers and every language; and LLM streaming is one-directional once the prompt is sent. Each token or group of tokens is sent as an event: a line beginning data: followed by a JSON object with the token text, an index and sometimes log-probabilities, and a blank line; a final event carries usage counts and a finish reason. Real-time voice and interactive agents, where the client must send audio or interrupt while receiving, use WebSockets or WebRTC instead (Chapter 15). Inside the provider, between gateway and engine, gRPC streams are common because they carry typed messages, propagate deadlines and cancellations, and multiplex many streams over few connections.

Figure 11.2 shows what actually travels on the wire for a short streamed answer. Each event is a self-contained line of text: the data: prefix, a JSON object repeating the response's identifier, model name and a "delta" with the new text, and a blank line. The final events carry the finish reason and usage counts, and a sentinel marks the end of the stream. Comment lines—a colon followed by anything—are ignored by clients and serve as keep-alives (§11.3).

Streaming has overheads worth computing. A token of English text is about four characters, but an SSE event carrying it as JSON is typically 100–200 bytes, so the wire format can be thirty times larger than the content. For Atlas's \(2.2\times10^{11}\) output tokens a day, 150 bytes per token is about 33 TB a day of response traffic—cheap compared with GPUs (§4.8), but significant for gateways that must encrypt and frame every event, and for clients on slow mobile links. The common mitigation is to coalesce: send an event every few tokens or every 20–50 ms rather than every token, which cuts events by a factor of three to ten with no visible effect on a human reader. A second subtlety is buffering: proxies, compression middleware and some HTTP libraries buffer responses until a block fills, which turns a stream into a long wait followed by a burst. Streaming endpoints must disable response buffering and compression along the whole path, and set headers that tell intermediaries not to buffer.

11.3 Long-lived connections

Every stream occupies a connection, or at least an HTTP/2 stream within one, for its whole duration, and the number of streams open at once follows from Little's law (Vol. I §1.10): concurrency equals arrival rate times duration. Atlas at its peak receives 10,000 requests per second, and a response streams for about 15 seconds on average, so about 150,000 streams are open at any moment—and the 5% of requests that are reasoning-heavy, streaming for several minutes, add tens of thousands more. Each open stream costs memory in the gateway (buffers, TLS state, request context, perhaps tens of kilobytes), a file descriptor, and work for every event sent. A gateway tier designed for short API calls, where concurrency is arrival rate times milliseconds, may be sized for a hundredth of this.

Long streams also collide with timeouts that were designed for short requests. Load balancers and proxies close connections that have been idle—no bytes in either direction—for a configured time, often 60 seconds by default on cloud load balancers. A reasoning model that thinks for 90 seconds before emitting its first visible token, or a provider that does not stream hidden reasoning tokens, presents an idle connection that the load balancer kills at exactly 60 seconds. The client sees a dropped connection; the engine keeps generating for a client that is gone. The fixes are to raise idle timeouts on every hop for streaming endpoints, to send keep-alive events periodically (SSE allows comment lines beginning with a colon, which clients ignore), and to stream progress or reasoning summaries so the connection is not idle. Equally, maximum request durations configured in gateways and service meshes must exceed the longest permitted generation.

Connections must also be drained gracefully. When a gateway instance is replaced during a rollout or scale-down, it should stop accepting new connections, let existing streams finish (subject to a grace period sized as in §6.7), and only then exit; regional load balancers support connection draining with configurable timeouts for this reason. And cancellation must propagate the other way: when a client disconnects, the gateway must tell the engine to abort the request, or the engine wastes GPU time generating tokens nobody will read. With 150,000 concurrent streams and a few percent of clients abandoning each minute, unpropagated cancellations can waste a measurable share of a fleet.

Worked example — sizing Atlas's streaming tier

Concurrency. 10,000 requests/s at peak. 95% are chat with mean streaming time 15 s; 5% are reasoning with mean 120 s. Concurrent streams: \(9{,}500\times15+500\times120\approx142{,}500+60{,}000\approx200{,}000\).

Memory. At about 64 KB per stream (TLS and HTTP state, buffers, request context), 200,000 streams need about 13 GB across the gateway tier: not a problem in aggregate, but instance limits on connections and file descriptors must be raised from defaults, and with 50 gateway instances each holds about 4,000 streams.

Event rate. About 4.5 million output tokens/s fleet-wide at peak (Table 1.1: \(2.4+1.4+0.75\) million). Coalescing tokens into events every 30 ms gives at most about 33 events per second per stream, or at most about 6.7 million events/s across 200,000 streams if every stream emitted continuously; in practice fewer, since many streams are waiting on prefill or reasoning. Each event is encrypted and framed: CPU, not bandwidth, sets the gateway's size.

Timeouts. Reasoning requests may produce no visible output for minutes: send an SSE comment every 15 s; set idle timeouts to 10 minutes on load balancers and maximum request duration to 30 minutes on the gateway; propagate client disconnects to the engine.

11.4 Rate limits for LLMs

A rate limit restricts how much of a shared service one caller may use per unit time. It protects the service from overload, divides capacity fairly among tenants, enforces commercial tiers, and contains abuse. For web APIs, limits are usually stated in requests per second or minute. For LLM APIs, a request is the wrong unit, because cost varies by orders of magnitude between requests. Providers therefore define several limits at once: requests per minute (to cap per-request overheads and abuse), input tokens per minute and output tokens per minute (to cap the actual work), sometimes concurrent requests (to cap the KV memory and decode slots a tenant can occupy at once), and longer-period quotas (tokens or dollars per day or month). A request is admitted only if it satisfies all of them.

The classical algorithm for a rate limit is the token bucket (Vol. I §27.5): a bucket of capacity \(b\) fills at rate \(r\) units per second, and a request costing \(k\) units is admitted if the bucket holds at least \(k\), which are then removed. Over any interval of length \(\Delta t\), admitted work is at most \(b+r\Delta t\): the rate is \(r\) on average with bursts up to \(b\). An equivalent formulation used by many production limiters is the generic cell rate algorithm (GCRA), from telecommunications, which stores a single timestamp per key instead of a counter and a time.

Algorithm 11.1 — GCRA for a limit of rate \(r\) with burst tolerance \(b\)

Keep, for each key, a theoretical arrival time \(\theta\) (initially 0). Let \(\delta=1/r\) be the emission interval and \(\tau_b=(b-1)\delta\) the burst tolerance. When a request costing \(k\) units arrives at time \(t\):

1. Set \(\theta'=\max(\theta,t)+k\delta\).
2. If \(\theta'-t\le\tau_b+\delta\), admit the request and store \(\theta\leftarrow\theta'\).
3. Otherwise reject it, and report a retry time \(\theta'-(\tau_b+\delta)-t\) seconds.

Why it is a token bucket. The quantity \((\tau_b+\delta)-(\theta-t)\), divided by \(\delta\), is the number of units the bucket would hold: \(\theta\) advances by \(\delta\) per admitted unit (removing tokens) and the gap \(\theta-t\) shrinks at unit rate as time passes (refilling at rate \(r\)), capped when \(\theta\le t\) (a full bucket). The test admits exactly when the bucket holds at least \(k\). The advantage is storage and atomicity: one number per key, updated with a single compare-and-set.

LLM limits raise a problem that request-based limits do not: output tokens are unknown at admission. A request might generate 10 tokens or the caller's maximum of 8,000. Admitting it against the output-token limit requires a guess, and the two standard approaches trade accuracy for simplicity. The first reserves the caller's declared maximum output (max_tokens) at admission and refunds the unused part when the request finishes. This never lets a caller exceed the limit, but it penalises callers who set large maxima and makes admission conservative. The second admits against an estimate—the caller's recent average output length—and charges the true count afterwards, letting the bucket go negative so that later requests are delayed; this is more permissive and occasionally lets a burst through. Input tokens can be counted exactly at admission, though tokenising every prompt at the gateway costs CPU, so some gateways estimate from character counts and reconcile later.

Drill 11.1 — Reserving output tokens

A tenant has an output-token limit of 400,000 tokens per minute with a burst of 100,000. Its requests declare max_tokens of 4,000 but generate 500 on average. If the gateway reserves max_tokens at admission and refunds on completion, and each request takes 20 s, how many requests per second can the tenant sustain? How does that compare with its true output rate?

Solution. While a request runs, 4,000 tokens are reserved; at completion 3,500 are refunded. The sustained admitted rate is limited by tokens actually charged (500 per request): \(400{,}000/60/500\approx13\) requests/s. But reservations in flight occupy the bucket: at 13 requests/s with 20 s duration, about 267 requests are in flight, holding \(267\times3{,}500\approx930{,}000\) tokens of unrefunded reservation—far above the 100,000 burst capacity. The bucket therefore cannot hold the reservations, and the tenant is throttled to about \(100{,}000/4000=25\) requests in flight, or 1.25 requests/s: a tenth of its entitlement. Reservation by max_tokens severely penalises callers with large maxima; estimating from history, or limiting concurrency separately, is fairer.

11.5 Distributed rate limiting

A single gateway could keep every tenant's bucket in memory. Atlas has dozens of gateway instances per region and several regions, and a tenant's requests arrive at all of them, so its limit must be enforced across instances. There are three common designs, sketched in Figure 11.3, with different points on a trade-off between accuracy, latency and availability.

A central store—typically Redis or a similar in-memory database, with the bucket or GCRA update performed atomically by a script—gives exact enforcement: every gateway consults the same state for every request. It adds a network round trip (sub-millisecond within a zone) and makes the store a dependency on the request path, which must be replicated and must fail sensibly (§1.7: keep enforcing the last known limits locally, rather than reject all or admit all). Its throughput must cover every request, which for hot tenants means sharding by key. Local buckets with a split quota give each of \(n\) gateways a share \(r/n\) of the limit and enforce it locally, with no coordination on the request path. They are fast and robust but inaccurate when a tenant's traffic is uneven across gateways—a tenant whose requests all land on one gateway gets only \(r/n\)—so the shares must be rebalanced periodically from observed traffic. Local decisions with asynchronous synchronisation let each gateway decide locally using its own estimate of the tenant's global usage, and exchange counts with an aggregator every \(\Delta\) seconds. Between synchronisations each gateway may admit up to the full remaining allowance, so in the worst case \(n\) gateways together over-admit by about \(n\,r\,\Delta\); with 50 gateways, a 100 ms sync interval and a limit of 1,000 tokens per second, that is up to 5,000 tokens—a five-second overshoot in a pathological burst, negligible in normal traffic.

Drill 11.2 — How much can synchronised local limits overshoot?

A tenant has a limit of 600,000 input tokens per minute (10,000 per second). Its requests are spread over 40 gateway instances, each making local decisions and synchronising counts every 200 ms. A misbehaving client suddenly sends everything it can. What is the worst-case over-admission before the gateways learn of each other's admissions, and what would reduce it?

Solution. Between synchronisations each gateway may believe the tenant has its full remaining allowance. In the worst case all 40 admit up to the allowance for one interval: about \(n\,r\,\Delta=40\times10{,}000\times0.2=80{,}000\) tokens, eight seconds' worth of the limit, on top of the bucket's burst. Afterwards the global state is known and the tenant is throttled until it is back within its limit, so the long-run rate is still enforced. To reduce the overshoot: synchronise faster for tenants near their limits, give each gateway a local cap of a few times its fair share \(r/n\), or route a tenant's traffic to a small subset of gateways (sharding by tenant), which reduces \(n\) for that tenant.

Which design fits depends on what the limit protects. Limits that protect the service's capacity can be approximate, because capacity planning has slack and admission control (§11.6) catches the rest. Limits that enforce money—prepaid credits, free-tier quotas that abusers try to exceed—need tighter accuracy, often with a central store for the final check of long-period quotas and local approximations for per-second smoothing. Many providers combine them: fast local GCRA for requests and tokens per minute, synchronised periodically, plus an exact central ledger for daily and monthly quotas. Rate limits divide capacity among callers who behave; protecting the service when everyone wants more than exists is the job of admission control.

11.6 Admission control, load shedding and retries

When demand exceeds capacity, a service must choose which work to do. The worst choice is not to choose: to accept every request into an ever-growing queue. Each request then waits longer, until requests wait longer than their clients are willing to wait; clients time out and retry, adding load; the engines spend their capacity on requests whose clients have already gone. Throughput stays high while goodput—requests completed within their deadline (Vol. I §13.2)—collapses. Figure 11.4 shows the effect in the simplest queueing model.

Figure 11.4's red curve is the formula \(\lambda\Pr(T\le t_{\text{dl}})\) for an M/M/1 queue, where the time in system \(T\) is exponential with rate \(\mu-\lambda\): goodput \(=\lambda\bigl(1-e^{-(\mu-\lambda)t_{\text{dl}}}\bigr)\), which reaches zero at \(\lambda=\mu\). Real LLM services are more complicated—many servers, continuous batching, heavy-tailed service times—but the qualitative lesson survives: as load approaches capacity, queueing delay grows without bound, and a service that admits everything delivers almost nothing useful. The green curve is what admission control achieves: the service admits a request only if it expects to meet the request's deadline, and rejects the rest immediately, so the requests it does serve finish in time. Rejection is unpleasant, but a fast rejection lets a client retry elsewhere or later, while a slow timeout wastes the client's time and the service's capacity.

Figure 11.5 arranges admission as a sequence of cheap checks, each of which ends in a fast, typed answer if it fails. Admission decisions for LLMs can use more information than generic services have. The gateway knows each request's input length and the router knows each replica's prefill queue (§8.4), so it can estimate the request's TTFT and reject it if the estimate exceeds the deadline. It knows the tenant's priority and can shed lower tiers first (free before paid, batch before interactive). And it can adapt the limit itself: instead of a fixed queue bound, an adaptive concurrency limit raises the number of in-flight requests while latency stays near its minimum and lowers it when latency rises, the same principle as TCP Vegas congestion control, which Netflix and others applied to service-to-service traffic.

The other half of overload is the client's behaviour. A client whose request fails or times out retries. If a fraction \(p\) of attempts fail and each client retries up to \(k\) times immediately, each original request generates on average \(1+p+p^2+\dots+p^k\) attempts. When failures are caused by overload, retries add load exactly when the service has none to spare, raising \(p\), which raises retries further: a retry storm. Figure 11.6 shows the amplification.

The defences against retry storms are well established, and an LLM service must apply them on both sides. Clients and SDKs should retry with exponential backoff and jitter—waiting a random time that doubles with each attempt—so that retries spread out instead of arriving in synchronised waves, and should respect Retry-After headers. Services should cap retries with retry budgets (retries may add at most, say, 10% to the load), distinguish errors that should be retried (429 Too Many Requests, 503 Service Unavailable with a retry time) from those that should not (400 Bad Request), and make retries cheap: an idempotency key lets a retried request be recognised and its cached result returned, and a resumable stream lets a client continue from the last token received rather than start over. Internal services between gateway and engine follow the same rules, since an internal retry storm is just as destructive.

Worked example — a 5% error spike becomes a 40% load spike

Incident. A bad deployment makes 5% of Atlas's replicas return errors. Clients use an SDK that retries immediately up to 10 times, and the gateway itself retries failed upstream calls up to 3 times. The fleet was at 85% utilisation.

Amplification. With \(p=0.05\), the gateway's 3 retries turn each client attempt into \(1+0.05+0.05^2+0.05^3\approx1.05\) upstream calls: harmless. But retries land on the healthy replicas, utilisation passes 90%, queues lengthen, TTFTs exceed the client's 10 s timeout for some requests, which now count as failures too: \(p\) rises to 30%. Clients' 10 retries now give \(1.43\) attempts per request, the gateway's 3 retries multiply that by 1.42: about 2 upstream calls per original request at the worst moment, against a fleet already near capacity. Load roughly doubles; within a minute most requests fail.

Fixes. Client backoff with jitter and at most 2–3 retries; gateway retry budget of 10%; retries only to a different replica; fast rejection (429 with Retry-After) once estimated TTFT exceeds the deadline; idempotency keys and resumable streams so retries do not redo work; and automated rollback of the bad deployment, which was the actual cause.

11.7 Designing the API

The last element of the front door is the API itself, whose design determines how well clients can use the service and how well the service can protect itself. By 2024 most LLM providers and open-source engines offered an interface compatible with OpenAI's chat-completions API—a list of messages in, a message or stream of message deltas out—so that client libraries and applications could switch between providers; newer interfaces added server-side conversation state, tool calls and structured outputs (Chapter 17). Whatever the shape, several properties matter for infrastructure. The request should declare limits—maximum output tokens, a deadline or timeout, stop sequences—so the service can plan and enforce them. It should carry an idempotency key, so retries are safe, and receive a request identifier that appears in logs and bills, so problems can be traced end to end. Responses should report usage—input, cached input, output and reasoning tokens—in the final event, so clients can track cost (§10.4). Errors should be typed and actionable: rate-limited (retry after so many seconds), overloaded (retry elsewhere or later), invalid request (do not retry), content refused (do not retry). And streams should be resumable where possible, identified by a stream ID and an offset, so a dropped connection costs a reconnect rather than a regeneration.

Versioning deserves a word. An API that names models by mutable aliases ("latest") lets the provider upgrade models silently, which surprises clients whose prompts were tuned to the old behaviour; one that names models by dated versions lets clients pin and migrate deliberately, at the cost of the provider serving several versions at once (Chapter 8's lifecycle). Most providers offer both: dated versions for stability and aliases for convenience, with published deprecation schedules. With the front door designed, the next question is which region's front door a user reaches, and what happens when that region fails.

Looking ahead

We followed a request from the client to the engine within one region: through TLS, load balancers and a gateway that authenticates, limits and admits it, over a streaming protocol that keeps a connection open for minutes. But Atlas's users are on every continent, some of their data may legally be processed only in particular countries, and whole regions occasionally fail. Which region should answer each request? How is traffic steered there, and moved away when a region is degraded? What state—prefix caches, conversation history, uploaded files—must follow a user across regions? And how much capacity must each region hold to absorb another's failure? Chapter 12 takes up multi-region serving and disaster recovery.

Chapter summary

  • A request passes DNS, TCP/TLS (reused connections avoid 1–3 RTTs), an edge, a regional load balancer, the API gateway (auth, validation, limits, metering, policy) and a router to an engine; the front door should add about 10 ms, while queueing and prefill dominate TTFT under load.
  • Tail latency compounds over dependencies: fan-out to \(k\) services is slow with probability \(\approx k\epsilon\); keep front-door dependencies few and protected.
  • Public LLM APIs stream with SSE over HTTP/1.1 or HTTP/2; real-time APIs use WebSockets; internal hops use gRPC. JSON framing inflates tokens about 30×; coalesce events and disable buffering.
  • Concurrent streams = arrival rate × duration (Little's law): about 200,000 for Atlas; raise connection limits, idle timeouts (default 60 s kills reasoning streams), send keep-alives, drain gracefully, propagate cancellations.
  • LLM limits combine requests, input tokens, output tokens, concurrency and quotas; token bucket and GCRA (one timestamp per key) enforce them; unknown output tokens are reserved and refunded or estimated and reconciled.
  • Distributed limiting: central store (exact, extra hop and dependency), split local quotas (fast, rigid), or local decisions with periodic sync (overshoot \(\lesssim n\,r\,\Delta\)).
  • Without admission control, goodput collapses as load nears capacity (M/M/1: \(\lambda(1-e^{-(\mu-\lambda)t_{\text{dl}}})\to0\)); shed early using estimated TTFT, priorities and adaptive concurrency limits.
  • Retries amplify load by \(1+p+\dots+p^k\); use backoff with jitter, retry budgets, typed errors, Retry-After, idempotency keys and resumable streams.
  • APIs should declare limits and deadlines, carry idempotency keys and request IDs, report usage by token type, return actionable errors, support resumable streams and pinned model versions.

Warm-up Walk me through what happens between a client sending a chat request and the first token arriving.

DNS resolves the API host (cached, geo-aware); TCP and TLS 1.3 handshakes (reused if keep-alive); the connection terminates at an edge near the user and is forwarded to a region; a regional load balancer spreads it over gateway instances; the gateway authenticates, validates, checks rate limits and quotas, meters, applies policy (residency, guardrails); the router picks a replica by load and cache affinity; the engine queues, prefills uncached tokens and decodes the first token, which streams back as an SSE event through the same chain. Warm and idle: ~100 ms; new connection and loaded replica: several hundred ms, dominated by queueing.

Warm-up SSE, WebSockets or gRPC for streaming LLM output?

Public chat/completions APIs: SSE over HTTPS—plain HTTP, passes proxies and CDNs, easy clients, one-directional is enough. Real-time voice or interactive agents where the client sends audio or interrupts while receiving: WebSockets or WebRTC (full duplex). Internal gateway-to-engine traffic: gRPC streaming over HTTP/2 (typed messages, deadlines, cancellation, multiplexing). HTTP/3 at the edge helps mobile clients. In all cases disable buffering and compression on streaming paths and coalesce tokens into events.

Warm-up How do you rate-limit an LLM API?

Multiple limits per tenant and tier: requests per minute, input tokens per minute (counted at admission), output tokens per minute (reserved at admission from max_tokens or estimated from history, reconciled at completion), concurrent requests, and daily/monthly quotas. Enforce with token buckets or GCRA (one timestamp per key). Across many gateways: local decisions with periodic synchronisation for per-minute limits, exact central ledger for money-like quotas. Return 429 with Retry-After and remaining-limit headers.

Core Explain GCRA and show it is equivalent to a token bucket.

State: theoretical arrival time \(\theta\). Emission interval \(\delta=1/r\), burst tolerance \(\tau_b=(b-1)\delta\). For a request of cost \(k\) at time \(t\): \(\theta'=\max(\theta,t)+k\delta\); admit iff \(\theta'-t\le\tau_b+\delta\), then store \(\theta'\); otherwise reject with retry-after \(\theta'-t-(\tau_b+\delta)\). Equivalence: define bucket level \(=((\tau_b+\delta)-(\theta-t))/\delta\); it decreases by \(k\) per admission (θ advances \(k\delta\)), increases at rate \(r\) as \(t\) advances, and is capped at \(b\) when \(\theta\le t\); the admission test is level ≥ k. Benefit: one value per key, atomic compare-and-set in Redis, no background refill.

Core How do you handle output-token limits when output length is unknown at admission?

Option A: reserve max_tokens at admission, refund the unused part at completion—never exceeds the limit but over-reserves for callers with large maxima (in-flight reservations can exhaust the burst capacity and throttle a tenant to a fraction of its entitlement). Option B: admit against an estimate (recent mean output length per tenant/model), charge actual usage at completion, allow the bucket to go negative so subsequent requests wait—fairer, occasionally lets bursts through. Combine with a concurrency limit (caps in-flight work directly) and server-side max output caps. Document behaviour; expose remaining limits in headers.

Core Design distributed rate limiting across 50 gateway instances in 3 regions.

Per-second/minute limits: each gateway runs local GCRA per tenant using its estimate of global usage; instances report counts to a regional aggregator every ~100 ms and receive updated global usage (or rebalanced shares); bound overshoot ≈ n·r·Δ and accept it for capacity-protection limits. Cross-region: allocate each tenant's global limit to regions in proportion to recent traffic, rebalanced every few seconds. Money-like quotas (credits, daily caps): exact central ledger (replicated store) checked at admission for large requests and reconciled per request; cache in gateways with short TTL. Failure mode: if the store or aggregator is unreachable, keep enforcing last known limits locally (static stability). Shard hot tenants' keys.

Deep-dive Explain goodput collapse under overload and design admission control for an LLM service.

As utilisation approaches 1, queueing delay grows without bound; with deadlines (client timeouts, TTFT SLOs), more and more completed work is useless—M/M/1 goodput \(\lambda(1-e^{-(\mu-\lambda)t_{\text{dl}}})\) peaks below capacity and falls to zero at \(\lambda=\mu\); abandoned requests still consume capacity and trigger retries. Admission control: estimate each request's TTFT from its uncached input length and the chosen replica's prefill queue; reject immediately (429/503 + Retry-After) if it exceeds the deadline; shed by priority (free before paid, batch before interactive); bound queues by time not count; use adaptive concurrency limits keyed to latency; propagate cancellations; prefer degrading (smaller model) to rejecting for some tiers. Measure goodput explicitly.

Deep-dive A 5% error spike became a 40% load spike and then an outage. Explain the dynamics and fixes.

Retries amplify load by \(1+p+\dots+p^k\), and layers multiply (client SDK retries × gateway retries × internal retries). Retries land on healthy replicas, pushing utilisation up, which lengthens queues and causes timeouts, raising \(p\)—positive feedback. Fixes: client backoff with jitter, few retries, honour Retry-After; retry budgets per layer (e.g. ≤ 10% extra load), retries only at one layer; retry to different replicas; circuit breakers to stop sending to failing replicas; fast rejection under overload; idempotency keys and resumable streams so retries don't redo work; and fix the root cause (roll back the bad deployment automatically).

Deep-dive Why do tail latencies compound across the front door's dependencies, and how do you contain them?

Each synchronous dependency (auth service, quota store, guardrail classifier, routing service) has its own tail; a sequential chain's tail is at least the largest and fan-out's latency is the maximum, so with \(k\) dependencies each slow with probability \(\epsilon\), about \(k\epsilon\) of requests are slow ("tail at scale"). Contain: minimise dependencies on the request path (cache auth decisions and limits locally, update asynchronously), use timeouts with fallbacks (fail open or closed by policy), hedged requests for idempotent reads, parallelise independent calls, keep dependencies in-zone, and measure per-hop latency distributions with tracing.

Design Design the API gateway layer for Atlas.

Edge: anycast/GeoDNS to nearest healthy region, TLS 1.3 termination, HTTP/2 and HTTP/3, DDoS protection. Regional L7 load balancers with long idle timeouts and connection draining. Gateway instances (stateless, autoscaled on concurrent streams and CPU): authenticate API keys (cached), validate requests, enforce per-tenant request/token/concurrency limits with local GCRA plus async sync and an exact ledger for quotas, data-residency routing, guardrail calls with timeouts, usage metering to a billing pipeline, request IDs and tracing. Design How would you make streams resumable after a dropped connection?

Assign each request a stream ID and number events with offsets; the gateway (or a small stream buffer service) keeps the generated tokens for a short window (or until completion plus a TTL) keyed by stream ID. On reconnect with stream ID and last offset, replay missing events and continue streaming if generation is ongoing. If the replica that was generating has failed, re-issue the request to another replica with the prompt plus already-generated tokens as a prefix (cheap with prefix caching) and continue from the offset, preserving sampling seeds if determinism is required. Bound buffer memory, authenticate reconnects, and expose the behaviour in the SDK so clients reconnect automatically with backoff.

Core Compare a central store with local token buckets for distributed rate limiting.

Central store (Redis with atomic scripts): exact global enforcement, simple semantics; costs a network hop per request, throughput limits per hot key (shard), and a dependency that must be highly available with a defined failure mode. Local buckets: zero added latency, robust to partitions; but split quotas under-admit uneven traffic, and unsynchronised local decisions over-admit up to \(n\,r\,\Delta\) between syncs. Hybrid: local decisions with periodic sync for per-minute limits; central exact checks for money-like quotas. Choose by what the limit protects.

Core What should an LLM API return in errors and final stream events?

Errors typed and actionable: 400 invalid (don't retry), 401/403 auth, 404 model, 413 too large, 429 rate-limited with Retry-After and which limit, 503 overloaded with Retry-After, content-policy refusal (don't retry), timeouts; include request ID. Final event: finish reason (stop, length, content filter, tool call), usage by token type (input, cached input, output, reasoning), model version served, and timing if useful. Headers: remaining limits and reset times. This lets clients back off correctly, track cost and debug.

Deep-dive How would you implement priority-based load shedding without starving low tiers?

Classify requests (enterprise, paid, free, batch) and give each a weight and a minimum guaranteed share of capacity; under overload, admit by weighted fair queueing over classes (each class's share proportional to weight, but never below its guarantee), and within a class by deadline feasibility. Shed lowest tiers first only above their guaranteed share. Use per-class adaptive concurrency limits and per-class queues bounded by time. Move deferrable traffic to batch queues instead of rejecting. Monitor per-class goodput and rejection rate; alert when lower tiers hit their floors for long periods (a capacity signal, Chapter 9).
