Volume II · Part II · Orchestration — Chapter 6

Containers and Kubernetes for Accelerators

A fleet of thousands of GPU servers is useless until something decides which program runs on which GPU, starts it, watches it, restarts it when it dies and replaces it when its code changes. In most AI infrastructure that something is Kubernetes, running containers. This chapter explains, from the operating system upward, what a container is, how Kubernetes turns declarations of desired state into running replicas, how GPUs are exposed to it, what software a GPU node needs, how one replica can span several machines, and how to configure the probes and shutdown behaviour of an inference server whose requests last minutes.

Why this chapter

Part I built the physical cloud: power, accelerators, networks and storage. Its last chapter repeatedly said "start a replica on a node" without asking who does the starting. In a small deployment a person does: they log into a machine and run vllm serve. In Atlas, with thousands of GPUs, three model tiers, daily autoscaling from about 140 to more than 300 replicas of the 70B model alone, weekly engine upgrades and daily hardware failures, it must be software. That software has two layers. A packaging layer—containers—makes a replica's code and dependencies into a single artefact that runs identically on any machine. An orchestration layer—Kubernetes, in most clouds and AI labs—places those artefacts on machines and keeps them in the state the operators asked for.

Kubernetes was designed for web services that need a fraction of a CPU and a few hundred megabytes of memory, start in seconds and can run anywhere. LLM replicas need eight GPUs connected by NVLink, terabytes of memory, specific NICs, minutes to start, and sometimes several machines that must start and stop together. Much of the engineering of AI platforms in 2023–2026 consisted of adapting Kubernetes to these needs, and interviewers for ML-platform and infrastructure roles probe that adaptation: "how does a pod get a GPU?", "what is a device plugin and why was DRA introduced?", "how do you deploy a model that spans two nodes?", "why did our rollout kill requests mid-stream?".

We begin with the operating-system mechanisms that make a container (§6.1). We then explain why an orchestrator is needed and how Kubernetes is built (§6.2), its object model with LLM-specific examples (§6.3), how accelerators are exposed through device plugins and Dynamic Resource Allocation (§6.4), and the software stack on a GPU node (§6.5). We extend to replicas that span nodes (§6.6), and finish with the operational details that most often go wrong for LLM servers: probes, rollouts and graceful termination (§6.7), and the limits of Kubernetes for AI (§6.8).

Learning objectives

  2. Describe the Kubernetes architecture (API server, etcd, scheduler, controllers, kubelet) and its declarative, reconciling model.
  3. Write the essential parts of a pod specification for an LLM server, and use Deployments, Services, labels, taints and affinity appropriately.
  4. Compare device plugins with Dynamic Resource Allocation for exposing GPUs, MIG slices and multi-node NVLink domains.
  5. List the components of a GPU node's software stack and their version dependencies, and what the GPU Operator automates.
  6. Deploy multi-node replicas as groups (LeaderWorkerSet), and configure probes, rolling updates and termination grace periods for long-running generation requests.

6.1 Processes, isolation and the container

A running program on Linux is a process: an address space (the memory it can see), one or more threads of execution, and a set of resources the kernel tracks for it—open files, network sockets, a user identity, a current directory. The kernel is the privileged program that owns the hardware and mediates every process's access to it, through system calls. By default every process sees the same global world: the same file system tree, the same list of other processes, the same network interfaces, the same host name. Two programs that need different versions of the same library, or that both want to listen on port 8000, collide in that shared world.

A container is a process, or group of processes, whose view of that world has been restricted and whose resource use has been capped, by two kernel mechanisms. Namespaces give a process a private copy of some global name space: a mount namespace gives it its own file-system tree (whose root is the container image's files), a PID namespace its own process numbering (it sees itself as process 1 and cannot see the host's processes), a network namespace its own interfaces, addresses and ports, and further namespaces isolate host names, inter-process communication and user identities. Control groups (cgroups) place the process in a hierarchy of resource budgets: at most so many CPU-seconds per second, at most so many bytes of memory (exceeding it triggers the out-of-memory killer), limits on I/O and process counts. A container runtime such as containerd or CRI-O creates these namespaces and cgroups, mounts the image's layers (§5.6) as the root file system, and starts the program inside.

For the mathematician — namespaces as restricted views, cgroups as budgets

Model the kernel's global state as a collection of name spaces: a set of file paths \(\mathcal F\), a set of process identifiers \(\mathcal P\), a set of network endpoints \(\mathcal E\), and so on. Without containers, every process's view is the identity map on each. A namespace replaces the identity with a different map for a group of processes: the mount namespace maps the container's paths into a subtree of \(\mathcal F\) (its image) plus explicitly shared mounts; the PID namespace is an injective map from the container's process numbers into \(\mathcal P\) that hides everything outside its image. Isolation is the statement that the images of different containers' maps are disjoint except where sharing was declared. Cgroups are a separate structure: a rooted tree whose nodes carry budgets \((c_{\text{cpu}},c_{\text{mem}},\dots)\), with each container a leaf, each node's budget at most its parent's, and the kernel's scheduler and memory manager enforcing the constraint that the usage of every subtree stays within its node's budget. Kubernetes' resource requests and limits (§6.3) are written straight into this tree.

The crucial difference from a virtual machine (§3.1) is that all containers on a machine share one kernel. A VM runs its own kernel on virtual hardware; a container is just a restricted process on the host kernel. Containers therefore start in milliseconds rather than tens of seconds, use no memory for a second kernel, and run at native speed. The price is weaker isolation: a kernel vulnerability can let a process escape its container, so containers from mutually untrusting parties are often placed in separate VMs, or in sandboxes such as gVisor or Firecracker microVMs (Chapter 17), when isolation matters (Chapter 14).

GPUs fit into this picture in a specific way that explains a whole class of production failures. The GPU's kernel-mode driver is part of the host kernel, so it is shared by all containers and is installed on the host, not in the image. A container reaches the GPU through device files such as /dev/nvidia0 and /dev/nvidiactl, which the runtime exposes into its mount namespace only if it has been granted that GPU. The user-mode parts of the driver—the libraries that CUDA programs call, such as libcuda.so—must match the kernel-mode driver's version exactly, so they too come from the host: the NVIDIA Container Toolkit, a hook in the container runtime, mounts them into the container at start-up. The CUDA toolkit libraries the program was built against (cuBLAS, cuDNN, NCCL) live in the image. The resulting rule is that the image's CUDA version must be supported by the host's driver version; CUDA's compatibility guarantees allow a newer driver to run older CUDA images, but not, in general, the reverse. A fleet that upgrades its engine image to a newer CUDA before upgrading node drivers finds its pods failing with "CUDA driver version is insufficient", and this is among the most common GPU incidents.

Figure 6.1 summarises the layering. In practice, cloud GPU fleets often use both: VMs or bare-metal machines as the unit the cloud provides, and containers inside them as the unit that operators deploy. Containers solve packaging; they do not decide where anything runs. That is the orchestrator's job.

6.2 Why an orchestrator, and how Kubernetes is built

Suppose Atlas's operators had containers but no orchestrator. To deploy the 70B tier they would need to choose 311 eight-GPU machines that are healthy and free, start a container on each with the right image, arguments and GPU assignment, register each with the router, notice when one crashes and restart it, notice when a machine dies and start its replica elsewhere, add and remove replicas as the autoscaler requests, and replace every replica with a new image during a rollout without dropping below capacity. Each of these is simple; doing all of them correctly, continuously, for thousands of containers, while machines fail and operators make changes, is not. It is the problem Google solved internally with Borg, a cluster manager running hundreds of thousands of jobs across many clusters, described publicly in 2015[1]. Kubernetes, open-sourced by Google in 2014 and governed since 2015 by the Cloud Native Computing Foundation, distils Borg's lessons into a general-purpose system[2].

Kubernetes' central idea is the declarative API with reconciliation that we met abstractly in §1.7. Users do not issue commands such as "start a container on machine 17". They write objects that declare desired state—"there should be 311 replicas of this pod template"—into a store, and a set of independent controllers each watches part of the state and acts to make reality match the declaration. If a machine dies, nobody has to notice and reissue commands: the controller responsible sees that only 303 replicas exist where 311 were declared, and creates eight more. Figure 6.2 shows the components that implement this.

Walk through Figure 6.2 from the top. All cluster state—every object's desired specification and observed status—is stored in etcd, a strongly consistent key–value store replicated across a few machines with the Raft consensus protocol, so that the cluster's state survives the loss of a control-plane machine. The API server is the only component that talks to etcd; it validates objects, enforces access control and lets clients watch for changes. Controllers run reconciliation loops: the ReplicaSet controller, for instance, watches ReplicaSet objects and their pods, and creates or deletes pods to make their number match the declared count. The scheduler watches for pods that have no node, chooses a node for each according to resource requests and constraints, and records the choice (it "binds" the pod). On every node, the kubelet watches for pods bound to its node, asks the container runtime to start them with the requested devices, runs their health probes, and reports their status back through the API server. The data plane of a served model—requests flowing to engines—never passes through any of this; Kubernetes is purely a control plane, and a well-built serving system keeps serving if the Kubernetes control plane is briefly unavailable (static stability, §1.7).

6.3 The object model, for an LLM server

Kubernetes exposes several dozen object types, but a model deployment needs only a handful, and it is easiest to learn them through one. The smallest deployable unit is the pod: one or more containers that are always scheduled together on one node, share a network namespace (and so an IP address) and can share volumes. An inference replica on one machine is one pod, usually with one main container running the engine and perhaps a small sidecar for metrics or log shipping. The pod's specification lists images, arguments, environment, volumes and—most importantly for scheduling—resource requests and limits. Requests are what the scheduler reserves on the node; limits are the cgroup caps the kubelet enforces. For GPUs, which cannot be overcommitted, request and limit are the same integer.

A fragment of a pod template for Atlas's 70B replica looks like this:

containers:
- name: engine
  image: registry.example.com/atlas/vllm@sha256:3f1c…   # immutable digest
  args: ["--model", "/models/llama3-70b-fp8", "--tensor-parallel-size", "8"]
  resources:
    requests: {cpu: "96", memory: 1200Gi, nvidia.com/gpu: 8}
    limits:   {cpu: "96", memory: 1200Gi, nvidia.com/gpu: 8}
  volumeMounts:
  - {name: dshm, mountPath: /dev/shm}       # NCCL needs a large shared-memory area
  - {name: model-cache, mountPath: /models} # node-local NVMe cache (§5.5)
volumes:
- {name: dshm, emptyDir: {medium: Memory, sizeLimit: 64Gi}}
- {name: model-cache, hostPath: {path: /nvme/models}}
nodeSelector: {gpu.example.com/type: h100-sxm}
tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]

Each line encodes a lesson. The image is referenced by digest, so every replica runs identical bytes. The GPU request of eight forces the scheduler to place the pod on a node with eight free GPUs, and since all eight must share an NVSwitch, on a single eight-GPU server. The shared-memory volume exists because container runtimes give /dev/shm only 64 MB by default, which is far too small for NCCL and for engines that pass tensors between processes, and this default has caused countless mysterious hangs. The model cache mounts the node's NVMe so that weights load from the local tier (§5.5). The node selector and toleration express placement: GPU nodes carry a taint that repels ordinary pods (so that a log shipper does not occupy a GPU node's scheduling capacity), and GPU pods carry the matching toleration. Richer placement uses affinity rules: "schedule near pods with label X" or, more commonly for reliability, anti-affinity and topology spread constraints, "spread replicas evenly across zones and racks" (Chapter 13).

Worked example — CPU requests can strand GPUs

Setup. Atlas-Small runs one Llama 3 8B replica per H100. A node has 8 GPUs, 192 vCPUs and 2,048 GiB of memory, of which the system reserves 8 vCPUs and 64 GiB for the kubelet, runtime and agents, leaving 184 vCPUs and 1,984 GiB allocatable.

A generous request. An engineer, having seen CPU-bound engines (Vol. I §12.2), sets each pod to request 32 vCPUs and 256 GiB. The scheduler can fit only \(\lfloor184/32\rfloor=5\) pods per node: three GPUs on every node are stranded—free, but unusable because no pod that wants them fits in the remaining CPU. Across 60 nodes, 180 H100s sit idle, about $3.9 million a year at $2.50 per GPU-hour.

A balanced request. Requests should divide the node's allocatable resources by the number of GPUs: \(184/8=23\) vCPUs and \(1984/8=248\) GiB per single-GPU pod. Setting 22 vCPUs and 240 GiB fits all eight pods, with a little room for sidecars.

Lesson. On a GPU node, every other resource should be requested in proportion to the GPUs a pod takes, so that the GPU is the binding resource. Chapter 7 generalises this into the fragmentation problem of multi-resource bin packing.

Pods are rarely created directly. A Deployment declares a pod template and a replica count, and manages a ReplicaSet that keeps that many pods running; changing the template triggers a rolling update, which we examine in §6.7. A Service gives a stable virtual address and DNS name to the set of pods matching a label selector, so that clients and routers can find replicas as they come and go; for LLM serving, the router of Vol. I §27.2 usually needs to know individual replicas, so it watches the Service's endpoints directly rather than relying on Kubernetes' simple load balancing. ConfigMaps and Secrets hold configuration and credentials. Namespaces (a Kubernetes concept, unrelated to kernel namespaces) partition objects among teams, with ResourceQuotas limiting what each may request—"the research namespace may use at most 512 GPUs"—which Chapter 7 develops into a scheduling policy. And because a Kubernetes object is just structured data, operators extend the system with custom resources and their own controllers; most AI platforms (KServe, LeaderWorkerSet, Ray, Dynamo, llm-d) are sets of custom resources and controllers layered on these primitives (Chapter 8).

6.4 Exposing accelerators: device plugins and Dynamic Resource Allocation

Kubernetes knows about CPUs and memory natively. Everything else—GPUs, NICs, FPGAs—is exposed through extensions, and the design of those extensions has shaped AI on Kubernetes. The first mechanism, the device plugin framework, arrived in 2017 (alpha in Kubernetes 1.8). A device plugin is a small daemon on each node that tells the kubelet how many devices of a named resource the node has—for NVIDIA's plugin, nvidia.com/gpu: 8—and, when a pod is assigned some of them, tells the runtime which device files and environment variables to give the container. The scheduler treats the resource as an integer count, like CPU, and places pods wherever enough units are free.

Integer counts were enough for "give me one GPU" and became awkward for everything else. A count cannot say which GPUs a pod should get: whether they share an NVSwitch, whether they are close to particular NICs and CPU sockets, whether they are H100s or H200s, or how much memory they have. It cannot express sharing (MIG slices or time-sliced replicas were bolted on by advertising each slice as a separate resource name, such as nvidia.com/mig-3g.40gb, which made the scheduler's view rigid). It cannot describe devices that span nodes, such as the 72-GPU NVLink domain of a GB200 rack. Kubernetes added a Topology Manager on each node to align CPU, memory and device assignments to the same NUMA node, but cluster-wide, the scheduler remained blind to device attributes.

Dynamic Resource Allocation (DRA), developed from 2022 and generally available in Kubernetes 1.34 in 2025, replaces counts with structured descriptions. A DRA driver on each node publishes a ResourceSlice listing its devices with typed attributes—model, memory, MIG profile, PCIe and NVLink topology, driver version—and capacities. Cluster administrators define DeviceClasses, and workloads create ResourceClaims that select devices with expressions over those attributes ("two GPUs with at least 80 GB of memory on the same NVLink domain") and can be shared between pods. Because the attributes are structured, the scheduler itself can evaluate claims and allocate specific devices during scheduling, rather than leaving the choice to the node. NVIDIA's DRA driver uses this to expose GPUs and MIG partitions with their properties and to represent multi-node NVLink domains, so that the pods of one replica on a GB200 NVL72 rack can be placed on the same domain and granted the cross-node memory channels they need.

Atlas's fleet mixes H100 and H200 nodes, some partitioned with MIG for small isolated models (§3.4), and GB200 racks for DeepSeek-V3; with device plugins, each of these needs its own resource names, labels and taints, and the scheduler cannot reason about NVLink or NIC locality. With DRA, a replica's claim can state what it needs, and the scheduler can find it. Whatever the allocation mechanism, the devices only work if the node's software stack is correct, and that stack is more intricate than it looks.

6.5 The software stack of a GPU node

Figure 6.3 shows the layers of software that must be present, in compatible versions, for a pod to run a CUDA program on a GPU node. From the bottom: the GPU firmware (and NVSwitch and NIC firmware); the kernel-mode driver loaded into the host kernel; on NVSwitch systems, the Fabric Manager service that configures the NVLink switch fabric (without it, multi-GPU NVLink traffic fails); on InfiniBand or RoCE nodes, the NIC drivers and the kernel modules that let NICs access GPU memory directly (GPUDirect RDMA); the container toolkit that injects user-mode driver libraries and device files into containers; the device plugin or DRA driver; DCGM (Data Center GPU Manager), which monitors health and exports metrics such as utilisation, memory usage, temperatures, power, ECC errors and NVLink errors; and, in the container image, the CUDA toolkit libraries, NCCL and the engine.

Keeping these layers consistent on thousands of nodes, through driver upgrades and node replacements, is itself an orchestration problem, and NVIDIA's GPU Operator solves it the Kubernetes way: it runs the driver, toolkit, device plugin or DRA driver, DCGM exporter, MIG manager and validation workloads as containers managed by controllers, so that a node joining the cluster is configured automatically and an upgrade is a change to a declared version that the operator rolls out node by node. Cloud providers' managed Kubernetes services offer GPU node images with these components preinstalled, and either approach works; what matters is that versions are declared, tested together and upgraded deliberately, with the driver upgraded before images that need newer CUDA.

DCGM deserves a special mention, because GPU health is the foundation of reliability at scale (Chapter 13). GPUs fail in ways that do not crash the machine: an HBM page develops uncorrectable errors, an NVLink lane degrades, a GPU falls off the PCIe bus, clocks throttle because of a cooling fault. The driver reports many of these as Xid error codes in the kernel log, and DCGM can run active diagnostics. A node agent that watches these signals and cordons a node—marks it unschedulable—and drains its pods when a GPU is unhealthy turns silent degradation into a clean replacement. Health is per GPU, but many replicas use several machines, which raises the question of how Kubernetes handles a replica that spans nodes.

6.6 Replicas that span nodes

Kubernetes' basic objects assume that each replica is one pod on one node. Several inference deployments break that assumption. A model too large for one eight-GPU server in the chosen precision—Llama 3 405B in BF16, or DeepSeek-V3 with wide expert parallelism on H100s—needs a group of pods on several nodes, connected over the back-end network, that together form one replica. Disaggregated serving (Vol. I Chapter 13) pairs prefill and decode workers that may be scaled separately but must find each other. And distributed engines typically need a leader process that receives requests and coordinates, plus workers that execute shards.

Treating each pod of such a group as an independent replica goes wrong in three ways. The scheduler may place some pods of a group and not others, leaving GPUs reserved for a replica that cannot run (Chapter 7 develops this "gang scheduling" problem). A failure of one pod leaves the others running but useless, unless something restarts the whole group. And a rolling update that replaces pods one at a time produces groups with mixed versions, which may not even communicate. The LeaderWorkerSet API (LWS), developed under the Kubernetes SIG Apps project from 2024 for exactly this purpose, makes the group the unit: an LWS object declares a leader template, a worker template and a group size, and replicates groups; each group's pods share an identity and network names so that workers can find their leader, a failure of any pod restarts the whole group by default, and rolling updates replace whole groups. Figure 6.4 shows the structure. Related APIs—JobSet for batch, KubeRay for Ray clusters—solve the same problem in other settings.

Grouping has a cost that a mathematician can compute immediately. If each node fails independently at rate \(\lambda_f\) per hour, a replica that needs all \(g\) of its nodes fails at rate \(g\lambda_f\), and if each failure takes the whole group out of service for a recovery time \(t_{\text{rec}}\), the fraction of time the replica is unavailable is about \(g\lambda_ft_{\text{rec}}\) when this is small. A four-node replica is down four times as often as a one-node replica, and its recovery takes longer because four nodes' worth of weights must be reloaded and a multi-node engine re-initialised. Chapter 13 turns this into a sizing rule for spare capacity; here it is the reason why large-memory hardware (H200, B200, MI300X) and rack-scale NVLink domains, which shrink \(g\), make large models operationally easier as well as faster.

Drill 6.1 — How often is a multi-node replica down?

Suppose each eight-GPU node suffers a fault that takes it out of service on average once every 60 days, and a replica's recovery (replacement node, weight load, initialisation, warm-up) takes 10 minutes. What fraction of time is a one-node Llama 3 70B replica unavailable, and a four-node DeepSeek-V3 replica? How many spare DeepSeek-V3 replicas does a pool of 20 need to keep 20 serving at least 99.9% of the time?

Solution. \(\lambda_f=1/1440\) per hour. One node: unavailability \(\approx(1/1440)\times(1/6)\approx1.2\times10^{-4}\). Four nodes: \(4\times1.2\times10^{-4}\approx4.6\times10^{-4}\). In a pool of \(n\) replicas, the number down at a random moment is approximately Poisson with mean \(n\times4.6\times10^{-4}\); with 21 replicas the mean is about 0.0097, and \(\Pr(\ge2\text{ down})\approx0.0097^2/2\approx4.7\times10^{-5}\), so one spare already keeps at least 20 serving more than 99.99% of the time. The calculation is cheap here because recovery is fast; with a two-hour recovery (no caching, slow cold start), the mean rises twelve-fold to about 0.12 and \(\Pr(\ge2)\approx0.0066\), so two spares would be needed for 99.9%.

6.7 Probes, rollouts and graceful termination for LLM servers

Kubernetes manages a container's lifecycle through three kinds of probe—periodic checks the kubelet runs against the container—and a shutdown protocol. Their defaults were designed for web services that start in seconds and answer requests in milliseconds, and an LLM server that takes a minute to start and streams responses for minutes violates both assumptions. Many production incidents in LLM serving are probe and shutdown misconfigurations.

A startup probe tells the kubelet when the container has finished starting; until it succeeds, the other probes are suspended. For an engine whose cold start takes 35 seconds on a good day and several minutes on a bad one (cache miss, slow storage), the startup probe must allow a generous window—often ten minutes or more—or the kubelet will kill the container mid-load and restart it, forever. A readiness probe tells Kubernetes whether the pod should receive traffic; a failing readiness probe removes the pod from its Service's endpoints without killing it. For an LLM server, "ready" should mean "weights loaded, engine warmed up, and able to accept work", and some platforms also report not-ready when the engine is saturated so that new requests go elsewhere—though load-aware routing (Vol. I §27.2) is a better tool for that. A liveness probe tells the kubelet whether the container is stuck and should be restarted. It is the most dangerous of the three: if it checks an endpoint served by the same busy event loop that runs inference, a long prefill or a burst of load can delay its answer beyond the timeout, and the kubelet then kills a healthy, busy replica—making the overload worse. Liveness checks for engines should be cheap, served independently of the inference loop, and lenient.

Graceful termination is the other half. When a pod is deleted—during a rollout, a scale-down or a node drain—the kubelet sends the container a termination signal, waits up to terminationGracePeriodSeconds (30 seconds by default), and then kills it. A well-behaved engine responds to the signal by failing readiness (so no new requests arrive), finishing the requests in flight, and exiting. The question is how long that takes, and the answer contains a subtlety. A request that is in flight at the moment of termination is not a typical request: long requests occupy the engine for longer, so they are over-represented among the requests in flight at any instant. This is the inspection paradox.

For the mathematician — the inspection paradox and residual generation time

Let generation times \(\Gamma\) be independent with distribution \(F\) and mean \(\mathbb E[\Gamma]\). Sample a request that is in progress at a random instant. Its total length has the length-biased density \(s\,dF(s)/\mathbb E[\Gamma]\), and its remaining time \(\Gamma_{\text{res}}\) has the equilibrium residual distribution

\[ \Pr(\Gamma_{\text{res}}>x)=\frac{1}{\mathbb E[\Gamma]}\int_x^{\infty}\bigl(1-F(u)\bigr)\,du , \]

with mean \(\mathbb E[\Gamma_{\text{res}}]=\mathbb E[\Gamma^2]/(2\,\mathbb E[\Gamma])\). For heavy-tailed \(F\)—and output lengths are heavy-tailed, especially with reasoning models—\(\mathbb E[\Gamma^2]/\mathbb E[\Gamma]\) can greatly exceed \(\mathbb E[\Gamma]\), so the requests in flight at shutdown take far longer to finish than a typical request. A grace period sized to the median request time kills a large fraction of in-flight work.

Figure 6.5 makes this concrete. It plots, from simulation, the fraction of in-flight requests that would be cut off by a given grace period, for two workloads at a TPOT of 30 ms: a chat workload with lognormal output lengths of median 400 tokens, and a reasoning workload with median 2,000 tokens. A typical chat response streams for 12 seconds, but a 30-second grace period cuts off about one in five of the requests in flight. For the reasoning workload, a 30-second grace period cuts off nearly three-quarters, and even five minutes leaves one in ten unfinished.

Figure 6.5 suggests three remedies, usually combined. First, set the grace period from the residual distribution of the workload, not from intuition: for chat, two to three minutes cuts off under 1%; for reasoning, ten minutes or more may be needed. Second, make interruption cheap: a client or gateway that can resume a stream on another replica—by resending the prompt plus the tokens already generated, which a prefix cache makes inexpensive—turns a cut-off request into a short pause rather than a failure (Chapter 11). Third, drain before terminating: a rollout controller that removes a replica from the router's pool well before deleting its pod lets in-flight work finish while no new work arrives. Kubernetes' PodDisruptionBudgets, which limit how many pods of a set may be voluntarily disrupted at once, protect capacity during node maintenance.

Drill 6.2 — The mean residual of a lognormal

For lognormal generation times with median \(m_\Gamma\) and log-standard deviation \(\sigma\), \(\mathbb E[\Gamma]=m_Se^{\sigma^2/2}\) and \(\mathbb E[\Gamma^2]=\mathbb E[\Gamma]^2e^{\sigma^2}\). Compute the mean generation time and the mean residual time of in-flight requests for the chat workload (median 400 tokens, \(\sigma=0.9\)) and the reasoning workload (median 2,000 tokens, \(\sigma=1.0\)) at 30 ms per token.

Solution. The mean residual is \(\mathbb E[\Gamma^2]/(2\mathbb E[\Gamma])=\tfrac12\mathbb E[\Gamma]e^{\sigma^2}\). Chat: \(\mathbb E[\Gamma]=12\text{ s}\times e^{0.405}\approx18\) s, and the mean residual is \(\tfrac12\times18\times e^{0.81}\approx20\) s—longer than the mean request itself. Reasoning: \(\mathbb E[\Gamma]=60\text{ s}\times e^{0.5}\approx99\) s, and the mean residual is \(\tfrac12\times99\times e\approx134\) s. A grace period equal to even the mean residual would still cut off a large fraction, because the residual distribution is itself heavy-tailed; that is why Figure 6.5 needs minutes for chat and ten minutes for reasoning.

Grace periods interact with rollouts. A Deployment's rolling update replaces pods in batches controlled by maxSurge (how many extra pods may be created above the desired count) and maxUnavailable (how many pods may be missing). Each batch costs a drain time plus a cold start, so the duration of a rollout of \(n_r\) replicas with batches of \(n_b\) is about \(\lceil n_r/n_b\rceil(t_{\text{drain}}+t_{\text{cold}})\). Figure 6.6 shows how strongly this depends on the cold-start time of Chapter 5.

Figure 6.6 connects the plumbing of Chapter 5 to the safety practices of Chapter 13. With fifteen-minute cold starts, a rollout of 100 replicas in batches of 2% takes thirteen hours, so in practice teams roll out 20–25% at a time, which removes a quarter of capacity at once and lets a bad version reach a quarter of traffic before anyone notices. With cold starts of half a minute, 2% batches finish in about eighty minutes. The engineering that shortens cold starts therefore also makes deployments safer.

Worked example — configuring Atlas's 70B replicas

Startup probe. Typical cold start 35 s on a warm node with cached weights, worst case about 6 minutes (object-storage fallback, cold compilation): allow 15 minutes (e.g. check every 10 s, 90 failures).

Readiness. Ready when the engine has loaded weights, captured graphs and answered a warm-up request; the router additionally reads queue depth and KV usage from the engine's metrics for load-aware routing.

Liveness. A lightweight endpoint served by a separate thread, which fails only if the engine's step counter has not advanced for several minutes while requests are queued; timeout 10 s, five failures before restart.

Termination. Chat traffic, output P99 about 3,000 tokens at 30 ms, but in-flight residuals are longer: from Figure 6.5, 180 s leaves about 0.5% unfinished. Set a pre-stop hook that fails readiness and waits for the router to stop sending traffic (10 s), then terminationGracePeriodSeconds: 240; the gateway resumes any stream that is still cut off.

Rollout. A first canary batch of 2% (6 replicas) held for 30 minutes of metric comparison, then maxSurge of about 20 replicas (6%) with maxUnavailable: 0 where spare GPUs allow (surge capacity instead of reduced capacity), and an automated pause on SLO regression. With 311 replicas at peak that is about 16 further batches at about 5 minutes each including drains: about two hours in all.

Disruption budget. At most 5% of the tier's replicas voluntarily disrupted at once, so node maintenance cannot drain a large part of the fleet simultaneously.

6.8 What Kubernetes does not do for AI

Kubernetes is the most common substrate for AI serving, but it is not complete, and it is worth stating its gaps clearly, since each is filled by a component discussed elsewhere in this volume. Its default scheduler places one pod at a time and has no notion of a group that must be placed together or not at all, nor of fair sharing of scarce GPUs among teams, nor of preempting low-priority training for high-priority inference in a controlled way; batch-scheduling add-ons such as Kueue, Volcano and NVIDIA's KAI scheduler (and, outside Kubernetes, Slurm) provide these, and Chapter 7 is devoted to them. It knows nothing about models, adapters, tokens or prefix caches, so model deployment, autoscaling on token-level metrics and cache-aware routing are built on top by serving platforms (Chapter 8). Its control plane has scale limits—the project's tested limit is about 5,000 nodes per cluster, and although cloud providers have demonstrated much larger clusters, large fleets are usually split across many clusters and regions, which requires a layer above Kubernetes (Chapter 12). And its abstractions are per-cluster and per-region, so global concerns—capacity across regions, failover, data residency—are outside it.

There are also alternatives. High-performance computing centres and many training clusters use Slurm, a batch scheduler with mature gang scheduling, topology awareness and fair-share accounting, and some organisations run Slurm and Kubernetes side by side or Slurm on top of Kubernetes. Ray provides a distributed programming model with its own scheduler, widely used for batch inference and reinforcement-learning rollouts (Chapter 19), usually deployed on Kubernetes through KubeRay. For online serving at scale, however, Kubernetes plus a set of AI-specific extensions has become the default, and the most important of those extensions is a scheduler that understands GPUs.

Looking ahead

We now know how a replica is packaged, how Kubernetes turns declarations into running pods, how GPUs and multi-node domains are allocated to them, and how to start, check, update and stop LLM servers safely. We repeatedly met the limits of Kubernetes' default scheduler: it places pods one at a time, cannot guarantee that all pods of a multi-node replica are placed together, does not prevent GPUs from being fragmented into unusable remnants, and has no policy for sharing a scarce cluster among inference, training and research teams. How should a GPU cluster be scheduled, and what does it cost to do it badly? Chapter 7 answers these questions.

Chapter summary

  • A container is a process with namespaces (restricted views of files, processes, network) and cgroups (resource budgets), rooted in an image; containers share the host kernel and start in milliseconds, with weaker isolation than VMs.
  • GPUs in containers use the host's kernel-mode driver; matching user-mode libraries are injected by the container toolkit; the host driver must support the image's CUDA version.
  • Kubernetes is declarative: desired state in etcd behind the API server, controllers reconcile, the scheduler binds pods to nodes, kubelets run them. It is a control plane; serving must survive its outages.
  • LLM pod specs need: GPU requests (integers), image digests, large /dev/shm, node-local model caches, taints/tolerations for GPU nodes, and spread constraints across failure domains.
  • Device plugins expose GPUs as integer counts; DRA (GA in 1.34, 2025) exposes structured device attributes and claims, enabling topology-aware placement, sharing and multi-node NVLink domains.
  • The node stack—firmware, driver, Fabric Manager, NIC and GPUDirect modules, container toolkit, device plugin/DRA, DCGM—must be version-consistent; the GPU Operator manages it; DCGM and Xid signals drive health-based cordoning.
  • Multi-node replicas are groups (LeaderWorkerSet): placed, failed and updated together; a \(g\)-node replica fails \(g\) times as often, so fewer, larger devices simplify operations.
  • Startup probes must allow long cold starts; liveness probes must not kill busy engines; in-flight requests are length-biased (inspection paradox), so grace periods must follow the residual distribution—minutes, not 30 s—and streams should be resumable.
  • Rollout time \(\approx\lceil n_r/n_b\rceil(t_{\text{drain}}+t_{\text{cold}})\): fast cold starts allow small, safe batches.

Warm-up What is a container, and how does it differ from a VM?

A container is a process (or group) whose view of the system is restricted by kernel namespaces (mount, PID, network, UTS, IPC, user) and whose resources are capped by cgroups, with a root file system from an image of layered archives. It shares the host kernel, so it starts in milliseconds, has no second-kernel overhead and runs natively. A VM runs a full guest kernel on virtualised hardware via a hypervisor: slower to boot, more overhead, stronger isolation. Containers' shared kernel means a kernel exploit can escape; for untrusted multi-tenancy, put containers in VMs or sandboxes (gVisor, Firecracker).

Warm-up How does a container get access to a GPU?

The kernel-mode driver is loaded on the host. When the scheduler assigns GPUs to a pod (via the device plugin or DRA), the kubelet and container runtime expose the corresponding device files (/dev/nvidia*) into the container and, via the NVIDIA Container Toolkit hook, mount the user-mode driver libraries (libcuda etc.) that exactly match the host driver. The image supplies the CUDA toolkit, NCCL and the application. The host driver must support the image's CUDA version (newer drivers run older CUDA; not the reverse).

Warm-up Describe Kubernetes' architecture and its reconciliation model.

etcd (Raft-replicated key–value store) holds all state; the API server fronts it, validates, authorises and serves watches; controllers watch objects and act to make actual state match desired state (ReplicaSet controller creates or deletes pods); the scheduler binds unscheduled pods to nodes based on requests, constraints and scores; each node's kubelet starts bound pods via the container runtime, runs probes and reports status. Users declare desired state (Deployment with N replicas); controllers converge to it from any starting state, which makes the system self-healing. It is purely a control plane.

Core Write the key parts of a pod spec for an 8-GPU LLM replica and explain each.

Image by digest (reproducibility, exact rollback); args for model path and TP size; resources: nvidia.com/gpu: 8 (request = limit; forces one 8-GPU node), CPU and memory sized for engine CPU work and pinned buffers; /dev/shm as a memory-backed emptyDir of tens of GB (NCCL, IPC); node-local model cache mount (NVMe); node selector or DRA claim for GPU type; toleration for the GPU-node taint; topology spread across zones/racks; startup probe with a long window; readiness tied to weights loaded and warm-up; lenient, independent liveness; preStop hook and long terminationGracePeriodSeconds; environment for NCCL and network interfaces; security context. For multi-node replicas use LeaderWorkerSet.

Core Why was Dynamic Resource Allocation introduced, and what does it enable for inference?

Device plugins advertise devices as integer counts, so the scheduler cannot see device attributes (model, memory, MIG profile), topology (NVLink domain, NIC/NUMA proximity), sharing, or devices that span nodes; workarounds used many resource names and labels. DRA (GA in Kubernetes 1.34) has drivers publish ResourceSlices with typed attributes; admins define DeviceClasses; workloads create ResourceClaims with selectors (e.g. two GPUs ≥ 80 GB on one NVLink domain) that can be shared; the scheduler allocates specific devices. For inference: mixed fleets (H100/H200/MIG/GB200) under one scheduler, topology-aware placement of TP groups and NICs, MIG partitions as allocatable devices, and multi-node NVLink domains (NVL72) for wide-EP replicas.

Core Our rollouts kill user requests mid-stream. Diagnose and fix.

Likely: default 30 s terminationGracePeriodSeconds, no preStop drain, router still sending to terminating pods, and long or heavy-tailed generations. In-flight requests are length-biased (inspection paradox): their residual time distribution has mean \(\mathbb E[\Gamma^2]/(2\mathbb E[\Gamma])\), much longer than typical; with chat at 30 ms TPOT, 30 s cuts off about 20% of in-flight requests, with reasoning about 70%. Fix: preStop hook that fails readiness and waits for the router to deregister; grace period from the measured residual distribution (minutes; longer for reasoning); gateway-level resumable streams (resend prompt + generated tokens to another replica, cheap with prefix caching); drain via the router before deletion; surge-based rollouts so capacity does not drop; PodDisruptionBudgets.

Core How should startup, readiness and liveness probes be configured for an LLM server?

Startup: generous window covering worst-case cold start (weights from object storage, cold compilation)—e.g. 10–15 minutes—so the kubelet does not kill a loading engine. Readiness: true only when weights are loaded, graphs captured and a warm-up request succeeds; false during drain; optionally false when saturated, though load-aware routing is better. Liveness: cheap endpoint on a separate thread that checks the engine is making progress (step counter advancing when work is queued), with long timeouts and several failures before restart; never tied to request latency, otherwise overload triggers restarts that worsen overload.

Core What is on a GPU node's software stack, and what usually breaks?

Firmware (GPU, NVSwitch, NIC, BMC); host kernel with GPU kernel-mode driver, NIC drivers, GPUDirect RDMA module; Fabric Manager (NVSwitch systems, must match driver); container runtime and NVIDIA Container Toolkit; device plugin or DRA driver; DCGM and exporter; MIG manager; in the image, CUDA toolkit, NCCL, engine. Breakages: image CUDA newer than host driver; Fabric Manager mismatch after driver update; missing GPUDirect module (slow or failed RDMA); MIG configuration drift; DCGM not catching degraded GPUs; firmware inconsistencies across nodes. Mitigate with the GPU Operator or curated node images, declared versions tested together, staged upgrades (drivers before images), and health checks that cordon bad nodes.

Deep-dive Derive the grace period needed to finish 99% of in-flight requests, and explain why it exceeds the P99 request duration's intuition.

Let generation time \(\Gamma\) have CDF \(F\). A request in flight at a random instant has length-biased total length and residual \(\Gamma_{\text{res}}\) with \(\Pr(\Gamma_{\text{res}}>x)=\frac{1}{\mathbb E[\Gamma]}\int_x^\infty(1-F(u))du\). Choose grace \(g\) with \(\Pr(\Gamma_{\text{res}}>g)\le0.01\). For heavy tails (lognormal with σ≈1, reasoning outputs), the integral decays slowly: the residual's mean \(\mathbb E[\Gamma^2]/(2\mathbb E[\Gamma])\) can exceed the mean of \(\Gamma\) many-fold. Numerically for lognormal chat (median 400 tokens, σ=0.9, 30 ms/token), \(\Pr(\Gamma_{\text{res}}>30\text{ s})\approx0.2\), \(\Pr(\Gamma_{\text{res}}>120)\approx0.014\), \(\Pr(\Gamma_{\text{res}}>180)\approx0.005\); reasoning (median 2,000, σ=1) needs about 10 minutes for 97%. Intuition from "most requests finish in 12 s" is wrong because sampling at an instant over-represents long requests.

Deep-dive How would you deploy DeepSeek-V3 across four 8-GPU nodes on Kubernetes?

Use LeaderWorkerSet with group size 4: leader pod (API, scheduling, rank 0) plus three workers; each pod requests 8 GPUs and the back-end RDMA NICs (DRA claim or RDMA device plugin), large /dev/shm, host networking or a CNI that exposes RDMA devices; placement in the same network pod or rail group (affinity or DRA topology) to minimise hops; gang scheduling (Kueue/KAI or LWS with a gang-aware scheduler) so all four are placed together; group restart on any failure; group-level rolling updates; weights pre-cached on NVMe of the pool's nodes or broadcast from peers; startup probe window for multi-node init; router sees each group as one replica. Consider disaggregated prefill and decode groups as separate LWSs with a KV-transfer layer (NIXL). Size spares for \(g=4\) failure rate.

Deep-dive Why do multi-node replicas hurt availability, and how do you quantify and mitigate it?

A replica needing all \(g\) nodes fails whenever any does: rate \(g\lambda_f\); unavailability ≈ \(g\lambda_ft_{\text{rec}}\), with \(t_{\text{rec}}\) also larger (more weights to reload, multi-node init). With node MTBF 60 days and 10-minute recovery, a 4-node replica is unavailable about 0.05% of the time; with 2-hour recovery about 0.55%. Model replicas down in a pool as Poisson and size spares to meet the target. Mitigate: shrink \(g\) (bigger-memory GPUs, FP8/FP4, NVL72 racks), speed recovery (cached weights, peer broadcast, snapshots, hot spare nodes), keep spare groups warm, isolate faults (restart only the engine, not reschedule, for transient errors), and spread groups across failure domains.

Design Design the Kubernetes setup for Atlas's three tiers across H100, H200 and GB200 nodes.

Node pools per hardware type with taints; GPU Operator (or managed node images) with pinned driver/toolkit/DRA versions; DRA classes for H100, H200, MIG profiles and GB200 NVLink domains. 8B tier: Deployment per model with 1-GPU pods (or MIG claims for isolated tenants), spread across zones and racks. 70B tier: Deployments of 8-GPU pods on H100 (TP8) or 2–4-GPU pods on H200, image digests, NVMe model caches. DeepSeek-V3: LeaderWorkerSets on GB200 racks with domain-aware claims, disaggregated prefill/decode sets. Probes and grace periods per tier (reasoning needs long grace). Gang-aware batch scheduler (Kueue/KAI) for multi-node groups and for batch work in troughs at low priority. PodDisruptionBudgets; health agent cordoning on DCGM/Xid; cluster autoscaler with warm pools; serving platform on top for routing and autoscaling; multiple clusters per region for blast radius and control-plane scale.

Design How do you upgrade GPU drivers across a 2,000-node fleet without downtime?

Test the new driver with current and next images, Fabric Manager, NCCL and engines on canary nodes of each hardware type, including performance and multi-node tests. Roll out by failure domain: cordon a small batch of nodes, drain pods gracefully (respecting PodDisruptionBudgets and long grace periods), upgrade driver and Fabric Manager (GPU Operator handles it as a declared version), validate with DCGM diagnostics and a smoke workload, uncordon. Keep spare capacity to absorb drained nodes; pace to the slowest of drain and cold start; pause automatically on error-rate or performance regressions. Only after drivers are upgraded fleet-wide, roll out images needing newer CUDA. Keep the previous driver available for rollback.

Core What are Kubernetes' limits for AI workloads, and what fills the gaps?

Default scheduler: one pod at a time, no gang semantics, limited topology awareness, no fair-share with borrowing or controlled preemption among teams—filled by Kueue, Volcano, KAI scheduler, or Slurm. No model awareness: deployment of models and adapters, token-based autoscaling, cache-aware routing—filled by serving platforms (KServe, llm-d, Dynamo, AIBrix, Ray Serve). Control-plane scale (about 5,000 nodes officially tested; larger with provider tuning)—use many clusters with a fleet layer. Per-cluster, per-region scope—global traffic management and capacity across regions built above. Device allocation was coarse until DRA. Ray and Slurm serve batch and training patterns.

Deep-dive How do cold-start time and batch size interact in rolling updates, and what is the safety argument for small batches?

Rollout duration ≈ \(\lceil n_r/n_b\rceil(t_{\text{drain}}+t_{\text{cold}})\). With 15-minute cold starts, 2% batches of 100 replicas take about 13 hours, so teams use 20–25% batches—removing a quarter of capacity (or needing a quarter more surge) and exposing a quarter of traffic to a possibly bad version before detection. With 35-second cold starts, 2% batches take about 80 minutes. Smaller batches limit blast radius: if a regression is detected after the first batch, only 2% of traffic was affected, and statistical detection on canary metrics can happen before wider exposure. Thus investing in cold-start speed buys both capacity (less surge/headroom) and safety (progressive delivery).

Warm-up What is a PodDisruptionBudget and why does an inference tier need one?

A PodDisruptionBudget limits how many pods of a labelled set can be voluntarily disrupted at once (by drains, node upgrades, cluster autoscaler scale-down), e.g. "at least 95% available" or "at most 5 unavailable". Without it, a node-maintenance operation could drain many replicas of a tier simultaneously, collapsing capacity. With long grace periods and slow cold starts, LLM pods take a long time to come back, so PDBs are essential to keep maintenance from becoming an outage. They do not protect against involuntary failures (node crashes), which spare capacity must absorb.
