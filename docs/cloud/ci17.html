Volume II · Part V · Beyond Chat — Chapter 17

Agents and Compound AI Systems

An agent does not answer a request with one model call. It plans, calls tools—search, code execution, databases, other services—reads their results and calls the model again, often dozens of times, holding a growing context and session state throughout. The unit of work becomes a program, untrusted code must be executed somewhere safe, and the latency, cost and reliability of a task are products of many steps. This chapter develops the infrastructure for agents: context growth and caching, tool protocols, sandboxes, session state across tool calls, program-aware scheduling, and the economics and reliability of long workflows.

Why this chapter

By 2025, a large and growing share of LLM tokens was consumed not by people chatting but by programs calling models in loops: coding agents that read a repository, edit files and run tests; research agents that search and read dozens of pages; customer-service agents that query order systems and issue refunds; computer-use agents that operate a browser. Each user request to such a system can trigger tens to hundreds of model calls and tool invocations, run for minutes, and consume hundreds of thousands of tokens. The engineering of Volume I—batching, caching, scheduling—was designed around independent requests. Agents violate that independence: the calls of one task are sequential and share a growing prefix; between calls the model waits for tools whose latency it does not control; and the task's value lies in its final result, not in the latency of any single call.

The infrastructure consequences are distinctive, and interviews for AI-platform roles ask about them: "why does an agent's cost grow quadratically with its steps, and how do you fix it?", "how would you run model-generated code safely for a million users?", "what should the engine do with a sequence's KV cache while a tool runs for thirty seconds?", "how would you schedule requests from agents differently from chat?", "a 40-step workflow fails 30% of the time—why, and what do you do?". This chapter answers them.

We begin by treating an agent as a program and quantifying its context growth (§17.1), then describe tool interfaces including the Model Context Protocol (§17.2) and sandboxes for code execution (§17.3). We analyse what to do with KV state while tools run (§17.4), how schedulers should treat programs (§17.5), what agent loops cost (§17.6), and how to make multi-step workflows reliable (§17.7), closing with agent platforms as infrastructure (§17.8).

17.1 From a request to a program

The basic agent loop, popularised by the ReAct pattern of Yao and colleagues (2022)[1], alternates reasoning and acting: the model receives a task and a list of available tools; it produces either a final answer or a tool call (a structured request such as "search for X" or "run this code"); the system executes the tool and appends its result to the context; and the model is called again with the extended context. Figure 17.1 shows the loop and the components around it.

The loop has a cost structure that surprises people the first time they see it. Suppose a task starts with a context of \(n_0\) tokens (system prompt, tool descriptions, task), and each step adds \(n_{\Delta}\) tokens (the model's output plus the tool's result). At step \(i\) the context is \(n_0+(i-1)n_{\Delta}\) tokens. If every model call re-processes its whole context, the total prefill work over \(n_{\text{step}}\) steps is

\[ \sum_{i=1}^{n_{\text{step}}}\bigl(n_0+(i-1)n_{\Delta}\bigr)=n_{\text{step}}n_0+\tfrac12n_{\text{step}}(n_{\text{step}}-1)n_{\Delta}, \]

which grows quadratically in the number of steps. With prefix caching (Vol. I Chapter 10), each call re-uses the cached KV of everything before it and prefills only the new \(n_{\Delta}\) tokens, so the total becomes \(n_0+(n_{\text{step}}-1)n_{\Delta}\), linear in the number of steps. Figure 17.2 shows the difference for a typical coding agent.

Figure 17.2 is the single most important fact about serving agents. An agent framework or serving stack that loses the prefix cache between steps—because consecutive calls land on different replicas, because the context is rebuilt with a timestamp or reordered tools at the top, or because the KV was evicted while a tool ran—pays the red curve instead of the green one, an order of magnitude more compute for long tasks. Keeping each task's calls on the same replica (session affinity, Vol. I §27.2), keeping its context append-only, and keeping its KV available across tool calls (§17.4) are therefore the first rules of agent serving. Token-priced APIs reflect the same fact: providers that offer cached-input discounts (§10.4) make long agent tasks affordable only if the agent's context is structured to hit the cache.

17.2 Tool calling and the Model Context Protocol

A tool call is a piece of structured output: the model emits, instead of free text, an object naming a tool and its arguments in a schema the application declared—typically JSON Schema. Models are trained to produce such calls, and engines enforce them with the grammar-constrained decoding of Vol. I §4.6, which guarantees syntactically valid output. Modern APIs let models emit several tool calls in one turn, which the orchestrator can run in parallel, cutting wall-clock time when the calls are independent (searching several sources at once, reading several files).

Every application used to wire its own tools to its own model integration, an \(N\times M\) problem between models and tools. The Model Context Protocol (MCP), published by Anthropic in November 2024 and adopted widely across the industry in 2025, standardised the interface: an MCP server exposes tools (callable functions), resources (readable data) and prompts to any MCP client (an agent application), over a JSON-RPC protocol carried on local standard input/output or on HTTP with streaming. A company can then expose its ticketing system, its code repository or its database once, as an MCP server, to every agent that needs it.

For infrastructure, a protocol for tools turns tools into services with the usual service requirements, plus some new ones. Tool servers need authentication and authorisation that act on behalf of the end user, not the agent—an agent reading a user's email must have that user's permissions and no more, which typically means delegated tokens (OAuth) scoped per tool and per user. They need rate limits and timeouts, because agents call tools in loops and a misbehaving agent can hammer a backend. They need latency budgets, because tool time adds directly to task time (§17.6). And they need audit, because a tool call is an action taken on a user's behalf, and the security principles of §14.7—least privilege, confirmation for side effects, egress control—must be enforced at the tool boundary, not inside the model.

17.3 Sandboxes for model-generated code

Many of the most capable agents write and run code: to analyse data, test a fix, transform files or drive a browser. That code is untrusted in the strongest sense. It was produced by a model whose context may contain injected instructions (§14.7), it may be buggy enough to consume unbounded resources, and it runs on infrastructure shared with other users. It must therefore execute in a sandbox: an environment that limits what it can see and do, from which escape is hard, and whose resources are capped. Figure 17.3 compares the main isolation technologies.

Figure 17.3's left column, the ordinary container of Chapter 6, shares the host's kernel, so a single kernel vulnerability can let hostile code escape; it is adequate for trusted code and not for code an adversary may have influenced. gVisor, open-sourced by Google in 2018, runs a user-space kernel (the Sentry) that intercepts the sandboxed program's system calls and implements them itself, passing only a narrow, audited set to the host kernel; it shrinks the attack surface at the cost of some system-call overhead. Firecracker, open-sourced by AWS in 2018 and described by Agache and colleagues in 2020, is a minimal virtual machine monitor built on KVM that boots a stripped-down guest kernel in about 125 ms with about 5 MiB of memory overhead, so that each untrusted workload gets a hardware-virtualised boundary at almost container cost[2]; it was built for AWS Lambda and is used by several code-execution services for agents. Snapshot-and-restore of initialised microVMs (the idea of §5.7) brings start times down further.

Isolation of the kernel is only the beginning of a sandbox policy. A code sandbox for agents also needs resource limits (CPU, memory, disk, number of processes, wall-clock time) so that runaway code cannot exhaust a host; network policy, usually no egress by default or an allow-list of package mirrors and approved APIs, because exfiltration through the network is the main way an injected instruction can do harm (§14.7); filesystem scoping, so the sandbox sees only the files of its task; no credentials inside the sandbox beyond what the task strictly needs; and lifecycle management, creating sandboxes per task or per session, keeping them alive for follow-up steps, and destroying them reliably afterwards.

Worked example — sizing a sandbox fleet

Demand. A coding assistant runs 50,000 concurrent agent sessions at peak. Each session keeps a sandbox alive for its duration (mean 12 minutes) and uses it actively about 20% of the time; each sandbox is allocated 2 vCPUs and 4 GiB of memory, with a 10 GiB scratch disk.

Concurrency. By Little's law the number of live sandboxes equals the number of sessions: 50,000. Their allocations total 100,000 vCPUs and 200 TiB of memory if reserved in full.

Overcommitment. Because sandboxes are busy only 20% of the time and their CPU use is bursty and largely uncorrelated (§2.4's argument applies), CPU can be overcommitted perhaps four-fold: about 25,000 physical vCPUs, roughly 130 servers of 192 vCPUs. Memory is harder to overcommit safely; with idle sandboxes snapshotted to disk after a minute of inactivity and restored on demand, resident memory might fall to about a third.

Start time. At 50,000 sessions with 12-minute lifetimes, sandboxes are created at about 70 per second at peak; with microVM snapshots restoring in tens of milliseconds, creation is not a bottleneck, but image and dependency caching (§5.6) is essential, because a task that waits a minute for pip install at every step wastes the user's time and the model's KV memory.

Lesson. The sandbox fleet is a CPU-and-memory fleet of a size comparable to the GPU fleet's host CPUs, with its own scheduling, overcommitment and security policies.

17.4 Session state: what to do with the KV cache while a tool runs

Between two model calls of an agent, a tool runs: a search returns in a second, a test suite in thirty seconds, a human approval in minutes. During that time, the sequence's KV cache—possibly tens of gigabytes for a long context on a large model—is idle. The engine has three choices. It can hold the KV in HBM, so the next call starts instantly, at the cost of memory that could serve other sequences. It can offload the KV to host memory or SSD (Vol. I §10.7) and reload it when the tool returns, at the cost of transfer time and bandwidth. Or it can discard it and recompute the prefill when the call resumes, at the cost of prefill compute and latency. Abhyankar and colleagues studied this problem for "augmented" LLM requests in 2024 and showed that choosing per request among these options, rather than always discarding, improved throughput substantially[3].

The choice can be made from costs. Let the KV occupy \(m_{\text{kv}}\) bytes, holding a byte of HBM cost \(\varpi_{\text{hbm}}\) per second (the replica's price divided by its KV capacity), and the tool's expected duration be \(t_{\text{tool}}\). Holding costs \(\varpi_{\text{hbm}}m_{\text{kv}}t_{\text{tool}}\). Recomputing costs the prefill of the context, \(c_{\text{in}}\) per token times the context length (§10.4), plus extra latency. Offloading costs a much smaller rate \(\varpi_{\text{host}}m_{\text{kv}}t_{\text{tool}}\) for host memory, plus the transfer. Figure 17.4 compares them for a 30,000-token context on Llama 3 70B.

Figure 17.4's three regimes are general. For short tool calls (a few seconds), holding is cheapest and gives the lowest latency. For calls of tens of seconds to minutes, offloading to host memory wins: the KV of a 30,000-token context reloads in about 0.2 s over PCIe, much faster than re-prefilling it, and host memory is cheap. For very long pauses—a human approval that may take hours—even host memory is not free, and discarding the KV and recomputing it later (with the conversation kept durably as text, §17.7) is simplest. An engine or platform that knows the expected tool duration—from the tool's type and history—can choose automatically, and the orchestrator can help by telling the engine that a call will resume after a tool, rather than letting it treat the request as finished.

Drill 17.1 — When to recompute

Using Figure 17.4's assumptions (HBM KV cost \(5.6\times10^{-5}\) dollars per second for this 4.9 GB context, prefill cost $0.25 per million tokens), at what tool duration does holding the KV in HBM cost the same as recomputing 30,000 tokens? What does the answer become for a 120,000-token context, and why?

Solution. Recompute: \(30{,}000\times0.25\times10^{-6}=\$0.0075\). Break-even: \(0.0075/5.6\times10^{-5}\approx134\) s. For 120,000 tokens, the KV is four times larger, so the holding cost rate is four times higher, but the recompute cost is also four times higher (in this linear model), so the break-even is the same 134 s. In reality the recompute cost grows faster than linearly for long contexts (attention is quadratic in prefill, Vol. I §3.8), so long contexts favour holding or offloading for longer; and recompute adds latency that grows with length, which the user feels directly.

17.5 Scheduling programs, not requests

The schedulers of Vol. I Chapter 11 treat each request independently: first come, first served, or with priorities and fairness across tenants. For agent traffic this is the wrong unit. An agent's value is the completion time of the whole program, which is the sum of its model calls' latencies plus its tool times, and a scheduler that ignores the program structure makes systematically poor choices. A long-running program's twentieth call waits behind a burst of short chat requests, although delaying it delays a task that has already consumed a great deal of service; or, under first-come-first-served, one very long program's calls repeatedly block many short programs, inflating their completion times, the classic convoy effect.

Program-aware schedulers address this by giving the engine knowledge of programs. Parrot (2024) introduced semantic variables that let applications expose the data dependencies between LLM calls, so the system can schedule a program's calls together, batch calls that share prefixes, and optimise end-to-end latency rather than per-request latency[4]. Autellix (2025) treats each agent program as a unit and schedules its calls by the program's cumulative service so far, a form of the least-attained-service policy from queueing theory, which, when program lengths are heavy-tailed and unknown in advance, favours programs that have consumed little service and lets short programs finish quickly without starving long ones; it reported large reductions in program completion time over per-request scheduling[5]. Figure 17.5 illustrates the difference.

For the mathematician — why least attained service helps heavy-tailed jobs

When job sizes are unknown in advance but drawn from a distribution with a decreasing hazard rate—as heavy-tailed distributions such as the Pareto and many lognormals have—a job that has already received a lot of service is likely to need a lot more. Least-attained-service scheduling (also called foreground–background) always serves the job that has received the least service so far, so new and short jobs overtake old, long ones. For decreasing-hazard-rate size distributions it minimises the mean response time among policies that do not know sizes, a classical result of queueing theory; for increasing hazard rates it is a poor choice. Agent programs, whose numbers of steps vary from a handful to hundreds with a long tail, fit the favourable case, which is why program-level attained service is a good scheduling key for agent traffic.

17.6 What agent loops cost, and how long they take

An agent task's cost and latency are sums over its steps, and it is worth computing them for a realistic case before deciding how to optimise.

Worked example — the cost of a coding-agent task

Task. A coding agent fixes a bug in 40 steps. It starts with 4,000 tokens of instructions and tool definitions; each step the model writes about 300 tokens (reasoning and a tool call) and the tool returns about 1,200 tokens (file contents, test output). The model is a 70B-class model priced at $0.60 per million uncached input tokens, $0.15 per million cached, and $2.40 per million output tokens (Atlas's list prices, §10.6).

Without prefix caching. Prefill tokens: about 1.33 million (Figure 17.2), costing about $0.80; output: \(40\times300=12{,}000\) tokens, about $0.03. Total about $0.83.

With prefix caching. Uncached input: about 62,500 tokens, $0.04; cached input: about 1.27 million tokens, $0.19; output $0.03. Total about $0.26, a third of the cost—and on a self-hosted fleet, where cached tokens cost the provider almost nothing (§10.4), the compute falls twentyfold.

Latency. Model time per step: prefill of 1,500 new tokens (about 60 ms) plus 300 output tokens at 30 ms each (9 s): about 9 s per step, 6 minutes of model time in total. Tool time: file reads in milliseconds, test runs perhaps 20 s each for 10 of the steps: about 3–4 minutes. The task takes about 10 minutes, dominated by decoding the model's output.

Levers. Fewer output tokens per step (concise tool calls, less verbose reasoning), parallel tool calls, a faster or smaller model for routine steps (routing, Vol. I §27.6), speculative decoding for decode-heavy steps (Vol. I Chapter 20), and caching—in that order of effect for this task.

The example generalises in three ways. First, for long agent tasks, the cached input dominates token counts and the output dominates latency, so prefix caching is the cost lever and decode speed is the latency lever. Second, agent tasks are where speculative decoding and smaller specialised models pay off most, because their outputs are often formulaic (tool-call syntax, repeated code) and draft models predict them well. Third, because tasks run for minutes and consume dollars rather than fractions of a cent, they need budgets: limits on steps, tokens, tool calls and wall-clock time per task, enforced by the orchestrator, so that a confused agent looping on a failing test cannot run up an unbounded bill (the "denial of wallet" of §14.8, self-inflicted). Rate limits stated per request (Chapter 11) do not capture this; agent platforms limit per task and per user per day as well.

17.7 Reliability of multi-step workflows

A task that requires every one of \(n_{\text{step}}\) steps to succeed, each independently with probability \(p_{\text{step}}\), succeeds with probability \(p_{\text{step}}^{\,n_{\text{step}}}\), and that number falls fast. Figure 17.6 shows it: at 99% per step, a 50-step task succeeds 61% of the time; at 95%, under 8%. "Steps" here include infrastructure failures—a timeout from a tool, a dropped connection, a rate-limit rejection, a crashed sandbox—as well as the model's own mistakes.

Figure 17.6 says that agent infrastructure must be engineered for reliability across steps, and the tools for that come from distributed systems. Retries of transient failures—tool timeouts, rate limits, dropped streams—turn a 95% step into a 99.75% one, provided the retried actions are idempotent: a tool call that creates a ticket or sends an email must carry an idempotency key (§11.7) so that retrying it does not do it twice. Durable execution records the workflow's state—the conversation so far, the results of completed tool calls, the sandbox's files—after every step in a durable store, so that a crash of the orchestrator, a replica or a sandbox resumes the task from its last completed step rather than from the beginning; workflow engines built for this pattern (in the style of Temporal) are increasingly used to run agents. Timeouts and budgets stop tasks that are not converging. Checkpoints for humans—asking the user to approve an action, or to clarify an ambiguity—both catch errors and bound the damage of injected instructions. And tracing every step, with its inputs, outputs, latency and cost, makes failures diagnosable; an agent trace is the equivalent of a distributed-systems trace with a model call at each span.

Drill 17.2 — How much do retries buy?

A 40-step task fails at each step with probability 2%. Three quarters of these failures are transient (timeouts, rate limits, dropped streams) and succeed if retried; the rest are permanent (the model takes a wrong action). What is the task's success probability with no retries, and with one retry of every transient failure? What bounds any further improvement from retries?

Solution. Without retries: \(0.98^{40}\approx0.446\). With one retry, a step fails permanently with probability 0.005, or transiently twice with probability \(0.015\times0.015\approx0.0002\); per-step success is about 0.9948, and \(0.9948^{40}\approx0.81\). Even unlimited retries cannot exceed \(0.995^{40}\approx0.82\), the ceiling set by permanent failures. Beyond that point the levers are not infrastructural—better models, verification steps, human checkpoints—which is why measuring the split between transient and permanent failures is the first step in any agent reliability review.

Figure 17.7 shows how durable execution also solves the long-pause case of §17.4: when a task waits hours for a human, its KV is discarded, its sandbox snapshotted, and its state kept as a record; when the approval arrives, the orchestrator resumes, the engine re-prefills (cheaply, from the prefix cache if it is still warm, otherwise at a modest one-time cost), and the task continues. Reliability, cost and resource efficiency all improve together.

17.8 Agent platforms as infrastructure

An organisation that runs agents at scale ends up operating a platform with components from every chapter of this volume: an LLM serving fleet with session affinity, prefix caching and KV policies tuned for tool pauses (Chapters 8 and 10); a sandbox fleet with strong isolation, network policy and snapshotting (Chapters 6, 7 and 14); tool gateways with delegated authorisation, rate limits and audit (Chapters 11 and 14); a durable orchestration layer with budgets, retries and checkpoints (Chapter 13); observability that traces programs, not just requests; and cost attribution per task and per user (Chapter 10). Security deserves the last word: an agent with tools is the system in which prompt injection (§14.7) turns into real actions, so least privilege, confirmation of side effects, egress control and audit are not optional features but the conditions under which agents can be deployed at all. The models decide what to do; the infrastructure decides what they are able to do.

Looking ahead

Agents, retrieval and multimodal inputs all widen what flows into and out of a model—and with it the scope for harmful content: injected instructions in retrieved documents, requests for dangerous information, outputs that violate policy, images and audio that must be screened. Every major LLM service therefore runs a second set of models alongside its main ones: classifiers that inspect inputs and outputs and decide what to allow. Where do these guard models run, how do they keep up with streaming output, what do they cost in latency and compute, and how should their thresholds be set when harmful content is rare? Chapter 18 develops the infrastructure of guardrails and moderation.

Warm-up Why does an agent's cost grow quadratically with steps, and how do you fix it?

Each step appends model output and tool results, so step i's context is n₀ + (i−1)n_Δ. Re-prefilling the full context each step gives total prefill n n₀ + ½ n(n−1) n_Δ, quadratic in n. Prefix caching reuses the KV of the unchanged prefix, so only the new n_Δ tokens are prefilled: n₀ + (n−1) n_Δ, linear. Make it work: append-only contexts (no timestamps or reordering near the top), session affinity to the same replica, keep or offload KV during tool calls, and use cached-input pricing. For a 40-step task this is ~20× fewer prefill tokens.

Warm-up What is MCP and what infrastructure does a tool server need?

The Model Context Protocol (Anthropic, 2024) is a client–server JSON-RPC protocol through which agent applications discover and call tools, read resources and use prompt templates from servers, over stdio locally or HTTP with streaming remotely. A tool server is a service: it needs user-delegated authorisation (OAuth scopes per user and tool), input validation, rate limits and timeouts, latency budgets, idempotency for side-effecting tools, audit logging, and the security controls of least privilege and confirmation for dangerous actions.

Warm-up How would you run model-generated code safely?

In a sandbox with a strong boundary: gVisor or Firecracker microVMs (not plain containers sharing the host kernel), created per task or session from snapshots for fast start; resource limits (CPU, memory, disk, processes, wall time); no network egress by default or an allow-list (package mirrors, approved APIs); scoped filesystem with only task files; no credentials; separate from model-serving and control-plane networks; destroy after use; monitor for abuse (crypto mining, scanning); audit executed code and outputs.

Core What should the engine do with a sequence's KV cache while a tool runs?

Choose by expected pause: hold in HBM for short pauses (cost ∝ HBM rate × bytes × time, best latency); offload to host memory (or SSD) for tens of seconds to minutes and reload (0.2 s for ~5 GB over PCIe, cheap memory); discard and recompute for long pauses (fixed prefill cost plus latency). Break-even hold vs recompute ≈ recompute cost / HBM holding rate (~134 s in the 70B example). The orchestrator should tell the engine that a call will resume and how long the tool usually takes; engines (InferCept-style) can then decide per request; prefix caching across replicas or hierarchical KV stores make recompute rarely needed.

Core Estimate the cost and latency of a 40-step coding-agent task.

n₀ = 4,000 tokens, each step adds 300 output + 1,200 tool tokens. Without caching: ~1.33M prefill tokens (~$0.80 at $0.60/M) + 12k output ($0.03) ≈ $0.83. With caching: 62.5k uncached ($0.04) + ~1.27M cached ($0.19 at $0.15/M) + output $0.03 ≈ $0.26. Latency: per step ~60 ms prefill + 300 tokens × 30 ms ≈ 9 s, ~6 min of model time; tools (tests) a few minutes: ~10 min total, decode-dominated. Levers: caching (cost), shorter outputs, parallel tools, smaller/specialised models for routine steps, speculative decoding (latency), budgets.

Core Why does a 40-step workflow fail so often, and how do you make it reliable?

Success compounds: p^n; at 98% per step, 40 steps succeed ~45%. Failures include model errors and infrastructure faults (tool timeouts, rate limits, dropped streams, crashed sandboxes or replicas). Fixes: retries for transient faults with idempotency keys for side effects (95% → 99.75% per step); durable execution recording each completed step so crashes resume rather than restart; timeouts and budgets; validation of tool outputs and structured outputs; human checkpoints for risky actions; better models or verification steps for model errors; tracing every step for diagnosis.

Core Compare containers, gVisor and Firecracker for agent sandboxes.

Containers: namespaces/cgroups/seccomp on a shared host kernel; millisecond start, negligible overhead; boundary is the kernel's syscall surface—too weak for hostile code. gVisor: user-space kernel intercepts and implements syscalls, passing a narrow set to the host; ~100 ms start, syscall-heavy workloads slower; much smaller attack surface. Firecracker: minimal KVM-based microVM with its own guest kernel; ~125 ms boot, ~5 MiB overhead, snapshots for faster restore; hardware-enforced boundary; used by Lambda and agent code-execution services. Choose microVMs or gVisor for untrusted code at scale; containers only inside a VM per tenant.

Deep-dive Explain program-aware scheduling for agent workloads and why least attained service helps.

Per-request schedulers optimise each call; agent value is program completion time = Σ calls + tools. FCFS creates convoys where long programs' calls delay many short programs. Program-aware schedulers track programs: Parrot exposes inter-call dependencies (semantic variables) to co-schedule and share prefixes; Autellix prioritises calls by their program's cumulative attained service. For heavy-tailed program lengths with decreasing hazard rates (long programs likely to continue), least-attained-service minimises mean response among size-oblivious policies, so short programs finish fast while long ones still progress (relative priority, no starvation if combined with ageing). Combine with session affinity and KV retention across tool calls.

Deep-dive How do agents change capacity planning for an LLM fleet?

Token mix shifts to very long, mostly cached contexts and many output tokens per task; prefill per step is small if caching works but KV residency per session is large and long-lived (contexts of 50–200k tokens held across tool pauses), so KV capacity and offload bandwidth become binding rather than FLOPs; session affinity reduces routing flexibility; bursts of parallel tool calls and sibling calls share prefixes. Plan in sessions × context size × residency time for KV, output tokens for decode, and uncached deltas for prefill; add host-memory/SSD KV tiers; sandbox and tool fleets as separate capacity; budgets per task to bound tail usage; forecast tasks, not requests.

Design Design the infrastructure for a coding agent serving 50,000 concurrent sessions.

LLM tier: 70B-class model (or mix with a smaller model for routine steps) with session-affine routing, append-only context discipline, prefix caching, hierarchical KV (HBM → host → SSD) with tool-duration-aware policies, speculative decoding; capacity from sessions × KV size and output tokens. Sandbox fleet: Firecracker microVMs from snapshots, ~50k live, CPU overcommit with idle snapshotting, cached package mirrors, no egress except allow-list, per-task filesystem (repo checkout), resource limits. Tools via MCP servers (repo, CI, issue tracker) with delegated auth. Durable orchestrator with per-step checkpoints, retries with idempotency, budgets (steps, tokens, time), human approval for pushes. Tracing and cost per task. Security reviews for injection paths (README instructions, issue text).

Design A customer-service agent can issue refunds. How do you make that safe?

Least privilege: refund tool scoped to the authenticated customer's orders, with amount limits per refund and per day; policy checks in the tool (eligibility rules) not in the prompt; confirmation step (customer confirms; human approval above thresholds); idempotency keys so retries cannot double-refund; separation of trusted instructions from untrusted content (order notes, emails) to resist injection; rate limits per customer and agent; anomaly detection on refund patterns; full audit trail with reasoning traces; durable workflow with resumable steps; red-team tests with injected instructions; fallback to human agent.

Core How do you prevent runaway agent costs?

Per-task budgets on steps, tokens (input, output), tool calls and wall-clock time enforced by the orchestrator; per-user daily limits; detection of loops (repeated identical tool calls, no progress); cheaper models for routine steps; caching discipline; alerts on cost per task distribution; clear termination with partial results; pricing that passes costs to users for long tasks; dashboards of cost per task by agent type. Treat it as self-inflicted denial of wallet.

Deep-dive What is durable execution and why does it suit agents?

A workflow engine records each step's inputs and outputs durably (event log); on failure or restart, it replays from the log, skipping completed steps (whose results are recorded) and resuming at the failed one; side-effecting steps carry idempotency keys. For agents: crashes of orchestrator, model replica or sandbox resume mid-task instead of restarting 40 steps; long waits (human approval, slow tools) hold no GPUs or sandboxes—just a record; retries and timeouts are policy; traces come for free. Requirements: deterministic orchestration logic around nondeterministic model calls (record model outputs), state size management (conversation and file snapshots), and versioning of workflows.

Core How should tools be exposed to agents across a large company?

Wrap internal systems as MCP (or equivalent) servers maintained by owning teams; central registry of tools with descriptions, schemas, owners, risk levels; gateway enforcing user-delegated auth, scopes, rate limits and audit; classify tools by side effects (read-only vs write vs irreversible) with confirmation policies; latency SLOs per tool; versioned schemas; sandboxed execution for code tools; monitoring of tool errors and agent misuse; documentation that is also model-readable (good descriptions improve tool selection).

Deep-dive When is it better to discard and recompute KV than to offload it?

When the pause is long enough that even cheap storage costs more than recompute (hours), when offload bandwidth or capacity is the bottleneck (many sessions pausing at once), when the context will be heavily modified anyway (summarisation), when the session may resume on a different replica or region (recompute there from durable text, or fetch from a shared KV store if available), or in confidential-computing environments where host transfers are expensive (§14.2). Recompute latency matters: for long contexts it can be seconds; prefix caching across replicas and shared KV stores (Mooncake-style) narrow the gap.

Warm-up How does serving agent traffic differ from serving chat traffic?

Unit of work is a program of many dependent calls; contexts grow and are heavily cached; calls pause for tools whose latency the engine doesn't control, so KV residency and offload policies matter; end-to-end task latency and cost matter more than per-call TTFT; outputs (tool calls, code) are formulaic and decode-heavy; untrusted code needs sandboxes; reliability compounds over steps; budgets are needed per task; security risk rises because outputs become actions. Infrastructure responds with session affinity, KV tiers, program-aware scheduling, sandboxes, tool gateways and durable orchestration.
