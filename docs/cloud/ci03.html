Accelerators as Cloud Products

Most teams never touch a GPU. They rent an instance: a bundle of accelerators, host CPUs, memory, local disk and network bandwidth, sold by the hour or by the year under a name such as p5.48xlarge or a3-highgpu-8g. This chapter explains what is inside those bundles and how they are virtualised, how one GPU can be safely divided among several workloads, how Google's TPUs, Amazon's Trainium and AMD's Instinct GPUs compare as products, and how to choose the cheapest hardware that meets a model's memory, latency and throughput requirements.

Why this chapter

Volume I described accelerators as an architect sees them: streaming multiprocessors, tensor cores, HBM and NVLink (Vol. I Chapter 5). Chapter 2 of this volume described them as a facilities engineer sees them: kilowatts and litres of coolant. Neither is how most engineers meet them. An inference team at a typical company opens a cloud console, sees a list of instance types with prices, and must choose. The choice decides the cost of every token the team serves for the next one to three years, and it is constrained by things the architecture diagrams do not show: how many GPUs come in one instance, whether the instance is a virtual machine or bare metal, what network bandwidth it has, whether the type exists in the region the team needs, and whether the cloud will actually sell it.

Interviewers probe this layer because it is where the theory of Volume I meets a budget. "Would you serve Llama 3 8B on L4s or H100s?" has a quantitative answer, and it depends on traffic. "Can we give each of our forty customers an isolated GPU for their fine-tuned 8B model?" has an answer involving MIG. "Should we move our 70B model from H100s to MI300X or TPUs?" has an answer involving memory per device, bandwidth per dollar and software maturity. By the end of this chapter you should be able to give all three.

We start with what an instance is, and why GPUs in a virtual machine run nearly as fast as on bare metal (§3.1). We survey the instance catalogue and its common anatomy (§3.2). We then derive the two quantities that decide whether a device can serve a model—whether it fits, and what latency floor its bandwidth imposes—and compare devices by cost per token (§3.3). We examine three ways of sharing one GPU among workloads and the isolation each provides (§3.4), survey the non-NVIDIA accelerators as products (§3.5), and assemble everything into a procedure for choosing hardware (§3.6). We end with the practical question of availability (§3.7).

Learning objectives
  1. Explain virtual machines, hypervisors, PCIe passthrough and bare-metal instances, and why accelerator performance in a VM is close to bare metal.
  2. Read an instance specification (GPUs, HBM, vCPUs, host memory, local NVMe, network bandwidth) and identify what matters for inference.
  3. Compute whether a model fits on a device, the maximum batch it allows, the TPOT floor set by bandwidth, and the resulting cost per token.
  4. Compare time-slicing, MPS and MIG for sharing a GPU, quantify their interference and isolation, and say when each is appropriate.
  5. Describe TPUs, Trainium/Inferentia and AMD Instinct GPUs as cloud products, including their software stacks and scale-up domains.
  6. Apply a step-by-step procedure for choosing hardware for a model, traffic level and latency target.

Uses: GPU architecture (Vol. I Chapter 5), the decode latency model (Vol. I §3.7), KV-cache sizes (Vol. I §3.4, Chapter 8), quantisation (Vol. I Chapter 14), parallelism (Vol. I Chapter 18) and Chapters 1–2 of this volume.

3.1 What you rent: instances, virtual machines and bare metal

A cloud instance is a computer that a customer can boot and control, carved out of the provider's physical servers. For most of the cloud's history an instance was a virtual machine (VM): a software-defined computer presented by a hypervisor, a thin layer of software that runs directly on the physical server and multiplexes its CPUs, memory, disks and network among several guest operating systems. Each guest believes it owns a computer; the hypervisor ensures that it cannot see or disturb the others. Virtualisation was what made the cloud possible: one physical server could be sold to many customers, resized, migrated and reclaimed without touching hardware.

For the mathematician — virtualisation as faithful simulation

Think of a computer's instruction set as an abstract machine: a state space (registers, memory, device state) and a transition function for each instruction. A hypervisor provides a simulation of that machine for each guest: a map from the guest's state to a subset of the real machine's state such that executing a guest instruction and then mapping gives the same result as mapping and then executing the corresponding real operations. In 1974 Popek and Goldberg showed that efficient virtualisation is possible when every instruction that could reveal or change the real machine's control state is "privileged"—it traps to the hypervisor when a guest executes it—so that all other instructions can run directly on the hardware at full speed. Modern CPUs added hardware support (Intel VT-x, AMD-V) that makes this condition hold, so a guest's ordinary computation runs natively and only privileged operations pay the cost of a trap.

Accelerators fit this picture through PCIe passthrough. A GPU is a device on the server's PCI Express bus. Rather than emulating a GPU in software, which would be hopelessly slow, the hypervisor assigns the whole physical GPU to one guest, and the server's I/O memory-management unit (IOMMU) translates the device's memory accesses so that it can read and write only that guest's memory. The guest loads the ordinary NVIDIA driver and talks to the GPU directly. Kernels run on the GPU exactly as they would on bare metal, and the data path between the GPU and its HBM does not involve the hypervisor at all. That is why a GPU in a well-designed VM delivers within a few percent of its bare-metal performance for compute-bound and memory-bound kernels alike. The costs of virtualisation appear elsewhere: in the host CPU cycles the hypervisor consumes, in the latency of interrupts and some I/O, and in the network path.

Network and storage I/O used to be the expensive part, because every packet passed through the hypervisor's software switch. Providers removed that cost by moving I/O into dedicated hardware. AWS's Nitro system, introduced from 2017, offloads networking, storage and security functions to separate cards, so that the main server's CPUs run almost nothing but the customer's guest; network interfaces present themselves to the guest through SR-IOV (single-root I/O virtualisation), a PCIe feature that lets one physical NIC appear as many virtual NICs, each assignable to a guest. Other clouds built comparable offload hardware. With these, a GPU instance's host overhead is small, and the provider can also offer bare-metal instances: the customer gets the whole physical server with no hypervisor, while the provider's offload cards still enforce network isolation and manage the machine.

Whether a team wants a VM or bare metal depends on details that matter for AI. Bare metal gives full control of the GPU driver and firmware, of NVLink and the fabric manager that configures NVSwitch, of performance counters and of MIG configuration (§3.4); it removes the last few percent of overhead; and it lets the customer run its own virtualisation or Kubernetes stack. VMs give faster provisioning, live maintenance and integration with the provider's managed services. Most neoclouds sell bare metal; hyperscalers sell both, and their largest GPU instances are usually "whole-server" VMs that occupy an entire eight-GPU machine, because no other customer could use a fraction of it anyway. That brings us to what those whole-server instances contain.

Despite the variety, the large instances share one anatomy, shown in Figure 3.2 for an eight-GPU H100 instance. The GPUs sit on a baseboard and are joined by NVSwitch chips, so any GPU can talk to any other at 450 GB/s per direction (Vol. I §17.4). Each GPU has its own back-end NIC, 400 Gb/s for H100 generations and 800 Gb/s for Blackwell, connected to the cluster fabric (Chapter 4); on AWS this is the Elastic Fabric Adapter (EFA), elsewhere InfiniBand or RoCE. Two host CPUs, with 192 or so virtual CPUs (vCPUs, hardware threads) and 2 TB of DRAM between them, run the operating system, the inference engine's scheduler and tokenizer, and data loading. Several local NVMe drives, typically 8 × 3.84 TB, provide fast scratch space and a cache for model weights (Chapter 5). A separate front-end NIC connects to the provider's ordinary network for API traffic, storage and management.

Two features of Figure 3.2 shape how instances are used. First, the instance is indivisible along the NVLink domain. A model that needs tensor parallelism over eight GPUs must sit inside one instance (or one NVL72 rack), because NVLink does not cross instance boundaries; a model that needs only one GPU can be packed eight to an instance as eight independent replicas. Clouds therefore sell the large GPUs mostly as whole eight-GPU instances, and fractional sizes (one, two or four GPUs) exist mainly for the inference-class parts. Second, the host is not negligible. Volume I showed that an engine's CPU work—scheduling, tokenisation, detokenisation, sampling bookkeeping—can become the bottleneck when steps are short (Vol. I §12.2). Eight engines on one instance share 192 vCPUs, and a mis-sized host or a noisy process can slow all of them. Instance shapes that skimp on vCPUs per GPU are a false economy for small, fast models.

Below the flagship eight-GPU instances sits a tier of inference-class GPUs: NVIDIA's L4 (24 GB of GDDR6 memory, 300 GB/s, 72 W), L40S (48 GB, 864 GB/s, 350 W) and older A10G, sold one to eight per instance on PCIe without NVLink. They are much cheaper per hour than H100s and were marketed for inference. Whether they are actually cheaper per token is the question of the next section.

3.3 Fitting a model: memory, latency floors and cost per token

Choosing a device for a model starts with two questions that follow directly from Volume I's decode model. Does the model, with enough KV cache for a useful batch, fit in the device's memory? And can the device read that memory fast enough to meet the latency target? Only then does price enter.

Fit. A replica of \(n_g\) devices, each with memory \(M_{\text{HBM}}\) of which a fraction \(f_{\text{use}}\) is usable (the rest goes to the CUDA context, fragmentation and safety margins), must hold the weights \(W_{\text{bytes}}=N b_w\), a reserve \(M_{\text{act}}\) for activations, CUDA graphs and workspace, and the KV cache of \(B\) sequences of mean context \(\bar t\), each needing \(\bar t\,s_{kv}\) bytes. The largest batch that fits is

\[ B_{\max}=\left\lfloor\frac{n_g f_{\text{use}}M_{\text{HBM}}-N b_w-M_{\text{act}}}{\bar t\,s_{kv}}\right\rfloor . \]

Latency floor. In memory-bound decode, each step reads the weights and the batch's KV cache, so with effective bandwidth \(\beta_{\text{eff}}=n_g\cdot\text{MBU}\cdot\beta\) the step time is \(t_{\text{step}}\approx(Nb_w+B\bar ts_{kv})/\beta_{\text{eff}}\) (Vol. I §3.7). Even at \(B=1\) the step cannot be shorter than \(Nb_w/\beta_{\text{eff}}\): this is the device's TPOT floor for the model. For a target TPOT \(t^{*}\), the batch the bandwidth allows is \(B(t^{*})=(t^{*}\beta_{\text{eff}}-Nb_w)/(\bar ts_{kv})\), and the batch actually used is the smaller of \(B(t^*)\) and \(B_{\max}\). The decode throughput is then \(\Phi=B/t_{\text{step}}\), and the cost per million output tokens at price \(c_{\text{gpu}}\) per device-hour is \(n_gc_{\text{gpu}}\times10^6/(3600\,\Phi)\) at full utilisation (Vol. I §27.7).

Worked example — Llama 3 8B on four devices

Setup. Llama 3 8B in FP8: \(Nb_w\approx8.03\) GB; FP8 KV cache, half of the BF16 \(s_{kv}=128\) KiB, so 64 KiB per token; mean context 2,048 tokens, so 0.134 GB per sequence; \(f_{\text{use}}=0.9\), \(M_{\text{act}}=2\) GB, MBU 0.8. Illustrative prices per device-hour: L4 $0.80, L40S $1.80, H100 $2.50, H200 $3.50.

L4 (24 GB, 300 GB/s). KV space \(21.6-8.03-2\approx11.6\) GB, so \(B_{\max}=86\). \(\beta_{\text{eff}}=240\) GB/s, so the TPOT floor is \(8.03/240\approx33\) ms: the L4 cannot meet a 25 ms TPOT target for this model at any batch. At 50 ms it allows \(B\approx29\), about 590 tokens/s, or about $0.38 per million tokens.

L40S (48 GB, 864 GB/s). \(B_{\max}=247\), floor 11.6 ms. At 50 ms, \(B\approx198\): about 3,960 tokens/s, $0.13 per million.

H100 (80 GB, 3.35 TB/s). \(B_{\max}=462\), floor 3.0 ms. At 50 ms the memory limit binds: \(B=462\), step 26 ms, about 17,700 tokens/s, $0.039 per million.

H200 (141 GB, 4.8 TB/s). \(B_{\max}=872\), step 32.5 ms, about 26,800 tokens/s, $0.036 per million.

Check compute. At the H200's batch of 872, the step's \(2NB\approx1.4\times10^{13}\) FLOPs take about 12 ms at 60% of 1,979 TFLOP/s, below the 32.5 ms memory time, so the memory-bound model holds.

Lesson. Per token, at full load, the large GPUs are about ten times cheaper than the L4, because cost per token is price divided by bandwidth-limited throughput, and bandwidth per dollar is far higher on HBM parts. These are roofline upper bounds—real engines reach perhaps half to two-thirds of them once prefill and scheduling are included (Vol. I §27.9 measured 9,000 tokens/s on an H100 at batch 128)—but the ratios survive.

Figure 3.3 generalises the example by plotting each device's roofline decode throughput against the TPOT target. Each curve rises steeply just above its floor, as the bandwidth left over after reading the weights admits more sequences, and then flattens when memory capacity caps the batch. The L4 has no throughput at all below 33 ms; the H100 and H200 have most of their throughput available even at 10–15 ms.

Should anyone, then, serve an 8B model on an L4? Yes, when traffic is small. The cost-per-token comparison assumed every device was fully used. A service that receives only a few hundred output tokens per second still needs at least one replica running, and its cost is the price of that replica whatever its utilisation. The relevant comparison is the cost per token as a function of demand, which Figure 3.4 shows.

Figure 3.4 contains the practical rule. At low demand the curves fall as \(1/\lambda\), because the fixed cost of one replica is spread over more tokens, and the cheapest option is the device with the lowest price per hour. At high demand the curves flatten at the device's full-utilisation cost, and the cheapest option is the one with the most throughput per dollar. The crossover for an 8B model is a few thousand tokens per second. Many real deployments—an internal tool, a fine-tuned model for one customer, a staging environment—live on the left of the chart, and for them a smaller device is the right choice. The violet curve shows a third option: a slice of an H100 obtained by partitioning it, which combines the low price of a small device with the bandwidth per dollar of a large one. Partitioning is the subject of the next section.

Drill 3.1 — Does Llama 3 70B fit on one H200?

Llama 3 70B in FP8 has \(Nb_w\approx70.6\) GB; its FP8 KV cache is \(2\times80\times8\times128\times1=160\) KiB per token. With \(f_{\text{use}}=0.9\) and \(M_{\text{act}}=6\) GB, what batch of 4,096-token sequences fits on one H200 (141 GB), and what is the TPOT floor and the step time at that batch?

Solution. Usable memory \(0.9\times141\approx126.9\) GB; KV space \(126.9-70.6-6\approx50.3\) GB. Each sequence needs \(4096\times160\) KiB \(\approx0.67\) GB, so \(B_{\max}=74\). The TPOT floor is \(70.6/(0.8\times4800)\approx18.4\) ms. At \(B=74\) the step reads \(70.6+49.6\approx120\) GB, about 31 ms. A single H200 can therefore serve this model at a 40 ms TPOT with a batch of about 74, roughly 2,400 tokens/s—but with little headroom for longer contexts. Two H200s with TP2 double the bandwidth and quadruple the KV space (since the weights are now split), which is why 70B models are usually served on two or more devices even when one would technically suffice.

3.4 Sharing one GPU: time-slicing, MPS and MIG

Many workloads cannot fill an H100. A small embedding model, a 1B classifier, a lightly used fine-tune, a developer's notebook: each would use a few percent of the GPU. Giving each its own GPU wastes most of the hardware; putting several on one GPU raises two questions. How is the GPU's capacity divided among them, and how well is each protected from the others—from slowing them down, from crashing them, and from reading their data? NVIDIA GPUs offer three mechanisms, which make different trade-offs. Figure 3.5 compares them.

Time-slicing is the default when several processes use one GPU. Each process has its own GPU context; the GPU runs one context at a time and switches between them, giving each a turn of some milliseconds. Memory capacity is not partitioned—all processes allocate from the same HBM, and one can starve the others—and there is no performance isolation: if two processes are busy, each runs at roughly half speed, plus the cost of context switches. Time-slicing is useful for development and for workloads that are mostly idle. For latency-sensitive serving it is dangerous, because each tenant's step time depends on what the others are doing.

The Multi-Process Service (MPS) lets kernels from several processes run concurrently on the GPU's SMs, through a shared server process that funnels their work into one hardware context. Concurrency lets small kernels from different processes fill SMs that each process alone would leave idle, so MPS achieves higher utilisation than time-slicing for workloads with small kernels. Since the Volta generation, MPS clients have separate address spaces and can be given caps on the fraction of SMs they may use and on memory. Isolation is still weaker than separate GPUs: the processes share memory bandwidth and caches, and a fatal fault in one client can affect others served by the same MPS server. MPS suits cooperative workloads under one owner, such as several small models of the same team.

Multi-Instance GPU (MIG), introduced with the A100 in 2020 and continued in H100 and Blackwell, divides the GPU in hardware. An H100's compute is organised into seven slices of SMs and its memory system into eight slices of L2 cache, memory controllers and HBM capacity. A MIG instance combines some compute slices and some memory slices into what looks to software like a separate, smaller GPU, with profiles named by compute slices and memory: on an 80 GB H100, 1g.10gb (one-seventh of the SMs, 10 GB), 2g.20gb, 3g.40gb, 4g.40gb and 7g.80gb (the whole GPU). Because each instance has its own share of SMs, L2 and memory channels, one instance's load cannot slow another's kernels or memory accesses, and faults are contained. The price is rigidity: only certain combinations of profiles fit on one GPU, reconfiguration requires the affected instances to be idle, and the slicing granularity is coarse.

For LLM decode, MIG has a particularly clean interpretation. Since decode is memory-bound, an instance with a quarter of the memory slices delivers about a quarter of the GPU's bandwidth—about 0.84 TB/s for a 2g.20gb instance of an H100, comparable to an L40S, with 20 GB of capacity. In Figure 3.4, three such instances per H100 at a third of its price each give the violet curve: as cheap as an L4 at low demand and far cheaper at moderate demand. MIG turns one large GPU into several small ones with nearly the large GPU's bandwidth per dollar, and with isolation strong enough to serve different customers' models side by side.

For the mathematician — interference under time-slicing

Model a time-sliced GPU shared by \(k\) tenants as a processor-sharing server. If tenant \(i\) is active (has work queued) a fraction \(\upsilon_i\) of the time, independently, then when tenant 1 is active the expected number of other active tenants is \(\sum_{i\ne1}\upsilon_i\), and its work progresses at rate roughly \(1/(1+\sum_{i\ne1}\upsilon_i)\) of the full GPU, minus context-switch overhead. A tenant whose own requests need a 30 ms decode step on a dedicated GPU sees an expected step of \(30(1+\sum_{i\neq1}\upsilon_i)\) ms—but the distribution matters more than the mean: when all \(k\) tenants are busy at once, its step is \(k\) times longer, and the tail latency of each tenant is set by the joint busy periods of all of them. With MIG, each tenant's step is fixed by its slice regardless of the others: a dedicated slice of \(1/k\) of the bandwidth gives a step \(k\) times the dedicated-GPU step always. Time-slicing is better on average for bursty tenants and worse in the tail; MIG gives predictable, worse-on-average latency. This is the general trade-off between statistical multiplexing and hard partitioning.

Cloud providers expose these mechanisms in different ways. Kubernetes can advertise MIG instances or time-sliced "replicas" of a GPU as schedulable resources (Chapter 6). Some providers sell fractional-GPU instances backed by MIG or by NVIDIA's vGPU software, which virtualises a GPU across several VMs with time-slicing or MIG underneath. For multi-tenant inference platforms, the usual pattern is MIG when tenants are different customers and must be isolated, MPS or simply running several models in one engine process when one team owns all the models, and time-slicing only for development. Sharing helps when models are small. When models are large, the question becomes which large accelerator to use, and NVIDIA is not the only supplier.

Google's TPUs are the most mature alternative. They were designed from the start as systolic matrix engines (Vol. I §5.8) joined by a dedicated inter-chip interconnect (ICI) in a two- or three-dimensional torus, so a TPU "pod" is a scale-up domain of hundreds to thousands of chips without external switches. They are sold as slices of pods: a v5e slice of 8 chips for a small model, a slice of 256 for a large one. Inference-oriented generations (v5e, v6e) traded per-chip memory for cost; the 2025 Ironwood generation, explicitly aimed at inference, raised per-chip memory to 192 GB and bandwidth to about 7.4 TB/s. The software stack is XLA, the compiler behind JAX and PyTorch-XLA, and serving engines such as JetStream and a TPU backend for vLLM. TPUs serve Google's own Gemini models and are used by external labs; their advantages are cost, availability within Google Cloud and very large scale-up domains, and their main obstacle is that code written for CUDA kernels does not run on them.

AWS's Trainium and Inferentia are Amazon's own accelerators. Inferentia2 (2022) targeted inference; Trainium2 (2024), despite its name, is used for both training and inference, with 96 GB of HBM per chip, 16 chips per instance joined by a proprietary NeuronLink, and "UltraServers" of 64 chips. They are programmed through the Neuron SDK, which compiles PyTorch and JAX models and offers a vLLM integration. Their pitch is price–performance within AWS, and their largest public deployment is Anthropic's use of Trainium2 at very large scale. As with TPUs, adoption depends on whether a model's kernels and engine features have been ported.

AMD's Instinct GPUs are the most direct alternative to NVIDIA, because they are GPUs with a similar programming model, programmed through the ROCm stack and the HIP language, which mirrors CUDA closely. The MI300X (2023) stood out for memory: 192 GB of HBM3 at 5.3 TB/s per GPU, more than twice an H100's capacity, so a model that needs two H100s may fit on one MI300X, and a 70B model in FP8 fits with room for a large KV cache. The MI325X raised memory to 256 GB, and the MI355X (2025) to 288 GB with FP4 support. vLLM and SGLang run on ROCm, and several large inference deployments have used MI300X. The historical gap has been software maturity: kernels such as FlashAttention variants, FP8 paths and collective libraries arrived later and initially reached a lower fraction of peak than on NVIDIA hardware, though that gap narrowed through 2024–2025.

From the infrastructure engineer's point of view, a non-NVIDIA accelerator should be evaluated with the same quantities as any other—memory, bandwidth, scale-up size, price per hour, achieved MBU and MFU on the actual engine and model, availability in the needed regions—plus two extra costs: the engineering effort to port and maintain the serving stack, and the risk of depending on a less widely used toolchain. The next section turns this into a procedure.

3.6 Choosing hardware: a procedure

We can now assemble the pieces into a procedure that answers "which hardware should we serve this model on?" for any model, latency target and traffic level. The procedure is deliberately mechanical, because in an interview—and in practice—the value lies in doing each step explicitly and stating its assumptions.

  1. State the requirements. Model (parameters, architecture, KV size per token), precision the quality budget allows (BF16, FP8, FP4; Vol. I Chapter 14), latency targets (TTFT and TPOT at a percentile), traffic (mean and peak prefill and decode tokens per second, context distribution), and constraints (regions, residency, isolation, budget, delivery date).
  2. Find feasible replica shapes. For each candidate device, find the smallest number of devices \(n_g\) (respecting the parallelism the model allows—tensor-parallel degrees must divide the head counts, and must lie within one scale-up domain) such that \(B_{\max}\) is large enough for a useful batch at the typical context. Discard shapes whose TPOT floor \(Nb_w/(n_g\,\text{MBU}\,\beta)\), plus communication time, exceeds the target.
  3. Estimate throughput at the target. For each feasible shape, compute \(\Phi\) at the TPOT target with \(B=\min(B(t^*),B_{\max})\) and check that compute does not bind; account for prefill sharing the device. Better still, measure it with the real engine (Chapter 28 of Volume I describes how).
  4. Compute cost at the expected utilisation. Cost per million tokens \(=n_gc_{\text{gpu}}\times10^6/(3600\,\Phi\,u)\), and at low traffic, the cost of the minimum replica count (Figure 3.4).
  5. Apply the qualitative filters. Availability and quota in the needed regions, purchase terms (Chapter 9), software maturity and the cost of porting, power and cooling if self-hosted (Chapter 2), and operational familiarity.
  6. Decide, and plan to revisit. Choose, keep a second option qualified, and re-run the procedure with each new hardware generation or price change.

Figure 3.6 draws the same procedure as a decision flow, and it is worth reading from the bottom up as well as from the top down. Read top-down, it filters: each box in the left column removes hardware that cannot meet a hard requirement—memory, latency, isolation, availability—before any price is consulted. Read bottom-up, it explains why real decisions rarely land on the option with the best headline cost per token: that option often fails a filter that the spreadsheet did not encode, such as a regional quota or the absence of liquid-cooled capacity. Interviewers reward candidates who apply the filters explicitly and say which one bound. Note also the loop on the right of the figure: the decision is revisited whenever prices, generations or traffic change, which in 2023–2026 meant roughly every six months.

Worked example — Llama 3 70B: H100, H200, B200 or MI300X?

Requirements. Llama 3 70B in FP8 (70.6 GB of weights, 160 KiB of FP8 KV per token); 4,096-token contexts; a working batch of 128 sequences (86 GB of KV); 6 GB per device of activations and workspace; 40 ms TPOT. Illustrative prices per device-hour: H100 $2.50, H200 $3.50, B200 $5.00, MI300X $3.00.

Feasible shapes. The replica needs about \(70.6+86=157\) GB plus workspace. H100 (80 GB): three devices would hold it, but tensor parallelism must divide the 8 KV heads, so TP4 (320 GB) is the smallest shape. H200 (141 GB): TP2 (282 GB). B200 (180 GB usable class): TP1 holds 162 GB at 90%—too tight with workspace—so TP2; in FP4 weights (35 GB) a single B200 suffices. MI300X (192 GB): TP1 holds 173 GB at 90%, marginal, so TP2 for comfort.

Bandwidth per dollar. Decode throughput is roughly proportional to aggregate bandwidth (all shapes have room for the batch). H100 TP4: 13.4 TB/s for $10/h. H200 TP2: 9.6 TB/s for $7/h. B200 TP2: 16 TB/s for $10/h. MI300X TP2: 10.6 TB/s for $6/h. Per dollar: 1.34, 1.37, 1.60 and 1.77 TB/s per $/h respectively. B200 in FP4 on one device reads half the bytes, so it is equivalent to 16 TB/s of FP8 bandwidth for $5/h, 3.2 per $/h—if FP4 meets the quality bar.

Latency floors. At MBU 0.8 the weight-read floors are about 6.6 ms (H100 TP4), 9.2 ms (H200 TP2), 5.5 ms (B200 TP2) and 8.3 ms (MI300X TP2), all comfortably under 40 ms, though TP all-reduces add a few milliseconds per step (Vol. I §18.2).

Qualitative filters. MI300X leads on paper, but its delivered MBU on the team's engine must be measured, not assumed; if it reaches only 0.6 against 0.8 on NVIDIA, its advantage disappears. B200 needs liquid-cooled capacity that may be scarce. H200 is a drop-in upgrade for an H100 stack.

Decision. Benchmark B200 (FP8 and FP4) and MI300X on the real workload; meanwhile move from H100 TP4 to H200 TP2, which keeps the software unchanged and halves the devices per replica. The general lesson: more memory per device lowers the parallel degree, which lowers communication overhead and raises bandwidth per dollar.

The worked example illustrates a subtle point. Memory capacity per device matters beyond "does it fit". A larger device lets a replica use fewer devices, and a smaller tensor-parallel degree means fewer all-reduces per step, less communication overhead, and replicas that are smaller failure domains and easier to schedule (Chapter 7). This is why the H200 and MI300X, whose compute is no faster than an H100's, sold well for inference: they let 70B-class models run on two devices instead of four. Conversely, for very large mixture-of-experts models such as DeepSeek-V3, the decisive property is the size of the scale-up domain: expert parallelism over 72 GPUs in one NVLink domain (Vol. I §19.6) or over a TPU pod is far cheaper in communication than the same parallelism over a scale-out network, so rack-scale systems are the natural home of the largest models.

Drill 3.2 — Isolated replicas for forty customers

Forty enterprise customers each have a fine-tuned Llama 3 8B (merged weights, FP8) and demand an isolated replica that no other customer shares. Each customer's peak load is about 1,500 output tokens/s at a 50 ms TPOT. Compare dedicating one H100 per customer with using H100 MIG 2g.20gb instances (three per H100, each about 2,480 tokens/s at 50 ms from the model of §3.3).

Solution. Dedicated H100s: 40 GPUs, each about 8% utilised at peak. MIG: each customer fits in one 2g.20gb instance (20 GB holds 8 GB of weights plus about 8 GB of KV), whose roughly 2,480 tokens/s covers the 1,500 tokens/s peak at about 60% utilisation; three instances per H100 gives 14 GPUs. Hardware isolation of SMs, cache, memory capacity and bandwidth meets the "not shared" requirement in a way that time-slicing or MPS would not. Cost falls by about 65%. If customers' loads are bursty and their peaks do not coincide, a shared multi-LoRA deployment (Vol. I §27.4) would be cheaper still, but it would not satisfy the isolation requirement.

3.7 Availability: the hardware you can actually get

The procedure of §3.6 ranks hardware by cost per token, but the ranking is useless if the winning hardware cannot be obtained. In practice, availability is often the deciding factor, for four reasons that an infrastructure engineer must understand.

First, not every type exists in every region. New GPU generations are installed first in a few large regions and reach others over a year or more; TPUs exist only in Google Cloud regions, and the newest generations only in some of them. A team bound to a European region for data residency (Chapter 12) may find that the hardware of its choice is simply not offered there. Second, capacity is rationed through quotas. Clouds limit how many accelerators of each type an account may launch in each region, and raising the quota for scarce types requires a request, a business case and often a commitment to reserved capacity. On-demand access to eight-GPU H100 instances was, for much of 2023–2024, more a theoretical than a practical option. Third, purchase terms change the price by large factors: on-demand, reserved for one or three years, capacity blocks booked for days or weeks, and spot capacity that can be reclaimed at short notice all coexist, and the cheapest hardware on a per-hour basis may be available only on terms that do not fit the workload (Chapter 9). Fourth, portability is a hedge. A serving stack that runs well on two or three hardware families can take whatever capacity is available at the best price, while a stack tied to one family must accept that family's price and supply.

For these reasons, large serving organisations treat hardware as a portfolio. They keep their engines portable across NVIDIA generations and, increasingly, across vendors (vLLM and SGLang support NVIDIA, AMD and TPU backends; Trainium has a Neuron integration). They qualify each model on several hardware types, so that traffic can move when capacity or prices change. And they place each workload on the hardware where it is cheapest: latency-critical traffic on the newest NVLink domains, steady high-volume traffic on whatever offers the best bandwidth per dollar, small models on MIG slices or inference-class GPUs, and batch work on spot or older capacity. This portfolio is connected by networks, inside each cluster and between them, and those networks are the subject of the next chapter.

Looking ahead

We have treated each instance as a self-contained machine: eight GPUs, an NVSwitch, and eight NICs whose bandwidth we quoted without asking where the cables go. But replicas larger than one instance (disaggregated prefill and decode, wide expert parallelism, multi-node tensor or pipeline parallelism), the loading of weights, and the movement of KV caches between machines all depend on the network that joins thousands of these instances. How is that network built, what does its topology cost, why do flows collide in it, and what does inference need from it? Chapter 4 answers these questions.

Chapter summary

  • An instance is a VM or a bare-metal server. GPUs are passed through to VMs via the IOMMU, so kernels and HBM traffic run natively; offload cards (Nitro) and SR-IOV remove most network and storage virtualisation cost.
  • Large instances are whole eight-GPU servers with NVSwitch, one 400–800 Gb/s back-end NIC per GPU, about 192 vCPUs and 2 TB of DRAM, local NVMe, and a front-end NIC; rack-scale systems (GB200 NVL72, Trn2 UltraServers) are sold as units.
  • Fit: \(B_{\max}=\lfloor(n_gf_{\text{use}}M_{\text{HBM}}-Nb_w-M_{\text{act}})/(\bar ts_{kv})\rfloor\). Latency floor: \(Nb_w/\beta_{\text{eff}}\). Throughput: \(B/t_{\text{step}}\) at \(B=\min(B(t^*),B_{\max})\).
  • For Llama 3 8B, an L4 cannot meet a 25 ms TPOT (33 ms floor); at full load H100/H200 are about ten times cheaper per token than L4, but at low demand the cheapest replica wins (crossover at a few thousand tokens/s).
  • Time-slicing shares the whole GPU in turns (no isolation); MPS runs kernels concurrently (partial isolation, good utilisation); MIG partitions SMs, L2, memory capacity and bandwidth into up to seven isolated instances.
  • A MIG slice delivers roughly its share of HBM bandwidth, so it combines a small device's price with a large device's bandwidth per dollar—ideal for isolated small-model replicas.
  • TPUs (XLA, large torus pods, Ironwood for inference), Trainium2 (Neuron, UltraServers) and AMD Instinct (ROCm, 192–288 GB per GPU) are production alternatives; evaluate them by measured MBU, scale-up size, price and porting cost.
  • More memory per device lowers the parallel degree, reducing communication and raising bandwidth per dollar; for giant MoE models the scale-up domain size is decisive.
  • Availability—regional presence, quotas, purchase terms—often decides; portable serving stacks and multi-hardware portfolios are the hedge.

Warm-up What is inside a typical eight-GPU cloud instance, and which parts matter for inference?

Eight GPUs on an NVSwitch baseboard (scale-up, 450 GB/s per GPU per direction on H100), one back-end NIC per GPU (400–800 Gb/s; EFA, InfiniBand or RoCE) for scale-out, two CPUs with around 192 vCPUs and about 2 TB DRAM, several local NVMe drives, and a front-end NIC for API, storage and management. For inference: HBM capacity and bandwidth (decode), NVLink (TP within the instance), back-end NICs (disaggregation, multi-node EP, KV transfer), vCPUs (engine CPU work for small fast models), local NVMe (weight cache and cold starts), and the front-end network (request traffic, weight downloads).

Warm-up Compare time-slicing, MPS and MIG.

Time-slicing: processes take turns on the whole GPU; no partitioning of memory capacity, no performance isolation, works anywhere; fine for dev or idle workloads. MPS: a server process funnels kernels from several clients into one context so they run concurrently on shared SMs; optional SM-percentage and memory limits; better utilisation for small kernels; weaker fault isolation (shared server) and shared bandwidth and caches. MIG: hardware partitions (up to seven on A100/H100) with dedicated SM slices, L2, memory controllers and capacity; strong performance and fault isolation; fixed profiles, coarse granularity, reconfiguration needs idle instances. Use MIG for multi-tenant isolation, MPS for cooperative workloads under one owner, time-slicing for development.

Warm-up Why do GPUs run at nearly native speed inside VMs?

With PCIe passthrough, the hypervisor assigns the physical GPU to one guest and programs the IOMMU so the device can only access that guest's memory. The guest runs the normal driver and submits work directly; kernels and HBM traffic never touch the hypervisor. CPU virtualisation is hardware-assisted, so ordinary instructions run natively. Network and storage use SR-IOV and offload cards (e.g. AWS Nitro), removing software switching. Residual overheads are a few percent in host CPU, interrupts and some I/O paths.

Core Should we serve Llama 3 8B on L4s or H100s? Answer quantitatively.

It depends on latency and traffic. In FP8 the weights are about 8 GB; an L4 at roughly 240 GB/s effective has a TPOT floor of about 33 ms, so it cannot meet a 25 ms target at all; at 50 ms it supports about 29 concurrent sequences of 2k context, about 600 tokens/s. An H100 at about 2.7 TB/s effective has a 3 ms floor and, memory-capped at about 460 sequences, about 17,700 tokens/s roofline. At illustrative prices ($0.80 vs $2.50 per hour) the H100 is about ten times cheaper per token at full load. But one replica must run: below about 1,000 tokens/s the L4's lower hourly price wins, and the crossover is a few thousand tokens/s. A MIG slice of an H100 often beats both at moderate demand. So: low-traffic, latency-tolerant deployments on L4 or MIG slices; anything high-volume or under 30 ms TPOT on H100/H200.

Core What are TPUs' strengths and weaknesses as an inference platform compared with NVIDIA GPUs?

Strengths: large scale-up domains via ICI tori (pods of hundreds to thousands of chips; good for large models and expert parallelism), competitive price-performance in Google Cloud, inference-focused generations (v5e, v6e, Ironwood with 192 GB HBM and about 7.4 TB/s), mature compiler (XLA) and production use for Gemini. Weaknesses: available only on Google Cloud; requires XLA-compatible code (JAX, PyTorch-XLA), so custom CUDA kernels and some engine features must be reimplemented; smaller ecosystem of serving engines (JetStream, vLLM-TPU); dynamic shapes and some control flow are harder under compilation; older inference generations had small per-chip memory (16–32 GB).

Deep-dive Analyse latency interference between tenants under time-slicing versus MIG.

Time-slicing is processor sharing: with \(k\) tenants each active a fraction \(\upsilon_i\) of the time independently, tenant 1's work progresses at roughly \(1/(1+\text{number of other active tenants})\) of the GPU, so its expected step is inflated by \(1+\sum_{i\ne1}\upsilon_i\), and in the worst case (all busy) by \(k\), plus context-switch overhead. Tail latency is driven by joint busy periods, which are hard to predict and depend on neighbours' traffic. MIG gives each tenant a fixed slice—its step time is always about \(1/\text{share}\) of the dedicated step, independent of neighbours. So time-slicing has better mean latency for bursty, rarely-coincident tenants (statistical multiplexing) but unbounded, neighbour-dependent tails; MIG has worse mean but predictable latency. For SLO-bound multi-tenant serving, predictability usually wins; for internal bursty dev workloads, time-slicing or MPS wins.

Deep-dive Why did the H200 and MI300X sell well for inference even though their compute is similar to the H100's?

Decode is memory-bound: throughput tracks bandwidth and batch, which is limited by KV capacity. H200 (141 GB, 4.8 TB/s) and MI300X (192 GB, 5.3 TB/s) raise both. More capacity lets a model run on fewer devices (70B on two instead of four), which reduces tensor-parallel communication (fewer, smaller all-reduces relative to compute), shrinks failure domains and scheduling units, and frees KV space for larger batches, raising throughput per device. Bandwidth per dollar and per watt also improved. Compute matters for prefill, where the gain was smaller, but for decode-dominated serving the memory system determines cost per token.

Deep-dive When does a MIG slice beat a dedicated small GPU, and when does it not?

A MIG slice gets roughly its share of HBM bandwidth and capacity at roughly its share of the large GPU's price, so its bandwidth per dollar equals the large GPU's (much higher than an L4's GDDR6), while its absolute price is low. For memory-bound small models at low to moderate demand, it beats a dedicated small GPU on cost per token and offers isolation. It does not win when the slice's capacity is too small for the model plus useful KV (e.g. 10 GB slices for an 8B FP8 model), when the workload needs more compute than its SM share (prefill-heavy), when instance reconfiguration is frequent (MIG changes need idle instances), when the cloud does not offer MIG-backed fractional instances (you need whole GPUs and bare metal or Kubernetes MIG support), or when demand is high enough to fill whole GPUs, where whole-GPU replicas avoid slice overheads.

Deep-dive What are the risks of moving a production serving stack from NVIDIA to another accelerator family, and how would you de-risk it?

Risks: kernel coverage and performance (attention variants, FP8/FP4 GEMMs, MoE kernels, sampling) reaching lower MBU/MFU; feature gaps in the engine (prefix caching, speculative decoding, structured output, LoRA); numerical differences changing outputs; collective libraries and multi-node support; tooling for profiling and debugging; driver and firmware maturity; availability and support; and team expertise. De-risk: benchmark the exact model, engine version and workload (prompt and output length distributions, concurrency) with SLO-based goodput, not peak throughput; run quality evaluations for output parity; shadow traffic before cut-over; keep the serving layer portable (vLLM/SGLang backends, abstracted kernels); migrate a fraction of traffic with fast rollback; negotiate capacity and support terms.

Design Design the hardware portfolio for a provider serving 8B, 70B and 671B-MoE models with bursty and steady traffic.

Segment by model and traffic class. 671B MoE: rack-scale NVLink systems (GB200/GB300 NVL72) or TPU pods for wide EP within one scale-up domain, disaggregated prefill/decode; reserved capacity, since supply is scarce. 70B: H200 TP2 or B200 (FP8/FP4) for steady traffic on reserved capacity; H100 TP4 as overflow; MI300X if benchmarks justify. 8B: whole H100/H200 replicas for high-volume tiers; MIG slices for many low-traffic fine-tunes or isolated customers; L4/L40S for latency-tolerant edge regions. Batch and evaluation: spot or older-generation capacity. Keep the engine portable across at least two families; qualify each model on two hardware types; route traffic by cost and availability; revisit every generation. Tie the portfolio to power (tokens per joule in constrained sites) and to regions (residency).

Design You can get H100s on-demand in region A or reserved H200s in region B 1,500 km away. How do you decide?

Compute cost per token for each: price per GPU-hour (on-demand H100 is typically several times reserved H200), replica shape (70B on H100 TP4 vs H200 TP2) and throughput, expected utilisation (on-demand can scale with demand; reserved is paid whether used or not). Latency: 1,500 km adds roughly 15–25 ms RTT—negligible for chat, significant for voice or many-round-trip agents. Data residency: is region B allowed for the users' data? Capacity risk: on-demand availability in A may vanish at peaks; reserved capacity in B is guaranteed. Reliability: using both regions adds geographic redundancy. A common answer: reserve H200s in B for the predictable base load, serve latency-tolerant traffic there, keep a smaller on-demand footprint in A for latency-sensitive and residency-bound traffic and for bursts.

Core Why is cost per token at full utilisation a misleading basis for choosing hardware for a new product?

New products usually have low and uncertain demand. Each model, region and isolation domain needs at least one replica (often two for availability), whose cost is fixed regardless of traffic, so at low demand cost per token is set by the minimum replica's hourly price, not by its throughput per dollar (Figure 3.4). Large devices that are cheapest at scale can be ten times more expensive per token when mostly idle. Also, peak-to-mean ratios, latency headroom and spare capacity reduce average utilisation. Choose hardware for the expected demand curve, start small (MIG slices, smaller GPUs, or a shared multi-model or multi-LoRA deployment, or an API) and migrate to large devices as volume grows.

Core What do quotas and capacity reservations mean for an inference team, and how do you plan around them?

Clouds limit how many accelerators of each type an account can run per region; scarce types need approvals and often commitments. Capacity for a launch or growth must therefore be requested weeks or months ahead, justified with forecasts, and often reserved; on-demand may not be available at peaks. Plan by forecasting demand per model and region, reserving the base, holding approved quota (and ideally reserved headroom) for bursts and failover, qualifying alternative instance types and regions, keeping engines portable, and monitoring quota utilisation as a capacity signal. Treat "can we get the GPUs?" as a first-class risk in launch plans.
